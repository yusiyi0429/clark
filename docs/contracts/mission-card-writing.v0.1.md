# Mission Card 起草口径

依据：[TKOS_Mission_Card_Mission_Plan_v0.1_2026-09-30](https://tokenking.feishu.cn/wiki/E2QywBfU5i3bEvkNcIVc8esTn8f)，飞书正文 revision 26。本文记录当前实现的字段对应与起草验收要求；后续修订应重新核对原文。

## 字段对应

| 正式名称 | 数据字段 | 起草要求 |
| --- | --- | --- |
| Mission 名称 | `title` | 简洁、具体、可识别，能区分要达成的结果。 |
| Mission DRI | `ownerId` | 由服务器上的任务卡归属确定，模型不得另派负责人。 |
| 所属责任单元 | `battlefieldIds` | 使用已有责任单元，与签发目标保持一致。 |
| 时间边界 | `timeBoundary` | 只写确实影响结果责任的已知时限／窗口；缺少依据时明确待确认事项。 |
| 战役结果 | `outcome` | 最终必须成立的独立结果或状态，不能以动作清单、阶段或材料交付代替。 |
| 贡献／存在必要性 | `why` | 对接上级周期目标，说明删去这场 Mission 会留下什么具体结果缺口。 |
| 成功／验收标准 | `successEvidence` | 可由真实 Evidence 核验的事实或结果状态，足以证明战役结果成立。 |
| 责任边界 | `boundaries` | 负责到哪里、不负责什么、与其他责任对象如何分界，避免写成执行步骤。 |
| 核心路径 | `keyPath` | 从当前状态走向战役结果的主要逻辑顺序，不展开到 Activity 级。 |
| 关键取舍 | `tradeoffs` | 影响范围、优先级、资源、速度或质量的主动选择。 |
| 关键约束与依赖 | `dependencies` | 仅保留会实质改变路径、节奏或可行性的条件，避免通用风险清单。 |
| 关键里程碑 | `milestones` | 少量 Mission 层成立状态／结果；已有依据时关联时间、工作结果和责任人，不以会议或活动充当里程碑。 |

资源、人与 Agent 分工、风险和复盘是现有补充字段，不应为了填满而编造内容。执行拆分尚未开放，本次不虚构 Task 全景、Task DRI 或时间承诺。

## 起草与校验

1. 只以服务器提供的已签发目标、真实上月任务与复盘、相关公司认知为依据。模板中的示例不属于公司的实际任务或事实。
2. 生成真正需要的 Mission；不为达到固定数量而拆分、重复或凑条目。可识别但缺少具体依据的信息明确待确认，不补造数字、日期、人员、权限或业务结果。
3. 生成后单独审阅每项 Mission 的结果、贡献、Evidence、边界、路径、取舍、依赖和里程碑，并核对是否与来源及责任一致。审阅必须覆盖全部 Mission 与各项规则，引用当前字段中的真实正文片段；数组引用其中一条原文。发现具体问题后带着字段和修正方向修复一次，再审阅；仍不合格则不保存为可用草稿。
4. 校验含义，而非单纯禁止“材料”“Demo”“会议”等字词：这些可作为路径或 Evidence 的载体，但不能单独替代要达成的业务状态。
5. 正常起草失败时明确显示失败，保留成功任务，仅重试失败责任人的起草。不会自动导入演示占位文件或把上月任务复制成新的 Co-Agent 草稿。
6. 起草和质量审阅的记录保留在服务器。已有任务和确认内容不因此自动重写；后续正文修改仍保留批注原文、澄清答案以及前后版本。

所有生成仍是待人讨论和确认的草稿。质量审阅不代替现有拍板和最终确认权限。
