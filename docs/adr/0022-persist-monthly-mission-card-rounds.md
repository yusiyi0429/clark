# 本月 Mission Card 的制定轮次、候选与确认边界

日期：2026-09-27。依据：`.scratch/onboarding/design-04-mission-cards.md`，特别是 §0 的已定事项。本 ADR 修订 ADR-0019 对 Mission 生效、导入和编辑的口径，以及 ADR-0020 对成员可见范围的口径。

本月 Mission Card 用来让同一战场的团队形成相互兼容的结果承诺。月度计划签发批准公司与战场的当月目标；个人卡确认批准各人的结果、边界、证据与协作安排。这是两次不同的决定，不能因为计划已签发就把草稿 Mission 显示为“生效中”。

## 决策

1. **先签发目标，再整理个人卡草稿**。同周期 `monthly_plans` 必须已签发且包含本战场结果，拍板人才能整理草稿和开放讨论。首次开放时冻结六个月目标、本月目标和签发时间，并保存战场与月度计划的 id、version；重开只改变讨论窗口，不重新取目标依据。
2. **轮次、个人卡与 Mission 分开保存**。`mission_rounds` 按战场 × 月份唯一；`personal_mission_cards` 按轮次 × Owner 唯一，卡的 UUID 跨阶段、跨重开不变，成员在创建时保存并去重。个人任务就是挂到卡上的一条 `missions`，保留 13 个字段，不引入执行状态或完成率。已有战场轮次时禁止删除战场。
3. **草稿已入库，但尚未成为组织承诺**。整理时写入 v1 Mission，并通过 `personalCard.status` 区分 draft、open、reviewing、confirmed；只有整轮确认后才是生效的个人承诺。`placeholder` 表示来源性质，确认后也不抹去。Mission 列表、详情和配置页明确显示草稿及占位标记，不能从 MonthlyPlan 的签发状态推断个人卡已经确认。
4. **10 月使用有来源的讨论候选**。只读的 `mission-card-drafts.v1` 文件由 9 月五张个人卡整理出 12 项个人任务，只挂战场 01；不为其他人或战场补造卡。里程碑用“待定 · ”，来源保留原文档及 revision，`source_title` 写讨论候选说明；没有 10 月原件页签，不保存飞书全文副本。导入严格校验字段和人员、战场、能力域引用，允许文件已有的 `carriedFrom.note` 可选来源说明。动作与运维脚本共用事务导入函数，记录文件名、sha256、schema 和导入时间；同一文件重跑不覆盖，文件变化则拒绝。
5. **拍板动作使用独立端点，并复查当前权限**。`POST /api/mission-rounds/actions/execute` 使用 `requirePerson`，只允许 CEO 或当前战场 DRI；原有 CEO 专用 `/api/actions/execute` 保持原边界。动作沿用签名 actionId、version 和 fingerprint 幂等。拿到锁后重新读取当前战场负责人，在幂等重放和版本冲突响应前复查权限，旧令牌不保留旧权限。未建轮次的 draft 动作签名对象是 `mission-round-slot`；入口使用独立 `MissionRoundDraftPayload`，不伪造 roundId 或个人卡。04b 接通 `viewCardId`：写前核对个人卡可见且属于动作轮次，成功或版本冲突返回这一张个人卡投影；不传时仍返回轮次摘要。
6. **同战场统一、固定 48 小时，时间只取应用时钟**。数据库 CHECK 保证 `closes_at = opened_at + 48h`，各战场独立开放。启动及每 60 秒的调度、写入路径的 `closeIfDue` 都可触发截止快照；快照按 `created_at < closes_at` 收取公开意见，并记录当时的 Mission 版本。轮次锁与唯一约束保证重复执行只生成一份快照。已到截止但快照尚未生成时，投影可以显示 closed；数据库状态仍只保存 draft、open、reviewing、confirmed。
7. **公开意见与集中 Review 独立于私聊**。意见存入 `mission_card_feedback`，不混入 `thread_messages`；引用和修改建议保留原文与源版本。集中 Review 是快照、同字段冲突和依赖条数的确定性规则汇总，不称作 AI 语义判断。重开记录操作者、时间和上次截止，旧 Review 留痕；新截止纳入截止前的全部公开意见，包括上一窗口的截止后留言，并结转已有处理结论。协作核对结论不结转。公开意见一条不删，私聊不进入快照。
8. **挂卡 Mission 的普通编辑始终锁定**。无论草稿、讨论中、待拍板或已确定，`mission.edit` 都返回 409 `MISSION_IN_MISSION_CARD`，投影不再下发编辑动作。未挂卡的 Mission 保持既有编辑路径。`mission-round.confirm` 在整轮事务内检查快照内全部 Mission 版本、全部意见已处理、非空协作结论及同字段唯一采纳，只写采纳的字段，每个涉及采纳修改的 Mission 仅升一次版本，Review 保存 `note` 与实际写回的 `applied_versions`。相同 fingerprint 重放不再写入；已确定后的纠错与再修订属于 GAP-04，当前没有产品内绕过途径，需另定规则。

## 04a / 04b / 04c / 04d 落地范围与后续

04a 已实现迁移 032–034、轮次与 Mission 增量契约、草稿导入、开放、截止快照、重开、轮次读与动作端点、调度、运维脚本，以及 CEO 通知栏整理草稿入口。04b 将整理成功与已建轮次接到同页个人卡，CEO 与成员复用同一套工作区开合、来源焦点还原和两频道右列。

04b 提供卡页、三种公开意见、候选引用、群组时间线、单调已读与按人隔离的个人 Agent scope。意见在轮次锁内复查权限与时间，按作者和 client_id 幂等；未开放与已确定拒绝写入，截止后的评论和引用明确标为下一轮可收取的留言。页面使用校正服务端时间的共享分钟时钟，群组每 3 秒增量读取；新意见或分隔线变化同步刷新整页。开场不注入 Agent，私聊不进入意见快照。

04c 提供逐条处理与改判、冲突停用原因、跨卡待处理定位、规则汇总三步、协作核对表单和整轮确认。正文与群组的处理结果由服务端统一投影；群组返回轮次版本，版本变化时重新获取已有意见，避免增量消息序号不变而保留旧结论。重开清空前端未提交核对结论，下一次截止结转已有处理结果。确认后保留同一页、同一历史与占位来源，公开意见和业务事实只读；私人 Agent 仍可只读问答，不进入 Review。

04d 将同一个轮次投影接入成员通知顶部、CEO「战略决策更新」和引导。`GET /api/me/mission-cards` 只返回未确认轮次：当前拍板人可看全部行，其他人只看本人 Owner 行，普通成员关系不单独生成通知。通知不写入 `notifications`；跨月未确认仍保留，截止不退组，确认后退出。引导的 `work.missionCards` 只取公司当前月份的本人卡，已确定卡仍保留；Owner 即使没有 Mission 也计入参与战场。下一件事按当前轮次状态优先导航到本人卡、首条待处理意见或准确草稿 slot 的确认框，导航不直接执行整理。

通知和卡页复用同一服务端状态句及待办句，按 `closesAt` 共用一分钟时钟，越过截止立即重新读取；未生成快照时显示「已截止 · 汇总中」。共享时钟保留在 `useRoundNow.ts`，避免 Windows 上 `roundClock.ts` 与展示组件 `RoundClock.tsx` 发生大小写模块冲突。本人成功动作触发刷新，其他会话变化通过 20 秒轮询及前台焦点刷新同步。成员战场详情页尚未实现，其状态块和 Mission 小标留待 03 接入；现有 Mission 总览与详情继续复用 `MissionStatus`。

站内入口不表示同事已收到通知，首轮仍需人工在站外提醒；不接入 Agent 自动起草、演示拨钟、飞书提醒或跨战场卡合并。
