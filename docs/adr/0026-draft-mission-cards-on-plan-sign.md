# 签发即起草任务卡并自动交给本人；战场参与者名单

日期：2026-10-08。依据：用户 10/6 的决定（项目文档 `claude/决策记录_10月上线与协作批注_2026-10-06.md` 第一节第 2、2a–2e、4a 条），工单 `.scratch/october-launch/issues/02-auto-draft-on-sign.md`。

本记录变更 ADR-0022 第 1、5 条中「签发后由拍板人整理草稿、再开放讨论」的口径，以及 [本人准备与组合核对](../contracts/mission-card-preparation-review.v0.1.md)「战场 DRI 从准备进度入口交给本人确认」一句。之后的本人准备、组合核对、战场 DRI 确认与确认后更正不变。

## 决策

1. **签发即起草，系统身份，不冒充 DRI**。CEO 签发月度计划提交成功后，系统为计划里有本月结果的每个战场各建一轮任务卡并在后台起草。签发重放不再启动；已有轮次的战场跳过；参与者为空的战场不建轮次。轮次的 `action_fingerprints` 为空，`draft_source.trail` 记一条 `{ by: "system", text: "CEO 签发后系统起草" }`。起草启动在签发事务提交之后进行，启动失败只记日志、不改变签发结果。
2. **整个战场起草成功后一起交给本人**。`completeMissionRoundDraft` 结束时本轮没有起草失败，就以系统身份执行与原「交给本人确认」相同的检查与写入（已签发目标、每卡至少一项任务、冻结目标快照），并留痕 `起草完成后自动交给本人`。不做逐人提前推送。
3. **起草失败停在草稿，由战场 DRI 重试**。失败的人在 CEO 与战场 DRI 的准备进度里可见；重试沿用原 `mission-round.draft` 重试动作（只给战场 DRI），重试全部成功后同样自动交给本人。起草全部成功、但交给本人的检查不过（如战场缺六个月目标）时，轮次停在草稿，原因写入 `draft_source.openProblem` 并作为 CEO 与 DRI 的待办句；补齐后由战场 DRI 用原「交给本人确认」动作交付。人工导入的占位草稿同样走手动交付。
4. **拿卡的人 = 战场参与者，CEO 不拿卡**。`battlefield_config.participant_ids`（迁移 057）为 NULL 时按上月在本战场有任务卡或 Mission 的人推算（含本月已登记 Mission 的人，即原起草名单规则）；CEO 在战场配置里存过一次就以名单为准，空数组表示没人拿卡。起草名单去掉角色含 `ceo` 的人和人员目录外的人。配置页的推算按最新一份月度计划的月份计算，与签发后的起草一致。
5. **取消 DRI 的「整理任务卡草稿」入口和「交给本人确认」按钮**。首页、引导、CEO 只读 MCP 不再给尚未建轮次的战场入口；DRI 在本人准备阶段只看进度，最后的「确认任务组合」不变。签发确认框按战场列出会拿到任务卡的人，名单为空的战场标出来，签发不拦，每行可去战场配置改参与者。
6. **起草依据增加已知的本月任务**。`MISSION_CARD_KNOWN_MISSIONS_FILE` 指向只读挂载的文件（默认 `seed/imports/2026-10-known-missions.json`），只取月份与轮次一致、有原文的条目，按 personId 放进起草输入 `knownMissions`。提示词：有已知任务时以它为底，沿用它的拆分和标题，按已签发的目标、上月任务卡与复盘、起草规范补全和修正，不另起一套。文件未配置、缺失或格式不对时照常起草。

## 限制

- 签发提交后、起草轮次写入前若进程中断，这次签发不会再自动起草，也没有产品内入口补起；MVP 不做补偿，需人工处理。
- 各战场同时起草，模型并发等于参与者总数（10 月约 12 人）。
- 签发后再补参与者不会自动起草该战场。
