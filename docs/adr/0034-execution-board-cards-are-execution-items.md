# 执行看板：卡就是执行事项，看板只在 Task 下；跨 Task 只给 worker 列表

V2 要让本人把一个 Task 拆成几张卡，交给 Claude Code 等执行方去做，做完由 Agent 先验收，再进 Task 的交付物。设计全文见 `.scratch/next-phase/设计_执行看板与本机执行_V2_2026-11-06.md`（第 3、18、20 节）。本 ADR 修订 [ADR-0020](0020-members-sign-in-and-own-execution-items.md) 第 4 条里的「不做看板」。

## 决策

1. **卡不是新对象，就是执行事项。** `tasks` 表加执行方、模型、交代、对哪条标准、岗位几列（迁移 226、230），老事项也有 `card`。没有另一张「卡」表，执行事项的权限、事项群、进展、验收都照旧。
2. **看板只在 Task 下，四列读的时候算。** `GET /api/plan-tasks/:taskId/cards` 只给这个 Task 的负责人。列（待开始、进行中、验收中、已完成）和标记（等批准、等回复、暂停、验收未过、受阻）由事项状态、本机最近一次执行、最近一次交回和推翻记录现算（`taskCards.ts` 的 `stageAndWait`），不存。
3. **跨 Task 不做看板，只给 worker 列表。** `GET /api/me/workers` 列本人带岗位的卡和专题，分进行中、已排队、已完成（今天，上海时间），加资源摘要；`#号` 读的时候按开工先后算，不存。伙伴经 `/internal/me/workers` 读同一份。没有岗位的执行事项是人自己的活，不进 worker 列表。
4. **拆卡出草稿，人点了才建。** 伙伴拆出来的是 `card_drafts`，本人放进看板时才建执行事项；同一个 Task 同时只跑一次拆卡（部分唯一索引）。
5. **进交付物先进「准备中」。** 验收通过的卡、本人点的专题版本进 `deliverable_pending_items`，本人点「出下一版」时连同上一版的材料一起出一版交付物（原有的交付物评审照常自动开始）。

## 和 ADR-0020 的关系

ADR-0020 第 4 条说成员工作台「不做项目管理、看板」，当时是为了把内测范围收窄到发信号、执行事项和事项群。V2 的看板不是项目管理：它不加新的任务层级、不排期、不分派给别人，只是把本人一个 Task 下的执行事项按「谁在做、做到哪」排成四列，卡仍是本人的执行事项。所以只修订「不做看板」这一句，ADR-0020 其余部分不变。

## 后果

- 看板和 worker 列表都是投影，改执行事项的地方不用同步看板；代价是每次读要多查本机执行、交回和推翻几张表。
- 老事项不用迁数据就能上看板；没设执行方的老事项从本机交回时当作 Claude Code 做的。
- 跨 Task 的总览只有 worker 列表这一种，想看「所有卡」的需求以后再说。
