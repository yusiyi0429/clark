# Agent 先验收、本人可推翻；岗位长期存在，验收里学到的提成岗位修改

卡做完由执行方交回。V2 设计（第 6、18、19 节）定了：先由云端的 Agent 按标准验，本人看结果、可以推翻；长期存在、会成长的是岗位，每次干活按岗位临时起执行实例。

> 2026-11-06 更新（设计第 21 节）：验收（和拆卡）改在本人电脑上做。交回以后本机起验收员会话，取验收交代、经同步条目 `verdict` 报结论，云端照下面第 3、4 条落下（同一个 `settleHandback`），并记下是本机验的、哪个模型、验收员岗位哪一版。第 1 条的云端队列和第 6 条的模型只在 `BOARD_CLOUD_AGENTS=1` 时用，缺省关。第 2–5 条不变。见 [RFC 第 13 节](../technical/execution-board/RFC.md)。

## 决策

1. **交回进云端队列，Agent 验收。** 本机报来的 `handback` 记一行 `card_handbacks`（完成标准取那一刻的快照，产出是本机点名的那几份），排进验收队列（`cardAcceptance.ts`）。卡已完成、或执行方是本人自己的，只记不验。
2. **验收看三样口径。** 这张卡的约定（V1 合进来以前为空）、卡所属岗位的验收口径、验收员岗位的口径（本人没有验收员岗位时用预设的）。材料是产出的文字、链接的正文（飞书文档读不到时如实写读不到）、最多 8 张图。
3. **结果直接改卡。** 都达到 → 卡完成、进「准备中」、事项群记一句；有没达到的 → 「验收未过」，退回执行方的话是固定格式；同一张卡连续两次没过 → 「受阻」，等本人。只看最新一次交回：旧的一次验完不改新交回的卡。
4. **本人可推翻。** 推翻「通过」→ 卡回进行中，准备中那行撤掉，推翻的原因作为退回的话等着送回执行方（已进了某一版交付物的不能推翻）；推翻「没过」→ 卡完成，验收记录写本人。推翻和第二次没过，各提一条岗位修改（`role_proposals`），由轻模型写成待本人确认的一条；本人采纳才写回岗位、版本 +1，岗位后来改过的不能采纳。
5. **作业和接口、数据分开写。** 拆卡、验收、提岗位修改各有一个「作业」文件（`cardPlanAgent.ts`、`cardAcceptanceAgent.ts`、`roleProposalAgent.ts`：提示词、输入、输出格式和校验），队列、读写库、改卡在另一个文件（`cardPlanner.ts`、`cardAcceptance.ts`、`roleProposals.ts`）。以后换执行方式（比如改由新 Chat 服务或本机来跑）只换作业那一层。
6. **模型。** 拆卡和验收用 `REVIEW_*`（没配时用 `PI_*` 的 heavy 模型）；提岗位修改用 light 模型、不开思考。测试里三样作业一律打桩。

## 后果

- 本人不用每张卡都自己验，但 Agent 的结论可以被推翻；推翻和反复没过会变成岗位的修改建议，岗位越用越准。
- 验收在云端跑、要读产出全文，所以本机交出的文件要传到云端（只收 Markdown、纯文本、HTML、PDF、Word、PNG、JPG）。
- 退回的话经网页送回本机（本机只上报、不从云端取指令）；页面关着时卡停在「验收未过」，下次打开再送。
- 队列是进程内的：认领带 run_token，10 分钟没动的重新排，单次 5 分钟超时，重启后接着验。多实例部署前要换成真正的队列。
