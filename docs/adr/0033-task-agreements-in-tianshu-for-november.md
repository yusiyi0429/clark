# 11 月的约定存在天枢，12 月改读本体；Task 的读权限放宽到认可人

2026-11-06 决定。适用于约定与对表 V1（`apps/api`、`packages/contracts`）。详细做法见 [RFC](../technical/agreement-check/RFC.md)。

## 背景

V1 的核心是「约定与对表」：本体 Task 的每条验收标准写清用什么证明、谁来认，再加这次不包括什么；DRI 对表只得到两种回答。

本体里现在没有这几项。12 月起，它们随 Mission 确认一起定，写进本体 Task 的 definition 块：
- 每条标准加 `proof`、`acceptor`；
- Task 加 `exclusions`。

字段怎么加由斯一定，在哪个界面填由溪南定。11 月的 Mission 已经确认过了，不回头重走确认。

另外，「请 X 看」要让认可人 X 真能看到证据。原来交付物只认「本人 Mission 下的 Task」：负责人不是 Mission 负责人时，负责人自己都打不开。

## 决定

**约定从哪来**
- 11 月由负责人或 Mission 负责人在 Task 面板上补，存在天枢的 `task_agreement_notes`（迁移 225）。
- 补充不是另一道认可，没有认可状态。每存一次在 `task_agreement_note_revisions` 留一份整份的修改记录。
- 读的顺序：本体里有就用本体的；没有就用天枢补的；两样都没有，就只有标准原文。
- 本体 Task 的 definition 块里只要出现一项 `proof`、`acceptor` 或 `exclusions`，整个 Task 就以本体为准：天枢补充不再读，也不能在天枢里改（409 `AGREEMENT_FROM_WORLD`）。不按字段把两边拼在一起。
- 读取先按几种可能的形状兼容（见 RFC 第 4 节），测试用假数据。斯一定下字段以后，只改 `planTasks.worldAgreementOf` 和测试数据。
- 天枢补充记下当时标准文字的摘要 `basis_hash`。本体里的标准改了，约定和对表都提示「标准改过」，补充按原文、包含关系、序号对回现在的标准。

**评审按约定判**
- 传版本时把约定快照存进 `deliverable_versions.agreement`，参考评审只看快照，之后改约定不影响已经传的版本。

**谁能看、谁能改**

| 谁 | 读约定、对表、交付物 | 改约定 | 传版本、交付 | 请 X 看 |
|-|-|-|-|-|
| 负责人（本体没登记时是 Mission 负责人） | ✓ | ✓ | ✓ | ✓ |
| Mission 负责人 | ✓ | ✓ | 只在他就是负责人时 | 同左 |
| 战场负责人、CEO、约定里的认可人 | ✓（只读） | — | — | — |
| 其他人 | 当作不存在（404） | — | — | — |

- CEO 按人员目录认，不看当前切在哪个视角。
- 交付物的写接口仍要求成员工作台视角。

## 代价

- 12 月切到本体以后，11 月存在天枢的补充不会自动迁进本体。要迁，得按 Task 逐个写本体（另做，不在 V1）。
- 本体只填了一部分字段的 Task，会整份以本体为准，天枢补的那些看不到了。这是有意的：同一份约定只有一个来源。
- 要判「战场负责人」「认可人」，读别人 Mission 下的 Task 时得列整个公司当期的 Task。第一次读本体可能慢（最多等 8 秒），超时会当找不到。
- 认可人能看到这个 Task 的全部交付物，不只是他认的那一条。
