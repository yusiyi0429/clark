# 本体接入：把认知状态接进三条链路

2026-08-31 勘察 + 计划。勘察结论见本文 §1，改动清单见 §2，验收见 §3。

## 1. 三个事实

**① 装配那一层把结构压成了字符串。**

`ContextBundle`（`graphknowledge/recipes.ts`）装内容的字段只有两个：

```ts
renderedMarkdown: string    // 拼好的一整段
memberIds: string[]         // 这次摸到的实体编号
```

而客户端返回的东西是**有结构的**：`GkEntity.{properties, relations, versions}`、
`GkVersion.status`、`GkDynamic.seeds[].score`。`renderVersions()` 把 `v.status`
拼成 `v2[confirmed] 2026-07-15` 一行字，`bundle()` 再 `finish(parts)` 拼成一个
string —— 到这里为止结构全部蒸发。

这不是本体的问题，是这扇门的**消费者假设**：它最早只服务 A1a，而 A1a 要的恰好就是
「一段能塞进 prompt 的上下文 + 一个 `memberIds` 白名单」。深研不是这种消费者 ——
它要拿认知状态做判断（候选事实必须落 `[P]`，缺口该变成命题，已确认的判断该当前提）。

**要紧的一句：这一层不改，接上本体那份 `/v1/context-packs:resolve` 也拿不到那五类**
（`current_facts` / `candidate_context` / `context_gaps` / `provenance_context` /
`omissions`）—— 它们会在同一行 `finish(parts)` 上被压平，而且压平之后没有一处会报错。

**② 公司已知的事不参与选题。**

「选题」指这一轮决定去查什么，落在 N2（`plan.ts`）的产物：一批可证伪命题 + 每条的
检索式。它决定 N3 发什么查询、什么能入账，最后决定报告能说什么。

三个 builder 的入参排开：

| 节点 | 看得见什么 | 出处 |
|---|---|---|
| N0 锚定主体 | `title` / `scope` / `preTake` | `anchor.ts:134` |
| N1 先验草稿 | `title` + 主体卡 + 八维框架 | `draft.ts:219` |
| N2 抽命题 | **只有草稿** | `plan.ts:213` |

`companyContext` 第一次出现是 N5（`pipeline.ts:852`）。**在版判断和内部文档也一样**
—— 它们在 `A4Input` 里躺着，前四步一个都不收。

所以：本体里记着某条判断的重开条件是「某价格跌破 X」，这一轮深研不会因此去查那个价格。

这一半是设计（N1 凭知识写、不被检索带偏，理由见 `plan.ts` 文件头写的上一版死因），
一半是欠账 —— **前提不是检索结果**，喂已确认判断不违反那条设计。

**③ 白名单只有 A1a 在用。**

`memberIds` 是今天唯一穿过那道边界的结构化数据。`checks.ts:57` 的 `citedOk` 拿它判
模型有没有编内部编号，但只有 `a1aTriage` / `a1aNew` / `a1aUpdate` 接了。A3 预研和
A4 深研都没接 —— 报告里引错内部编号，今天没有任何一处会拦。

（`recipes.ts:26` 那行注释写「A3 的引用 ID 真实自检拿它当白名单」，是过期的。）

## 2. 改动清单

### 第一批 · 不依赖本体，现在就能做完并验证

| # | 改什么 | 为什么现在能做 |
|---|---|---|
| **B1** | 在版判断（带 `standing`）进 N1 先验草稿，按认知状态分三栏：已确认的当前提、动摇/未验证的当「公司自己也没把握，正是该查的」、已放弃的当「别再推荐」 | `A4Input.judgments` 已经有 `standing`，数据来自 clark 自己的库，不等本体 |
| **D0** | 修 `recipes.ts:26` 的过期注释 | 一行 |

B1 是这一批里唯一改变产出的一条：它让「公司已经押了哪些注、哪些正在动摇」参与
**选题**，而不是只在写报告时出现。

**原来列在这一批的 C1（`memberIds` 逐条进装配清单）撤掉了。** 勘察下来它不是缺口：
`openContext` 收尾那条 trace 已经带着 `bundle.calls`，每次 P1/P2 的
`path: /api/v1/entities/<code>` 就是那一轮摸过的每一个编号，复现和审计都够用。而把几十行
不可点击的图谱编号塞进用户看的装配清单，是把界面变差去换一份 trace 里已经有的东西。

## 3. 验收

第一批：

- B1 —— `buildDraftUser` 在给了在版判断时，输出里分得出「已确认」和「动摇/未验证」
  两栏；一条都没给时不多出空段落。`DRAFT_SYSTEM` 里说清两栏各自怎么用。
- C1 —— 装配清单里能逐条看到本体对象编号。
- 全量 `npm run test` + `tsc` + `eslint` 全绿。

**篇幅纪律**：N1 的输出额度 `DRAFT_MAX_TOKENS = 8000` 是**含思考**的。加长输入会把
正文挤没，而失败方式是静默的（同 2026-08-31 在 N2 上真发生过的那次：思考吃掉九成额度
→ 命题归零 → N3 整段被跳过，而这一轮照旧报 ok）。所以前提那一段**必须封顶**。
