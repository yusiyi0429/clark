# 信号自动抓取怎么从实验台走到线上

`2026-08-19-catching-signal-strategy-v0.1.md`（预装的靶点策略，待业务审阅）、

## 1. 这份 spec 定的是什么

不重复 catching 频道的设计——那份已经写完了。这份定的是**它怎么从方法负责人的
实验台变成 CEO 每天真的能看到的东西**，也就是两个仓库之间的分工、切口、顺序，
以及「什么时候算调完可以上线」。

原始设想是「先上 tkos-lab，测试调参后再推向 clark-main」。这个流程是对的，
而且是走过五次的路：clark-main 的 `src/lib/agent/a1a/run.ts` 头一句注释就是
「对齐自 `tkos-lab/src/tkos_lab/agents/a1a_signal.py`」，A1a / A3 / A4 / A6 / A10
全是这么来的。理由不是习惯——**调参需要的器具只在实验台有**：Prompt 库版本化与
星标、Run 台账、证据缓存与回放、离线 mock。catching 的两个自变量（选源、
阈值与 rubric）全靠这套器具才能归因，尤其 `replay_of` 那条：没有证据缓存就没法
「固定证据只改研判」。在 clark-main 里调，等于先把这套器具搬进产品仓库，
而它们对 CEO 一点用没有。

真正要迁移的三样东西是纯数据，零移植成本：靶点策略正文、spec 里那几个数、
沉淀下来的 `pinned_sources` 与选定的 `search_provider`。

## 2. 三个决定

| # | 决定 | 后果 |
|---|---|---|
| 1 | 抓取管道（RSS 解析 / 正文抽取 / 去重 / 时间窗）**只实现一次**，在实验台的 Python 里，做成可单独部署的作业 | 抓取不写两遍；实验台与线上跑的是同一套归一化文本，所以调好的 `threshold` 到线上等价 |
| 2 | 作业**五步全包**（plan / fetch / screen / triage / report），交付「过线信号」 | 方法迭代永远只在实验台一处发生：策略正文改一版，线上立刻跟着改，零移植 |
| 3 | 上线判据是**连续两轮扫描不再改策略**，不等 precision 统计 | 调参与上线并行，不用等一个完美的收敛点 |

### 与 2026-08-18 那份 spec 的关系

`2026-08-18-harness-sync-design.md` 的 §4 明确否掉了「抽共享 Python 服务部署
两次」，理由是「正式版现在是单个 Next.js 容器，为此多一个 Python 运行时和一套
部署，对 MVP 是纯负债」。这里的决定 1 与它相反，**不是反悔，是 catching 不满足
那条理由成立的两个前提**：

1. **A1a / A3 / A4 每一段都吃公司上下文、都要写回 store、都在用户点下去的请求
   周期里跑**，所以翻成 TS 放进同一个容器是对的。catching 恰恰相反：
   `context_mode` 恒为 `external_only`，**不接 GraphKnowledge**（那份 spec 的
   「定位」一节讲了为什么：给单条信号装公司上下文是 A1a 的活），不写回图谱，
   而且它天然是后台定时作业——CEO 晨报要求每天有货，不是有人点一下才有。
   它是整条链路里唯一可以整体外置的一段。
2. **前五次移植的都是纯 Prompt 加模型**：文本进、JSON 出，成本几乎全在把 Python
   翻成 TS。catching 多了一层抓取管道，它不含任何方法判断，翻译它没有任何方法
   收益，只有两处代码各自维护的成本；而且抽正文的库换一套（`trafilatura` →
   `readability`），同一篇文章归一化出来的 `text` 就变了，研判读的就是这段文本，
   1–5 分的分布跟着漂，实验台调出来的 `threshold` 到线上静默失真。

§4 否掉的另一条——「正式版转发实验台 API」——**这里同样不做**。作业是从实验台
代码构建出来的**独立部署单元**，不共享实验台的进程、口令门和实验记录库；生产
流量不会压到方法部门那台服务上，两边绑的是代码库，不是运行实例。绑代码库这件事
本身有成本，撤退路线见 §8。

## 3. 切口：一个作业，两个入口

五步只实现一次，被两个入口驱动，跑的是同一个 `CatchingSignalHarness`，不分岔：

| 入口 | 谁用 | spec 从哪来 |
|---|---|---|
| 实验台 `POST /api/runs` | 方法负责人调参 | 前端 spec 表单 |
| 作业 `python scripts/catch.py --from-run <run_id>` | 线上每日供给 | 复用那次实验的 `run.config["spec"]`，`replay_of` 强制置空 |

`--from-run` 是「把调好的参数上线」的唯一手段：**上线参数就是一个 run id**，
不建配置文件、不建管理界面，因此天然可追溯。作业自己也落一条 Run
（`config` 里记 `from_run`），线上每天跑的东西和实验记录在同一个台账里。

跨仓库只有一个契约：过线信号的形状。方向是**作业推给 clark-main**，不是前端去
拉实验台——定时在作业这边，前端不必知道实验台存在，也不必为机器再开一条穿过
口令门的鉴权路。

## 4. tkos-lab 那份 spec 要改三处

`2026-08-19-catching-signal-design.md` 的全部设计都还成立，但有三处按上面的决定
要修。下面是可直接应用的原文。**这是另一个仓库，改不改、什么时候改由方法侧定。**

### 4.1 「明确不做」里那条定时调度

原文：

> - 不做定时调度。整个系统是「人点开始才跑」，catching 不例外；Vercel Cron
>   或外部触发是频道被验证有用之后的事。

换成：

> - **频道不做定时调度。** 实验台仍是「人点开始才跑」，catching 不例外。定时
>   属于另一个入口——作业入口（见第十二节），它跑的是同一个 harness，但不在
>   实验台的请求周期里。别照着这一条把作业入口删掉。

### 4.2 第四节 `sources/` 的定位升格

在「新依赖」那一段之后补：

> **`sources/` 是产品线上唯一的抓取实现**，不只是实验台的内部模块。所以那条
> 降级退路（trafilatura 包体超限退 `readability-lxml`）一旦用上，要在 README 和
> `sources/` 的模块注释里写明当前在跑哪一种：归一化条目的 `text` 是研判读的
> 东西，抽正文的库换了，1–5 分的分布会跟着漂，`threshold = 3.5` 这条线随之
> 失真——而且是静默失真，从产出上看不出来。

### 4.3 新增第十二节「作业入口与推送契约」

> ## 十二、作业入口与推送契约
>
> 同一个 `CatchingSignalHarness` 由两个入口驱动（见 clark-main 那份
> `2026-08-19-catching-signal-rollout-design.md`）：实验台的 `POST /api/runs`，
> 和 `python scripts/catch.py --from-run <run_id>`。后者复用那次实验的 spec、
> 强制把 `replay_of` 置空，跑完把过线信号 POST 给 clark-main 的收件端点，
> 带 `OPERATOR_TOKEN`。
>
> 契约是 `signals` 元素的形状加三个字段：
>
> ```json
> {"run_id": "…", "scanned_at": "2026-08-19T07:00:00Z",
>  "signals": [{"dedupe_key": "…",
>               "title": "…", "url": "…", "text": "…", "published_at": "…",
>               "source": "…", "origin": "pinned",
>               "score": 4.2, "dimensions": {…}, "kiq": "KIQ2.2",
>               "why": "…", "suggested_issue": "…"}]}
> ```
>
> `dedupe_key` = 归一化后的 URL（去 utm 与 fragment，与 `step_screen` 去重用的
> 同一个函数），收件方按它幂等落库。**没有它这条链路必然堆重复**：
> `time_window_hours = 72` 而扫描每 2–3 天一轮，窗口本来就是重叠的。
>
> 推送失败**不**影响这次 run 的 `ok`——信号已经产出并落库，投递是另一件事。
> 作业退出码非零、错误记进 trace，重跑一次即可（幂等键保证重跑安全）。

## 5. clark-main 侧：很薄的一层

- **收件端点** `POST /api/signals/inbox`，受 `OPERATOR_TOKEN` 保护（这个变量已经在
  `docker-compose.yml` 里），按 `dedupe_key` 幂等落库：已存在的键更新
  `score` 与 `why`，不新增一条。
- **数据层**加「待挑的信号」这个对象：`src/lib/data/types.ts` + `store.ts` +
  `persist.ts`。`TKOS_SEED_FROZEN` 那套约束照旧（见 `docs/03_MVP上线与运维须知.md`）。
- **一个列表页**：分数、标题外链、来源与时间、`why`、建议议题方向，三键处置。
  **「开成议题」就是拿这条原文调现有的 A1a**（`src/lib/agent/a1a/run.ts`），
  一行新的判断逻辑都不用写。
- **处置动作记下来**。它是阈值的免费标注——CEO 挑了哪几条、放下哪几条，就是
  precision 的原始数据。v1 只记不读，v2 的人工标注直接读它。

不改 A1a，不改提请台。`prompts/cognitive/` 里**不放** catching 的认知段——策略
正文只在实验台一处，这是整段外置换来的最大好处，别为了「看起来和别的频道一致」
抄一份过来；抄了之后改一处漏一处，漏的那一份照样跑、照样出格式正确的信号，
只是它按上一版标准在判断，结果页上看不出任何区别（同 `prompts/cognitive/README.md`
里「引，不要抄」那条的道理）。

## 6. 顺序：一条阻塞项，四条轨

**唯一的阻塞项是靶点策略 v0.1 的业务审阅**（CEO 与方法负责人）。它只阻塞两件事：
装成 `prompts/cognitive/catching.triage.md` 的默认稿、决定作业上线用哪一版。
**不阻塞任何代码。**

**轨 1｜实验台实现（现在开工）** —— 顺序有讲究：

1. `cache.key_for` 并入 provider 名 + `test_evidence_cache_key_includes_provider`。
   **先修它**：后面每个实验都踩在它上面，不修则「同 case 同 queries 不同 provider」
   命中同一条缓存，对照实验静默失效。
2. `BochaSearch` / `DoubaoSearch` + `provider(name=...)` 那个可选参数。
3. `sources/`：rss + url + 归一化条目 + 单源失败不拖垮整个 run。
4. `CatchingSignalHarness` 五步 + `checks.catching` + `DEFAULT_SPEC`。
5. **回放（`replay_of`）**。必须在第一批实验之前落地——它是「只改研判」的唯一
   手段，缺了它实验 ② 做不了。
6. 侧边栏分组 + spec 表单 + 结果呈现（漏斗带 / 过线卡 / `below_threshold`）。
7. 作业入口 `--from-run` + 推送函数（推送目标先留空跑通，收件端点还没有）。

1–5 决定实验能不能归因，6 决定能不能看，7 决定能不能上线。要抢时间，6 可以与
3–5 并行，7 一定排最后。

**轨 2｜策略审阅（并行，等人）** —— 审完那一版存进 Prompt 库并加星标，作业上线
用的就是加星那条。审阅期间轨 3 用 v0.1 原文当草稿跑：**跑出来的数据本身就是
审阅材料**——「按这份策略扫回来的东西长这样」比空着评十七条 KIQ 容易得多。

**轨 3｜第一批两个实验（轨 1 的 1–5 完成后）** —— 顺序不能反：

- **实验 ①** bocha 对 doubao：同 pinned、同策略、同主题，只换 `search_provider`。
  比每源产出率与过线集合。必须先做，它决定后面所有实验站在哪份证据上。
- **实验 ②** `replay_of` 固定实验 ① 的证据批次，只动 `threshold` 与 rubric。
  `below_threshold` 里「差一点」的那几条是判据。

**轨 4｜clark-main 那薄一层 + 打开开关**（判据达成后）。§5 那四件事。

## 7. 判据怎么落地

判据是「连续两轮扫描，方法负责人看完不想再改策略」。要让它可执行，补两件小事，
都不新建机制：

- 每轮扫描之后在那条 run 上留一句话：**这轮改了什么、或者没改**。连续两条
  「没改」就是达成。星标与 Run 台账已经在了，缺的只有这一句。
- 达成时把那条 run 的 id 与加星的策略版本写进 CHANGELOG 的 v0.15.0 那条。
  作业上线的 `--from-run` 就是它；以后追「线上跑的是哪套参数」只看这一行。

判据能这么松，是因为决定 2 把上线成本压到了接近零：**「推向 clark-main」剩下的
只是让产品开始消费作业的产出**，不是第六次移植。前提是产品侧给的是「待挑的
信号」而不是直接进提请台——差一点的信号展示出来不伤人，CEO 没挑的那几条本身
就是对阈值最好的标注。

## 8. 风险与撤退路线

| 风险 | 现在怎么处理 | 撤退条件 |
|---|---|---|
| 作业与实验台同一个代码库，实验台改坏 `sources/` 会影响 CEO 每日供给 | **作业按 tag 部署，不跟实验台主干走。** 升级是一个显式动作 | — |
| 抽正文降级（`trafilatura` → `readability-lxml`）让 `threshold` 失真 | §4.2 要求写明在跑哪一种；换实现后用 `replay_of` 重跑一轮校准 | — |
| 多一个 Python 部署单元的运维成本 | 本体 API、GraphKnowledge 已经是独立服务，不算开先例 | 运维成本被证明高于翻译成本，则回到「clark-main 用 TS 重写抓取层」 |
| catching 以后需要公司上下文 | 现在不需要（`external_only`，见那份 spec 的「定位」） | 一旦研判要接图谱，整段外置的前提就不成立，按 2026-08-18 §4 的老路翻成 TS |

## 9. 明确不做

在 catching 那份 spec 的「明确不做」之外，新增三条：

- **不为作业建配置文件或管理界面。** 上线参数就是一个 run id。
- **不做 clark-main → tkos-lab 的反向查询**（点开一条信号去看它的 trace）。
  trace 是给方法负责人的，去实验台看。
- **不在 clark-main 侧再加一层准入过滤。** 两处标准会打架；而且线上一装过滤器，
  实验台调出来的阈值就不再是最终阈值——这次调参就白做了。
