# DRI 第一版交互演示

入口：`http://localhost:3000/dri-demo`，沿用已有访问控制。它是独立页面，不替换 `/dri`，也不修改 CEO Agent、数据层和模型配置。

## 演示目标

让 DRI 明确自己的约定结果，能在外部工具开展工作，并把成果带回来，形成可回应、可协同、可验收的交接。视觉沿用全站 paper / surface / ink / judgment / confirmed 语义色、天枢品牌和系统字体。桌面采用主工作区与背景侧栏，窄屏采用单列。

## 建议体验顺序

1. 我的工作 → 查看并回应 → 先澄清或提出调整。
2. 发出问题 → 演示收到委托人回应 → 按约定承接。
3. 准备外部工作材料 → 复制；带回成果 → 载入示例成果 → 审阅并保存。
4. 发起协同请求 → 查看发送范围 → 模拟收到销售负责人回应。
5. 审阅并提交 → 模拟要求补充 → 修改成果 → 再次提交 → 模拟接受。
6. 展开工作记录与提交版本，查看 v1 / v2 原文；查看本月承诺，提交调整提案，确认生效约定仍为 v1。

## 已实现与演示边界

- 真正可操作：页面切换、承接/澄清、原文与判断编辑、工作包复制、读取 1 MB 内 TXT/MD、协同请求、版本快照、提交/退回/接受、承诺调整提案、原文和记录展开、重置。
- 全部任务、人物、日期和回应为示例。刷新重置，不写浏览器持久存储或真实 store，不向他人发送消息。
- 不调用模型。示例成果附带预设判断；导入用户自己的材料时要求用户填写判断，不假装已经执行提取或事实核验。暂不支持 PDF/Word/链接解析、语音、自由对话、自动规划或深研。
- 提供者不等于事实原始出处，更不等于已核验。当前展示“原始事实尚未核验”。真实接入需要保留到段落/页码的证据指针。
- 明确区分：收到委托、承接、保存草稿、提交、验收。任务验收不自动改变 Outcome，不自动待上会，不写本体。
- 承诺调整保留为提案，不自动改变既有范围或日期。
- 模拟验收和模拟协作者回应只是演示控件。正式产品必须分别由有权限的真实身份操作。

正式接入顺序：先确定任务/承诺/交付的独立对象及权限，再替换演示状态操作；随后接入上传与来源提取、协同收件箱及验收回应。最后接共享研究能力。不要把演示 reducer 当成生产鉴权或业务工作流。

视觉组件可以复用，但建议真实接入时按首页、任务页、承诺页及弹窗拆分组件。本次保持所有演示改动在新增文件中，便于与正在进行的 CEO Agent 工作独立审阅。
