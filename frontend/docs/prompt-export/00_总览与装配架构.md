## 一、先看清一件事：这里有两套 Prompt 机制，不是一套

同一个仓库里并存两种写法。**不是历史遗留没清理，是两类 Prompt 的改动频率不一样。**

### 机制 A：五段装配（`prompts/` 目录下的 md 文件）

Prompt 拆成两个文件、五个段落，运行时拼起来。对齐自实验台的
`tkos-lab/src/tkos_lab/prompt/assembler.py`，装配器在 `src/lib/agent/prompts.ts`。

五段的顺序是固定的：

| 段 | 名字 | 内容从哪来 |
| --- | --- | --- |
| ① | 输入契约 | `prompts/engineering/<key>.md` 里的 `{{INPUT}}` 位置 |
| ② | 上下文注入 | `{{CONTEXT}}` ← `Harness.contextBlock`（见下面第三节） |
| ③ | **认知指令** | `{{COGNITIVE}}` ← `prompts/cognitive/<key>.md`（方法部门维护） |
| ④ | 输出格式 | `prompts/engineering/<key>.md` |
| ⑤ | 硬约束 | `prompts/engineering/<key>.md` |

**顺序不能改。** ④⑤ 必须是模型最后读到的东西 —— 认知段（③）里那套文本块式的 Output Contract 一旦排在
输出格式后面，就会把这边的 JSON 形状压掉。

**用这套机制的只有 A1a 一条链路的四个 key**：`a1a.triage`、`a1a.issue.new`、`a1a.issue.update`、
`a1a.issue.external`。

分成 engineering / cognitive 两个目录的理由是**谁改**：工程段（形状、字段名、JSON schema）跟着代码走，
认知段（该怎么想、什么算好、什么是常见错）由方法部门改，改它不需要动代码，也不该动代码。

### 机制 B：代码里的 system + builder（`src/lib/agent/<agent>/prompt.ts`）

A3、A4、A5、A2、A6、A10 以及给材料起标题的那一次调用，system prompt 是 TS 里的模板字符串常量，
user 消息由一个 `buildXxxUser()` 函数按当次材料拼出来。

**为什么没有一起搬成 md**：这几条链路的 user 段不是「填四个洞」，而是有条件分支的组装 ——
有没有递上来的原文、有几份文档只有标题没有正文、有没有既有判断要列。这类逻辑写在 md 里没有落点。

**但认知段仍然走同一个入口。** A3 和 A4 的认知段也放在 `prompts/cognitive/` 下
（`a3.pre-research.md`、`a4.research.md`），由同一个 `cognitiveFor()` 读出来，作为 user 消息里的
一个小节注入（A3 是 `## 预研该怎么做`，A4 是 `## 深度研究该怎么做`）。所以方法部门改认知标准的入口
是统一的，不管这条链路用的是机制 A 还是机制 B。

**故意没有认知段的**：A5（判断生成）、A2、A6、A10、起标题。A5 那一条写在
`src/lib/agent/a5/prompt.ts` 的文件头上 —— 不要为了「补齐」给它建一个认知段文件。

## 二、技能是「引」进来的，不是抄进来的

认知段（`prompts/cognitive/*.md`）的写法是：第一行一个技能引用标记，然后 `---`，然后是这一次的落法。

```markdown
{{SKILL:m1a-s01-issue-framing}}

---

## 这一次怎么落
…
```

`{{SKILL:<name>}}` 在装配时被替换成 `prompts/cognitive/skills/<name>.md` 的全文（去掉 frontmatter）。

**「引，不要抄」是一条硬规矩。** 光 S01 一份技能就服务四个 prompt key；抄进去之后技能改版，
四份副本里改哪几份、漏哪几份，从产出上看不出来 —— 那是静默的版本漂移。

三份技能原文一并导出在 `skills/` 目录下：

- `m1a-s01-issue-framing.md` —— 信号 → 议题（服务 A1a 的四个 key）
- `m1a-s02-pre-research.md` —— 预研（服务 A3）
- `m1a-s03-strategic-deep-research.md` —— 战略深度研究（服务 A4）

技能是方法部门的资产，status 是 Calibration Draft。**落法段可以压掉技能里的任何一段** ——
这是设计，不是漏洞，但代价记录在案：曾经一句「这一次的交付不是那份 Word 报告」，静默地把 S03 §6
整节关掉了。所以落法段里凡是要覆盖技能的地方，都必须明写「技能里的 §X 这一次不适用」，不能靠读者推断。

治理规则的全文在 `prompts/cognitive/README.md`，原样附在本文件末尾。

## 三、公司上下文有三档，不是两档

每一次运行的第一步都是 `Harness.openContext(recipe, q)` —— 去 GraphKnowledge 里选锚点、装上下文。
结果分三档，第 ② 段填的东西由 `Harness.contextBlock` 决定：

| 档 | 什么情况 | 第 ② 段填什么 | 引用约束 |
| --- | --- | --- | --- |
| 锚定 | 图里命中了这条输入对应的锚点 | `bundle.renderedMarkdown`（装好的公司上下文正文） | 可以引 member id |
| **只有公司经营状态** | 锚点没命中，但取到了那 4000 字的公司整体状态（P0） | `wrapCompanyStateOnly(p0)` | `cited_member_ids` 必须是 `[]` |
| 纯外部 | 连 P0 都没有 | `NO_COMPANY_CONTEXT` | `cited_member_ids` 必须是 `[]` |

**中间那一档必须单独存在。** 说成完整上下文，模型会写「公司现有判断是……」；说成什么都没有，
就是手里有真材料却谎称没有。这三段说法的原文在 `src/lib/agent/prompts.ts` 里（附在末尾）。

后两档都把「引用必须为空」写成硬约束。留个空洞的话，模型会自己编一套公司战略假设出来然后正常引用它 ——
那种产出格式全对、引用看着也有，只是全是假的。

`Harness.contextBlock` 原文：

```ts
  /**
   * 【公司经营状态】那一段的原文，**只在纯外部这条路上有值**。锚定时它已经在
   * `bundle.renderedMarkdown` 里，见门那边 `staticContext` 的注释。
   *
   * 屏幕上那行溯源要靠它分档：有它写「只有公司经营状态」，没有才写「本次无公司上下文」。
   */
  get companyStateOnly(): string {
    return this.opened?.staticContext ?? "";
  }

  /**
   * 该往 Prompt 第 ② 段填的东西。装 prompt 一律用这个，不要直接用
   * `bundle.renderedMarkdown` —— 纯外部时那是 undefined，落进 prompt 是空洞。
   *
   * **三档，不是两档。** 中间那一档是「锚点没命中，但公司经营状态取到了」：那 4000
   * 字跟锚点无关，一次调用就能拿到，扔掉它等于让深研在零公司上下文下写报告。它有
   * 自己的说法（`wrapCompanyStateOnly`），不能复用另外两档任何一句 —— 说成完整上下文，
   * 模型会写「公司现有判断是……」；说成什么都没有，就是手里有真材料却谎称没有。
   */
  get contextBlock(): string {
    if (!this.externalOnly) return this.bundle?.renderedMarkdown ?? NO_COMPANY_CONTEXT;
    const p0 = this.companyStateOnly;
    return p0 ? wrapCompanyStateOnly(p0) : NO_COMPANY_CONTEXT;
  }
```

`openContext` 原文（注意 catch 里那条注释：图服务连不上必须就地失败，**不能吞掉异常当纯外部继续跑**）：

```ts
  /**
   * 选锚点 + 装上下文。返回**这次有没有公司上下文**。
   *
   * 三条链路的第一步都是这一句。三态在上半的 `openContext()` 里就分开了：
   * 命中 → 装配并冻结；`AnchorNotFound` → 那扇门自己吃掉，这里拿到
   * `mode:"external_only"`；`GraphKnowledgeUnavailable` → 原样抛出，就地失败。
   *
   * 这里的 catch **不改变控制流**：它落一条 `status:"failed"` 的 Run 记录，
   * 然后把记录挂在 `AgentRunFailed` 上原样抛出去（见那个类的注释）。真正危险的
   * 是把异常吞掉当纯外部继续跑 —— 那会让图服务一停机所有运行都自动降级，还照样
   * 产出一份格式完整的报告。**不要在这里加 `return` 或 `this.note` 之后往下走。**
   */
  async openContext(
    recipe: Recipe,
    q: string,
    /** `anchorCode` 复现旧运行；`judgmentCodes` 是这条议题挂着的判断号（只有 S02 认）。 */
    opts: { anchorCode?: string; judgmentCodes?: string[] } = {}
  ): Promise<boolean> {
    this.attemptedRecipe = recipe;
    let opened: OpenedContext;
    try {
      opened = await openGraphContext({
        recipe,
        prefix: PREFIX[this.agent],
        channel: this.agent,
        q,
        anchorCode: opts.anchorCode,
        judgmentCodes: opts.judgmentCodes,
        viewer: this.viewer,
        asOf: this.asOf,
      });
    } catch (e) {
      throw new AgentRunFailed(
        this.finish({ status: "failed", error: e instanceof Error ? e.message : String(e) }),
        e
      );
    }
    this.opened = opened;
    for (const n of opened.trace) this.trace.push({ ...n });
    if (opened.mode === "external_only") {
      // 有没有装上 P0 要记进 trace：两种情况下这条链路手上的材料不一样厚，事后
      // 比对两次运行的产出时，这一行是唯一看得出差别在哪的地方。
      this.note("转纯外部", {
        why: opened.noAnchorReason,
        companyStateChars: opened.staticContext.length,
        note: opened.staticContext
          ? "这不是故障。只有【公司经营状态】，没有这条议题的既有认识；引用必须为空"
          : "这不是故障。没有公司上下文，本次全程只用输入原文与外部材料；引用必须为空",
      });
    }
    return opened.mode === "anchored";
  }
```

## 四、装配之后发生什么：一次模型调用的记账

`Harness.callPrompt(key, parts)` 是机制 A 的调用口：装五段 → 调模型 → 判形状 → 记账。

```ts
  /**
   * 调一次模型，prompt 由 `prompts/engineering/<key>.md` 五段装配。
   *
   * 返回的是**对象**：下游（自检、路由、写卡）全都按对象取字段，光检查「能不能
   * parse」放它过去，就会在几帧之外炸成 `undefined is not an object` —— 堆栈指向
   * 自检代码，真正的原因（模型输出的形状不对）反而看不见。所以在边界上判形状。
   */
  async callPrompt(
    key: string,
    parts: { input?: string; context?: string; evidence?: string; challenges?: string },
    opts: { slot?: Slot; maxTokens?: number; temperature?: number } = {}
  ): Promise<Record<string, unknown>> {
    const p = await assemble(key, { ...parts, cognitive: this.cognitive[key] });
    const r = await this.callMessages(
      `模型调用 · ${key}`,
      [
        { role: "system", content: p.system },
        { role: "user", content: p.user },
      ],
      opts,
      { promptKey: key, cognitiveSource: p.cognitiveSource, promptChars: p.chars },
      key
    );
    /*
     * 取的是上面那句 `callMessages` **刚 push 进去的那个节点** —— 顺序耦合，靠的是
     * 「callMessages 的最后一句是 push」。中间不许再插 `note()`：插了之后
     * `shapeFixed` / `error` 会写到那条 note 上，而结果页只会显示一条没有报错的模型
     * 调用和一条挂着报错的本地记事，从屏幕上完全看不出是记错了地方。
     */
    const node = this.trace[this.trace.length - 1];
    let parsed: unknown;
    try {
      parsed = parseJson<unknown>(r.text);
    } catch (e) {
      node.error = `输出不是合法 JSON: ${e instanceof Error ? e.message : String(e)}`;
      throw e;
    }
    if (Array.isArray(parsed) && parsed.length === 1 && parsed[0] && typeof parsed[0] === "object") {
      // 单元素数组是同一个对象套了层壳，拆开就是要的东西。拆了要留痕：不然
      // 「这个模型需要更强的格式约束」这件事在结果页上无从得知。
      node.detail.shapeFixed = "模型把对象包在单元素数组里返回，已拆开";
      return parsed[0] as Record<string, unknown>;
    }
    if (!parsed || typeof parsed !== "object" || Array.isArray(parsed)) {
      const got = Array.isArray(parsed) ? `数组（${parsed.length} 个元素）` : typeof parsed;
      node.error = `输出不是 JSON 对象，是 ${got}`;
      throw new Error(node.error);
    }
    return parsed as Record<string, unknown>;
  }
```

机制 B 的链路自己拼 messages，走 `Harness.callMessages(label, messages, opts)`；A4 写报告那一层传
`json: false`（那一次要的是自由文本，不套 `json_object`）。

**每一次调用都进 trace，每一次 token 都累计。** 一次运行结束时 `finish()` 拼出一条 Run 记录，
台账上能回答这几件事：

- 用的是哪个 prompt key、认知段来自哪里（`cognitiveSource ∈ runtime | default | empty`）、prompt 有多少字
- 这次是哪一档上下文（`contextMode`）、哪个配方（`contextRecipe`）、锚点是谁、图快照是哪一个（`snapshotId`）
- 走的哪个槽位、实际发出去的模型 id、思考档位、每一步耗时与 token
- 质量门的自检结果（`checks` / `checkSummary`）、被挡下来的违规（`violations` / `firstRoundViolations`）

**失败要响。** prompt key 找不到抛 `PromptKeyError`，技能名找不到抛 `SkillNotFoundError` ——
都不许回落成空字符串。回落的后果是产出一份格式完整、认知段整段缺失的东西，而屏幕上看不出任何异常。

## 五、质量门和认知标准是两回事

Prompt 里说的是「该怎么想」；**可数的东西不写进祈使句，交给确定性校验器**。校验器在：

| 文件 | 管什么 |
| --- | --- |
| `src/lib/agent/rules.ts` | 通用规则，含 G-05 禁词（必然 / 一定会 / 毫无疑问 / 唯一的 / 完全不可能） |
| `src/lib/agent/a3/validate.ts` | 预研的字段、句数、溯源（A3-13：每条 Evidence 必须有溯源，p0） |
| `src/lib/agent/a4/validate.ts` | 深研四节的条数、溯源、禁词 |
| `src/lib/agent/a2/run.ts` → `validateQuestion` | A2-01…A2-05 |
| `src/lib/agent/a6/extract.ts` → `checkTurn` | A6X-01…A6X-03 |
| `src/lib/agent/a10/run.ts` → `validateClosure` | A10-01…A10-09 |

没过就打回重修，重修的提示词三条链路是同一句 —— **把违规原样递回去，不笼统地说「请改进」**：

```text
上一版没通过质量门。逐条改，其余不要动：

<逐条列出的违规>

只输出修正后的 JSON。
```

重修轮数写死在各链路（`MAX_REPAIR = 2`）。重修**不算下一步**：进度条上写成「写这一轮预研 · 第 2 遍」，
序号不动 —— 让它进序号会把分母搞坏（「共 4 步」跑出「第 5 步」）。

## 六、模型槽位与思考深度

槽位按角色配，不按厂商配（`src/lib/models/slots.ts`）：

| 槽位 | 别名 | 谁在用 |
| --- | --- | --- |
| `pro` | `deepseek-pro` | A1a、A3、A4（含反证那一遍）、A5、A2、A10 |
| `flash` | `deepseek-flash` | A6（每轮对话都跑，要快）、给材料起标题 |
| `alt` | `kimi-k3` | **这一版没有任何链路在用**。留着是为了「换一个不同家族的模型进来」不需要改调用方 |

`alt` 的不变量是「必须和 `pro` 不同家族」，理由不是要用不同厂商，是**自己判自己会通过自己的失败模式**。
2026-08-20 起 A4 的反证那一遍改回了 `pro`，所以交叉家族校验目前是没有的。

思考深度用官方 effort 词表，同一个旋钮同时决定研究规模（`src/lib/agent/harness.ts`）：

| 档 | searchK | maxProps | maxRounds |
| --- | --- | --- | --- |
| low | 3 | 3 | 1 |
| medium | 4 | 3 | 1 |
| high（默认） | 5 | 4 | 2 |
| xhigh | 6 | 5 | 2 |
| max | 8 | 6 | 3 |

火山那三个模型 `acceptsEffort` 都是 false，所以正式版里这个值只驱动上面这张表，从不发给模型

## 七、改 Prompt 的时候要知道的两件工程事实

1. **`prompts/**/*.md` 是磁盘读取 + 进程内缓存。** 改完要重启 dev server 才生效。
   部署时靠 `next.config.ts` 的 `outputFileTracingIncludes: ["./prompts/**/*.md"]` 把它们打进函数包 ——
   漏了这一行，本地全对、线上全部 `PromptKeyError`。
2. **填洞用的是函数形式的 replacer。** 公司上下文正文里可能出现 `$&`、`$1` 这类字符串，
   用字符串形式的 `replace` 会把它们当反向引用展开。

## 附录 A · 装配器全文（`src/lib/agent/prompts.ts`）

这一份要连注释一起读 —— 三段上下文说法的原文（`NO_COMPANY_CONTEXT`、`wrapCompanyStateOnly`）、
兜底串、key 的合法字符、frontmatter 怎么剥，都在里面。

```ts
/**
 * 五段 prompt 装配。对齐自 `tkos-lab/src/tkos_lab/prompt/assembler.py`。
 *
 * ① 输入契约 ② 上下文注入 ③ 认知指令 ④ 输出格式 ⑤ 硬约束。
 *
 * ①②④⑤ 在 `prompts/engineering/<key>.md` 里，是工程的事；③ 由运行时传进来，
 * 缺省回落到 `prompts/cognitive/<key>.md`，是方法部门的事。两边分开放，是为了
 * 让改 prompt 的人不用碰代码，也不会顺手把输出格式改坏 —— 输出格式一改，下游
 * 按字段取值的每一处都会静默拿到 undefined。
 *
 * 用 `.md` 文件而不是 TS 模板字符串：prompt 要能改完就生效、不用重新构建。
 * 代价是它不进 webpack 产物，所以 `next.config.ts` 里要显式追踪。
 */
import { readFile } from "node:fs/promises";
import path from "node:path";

const ENG = path.join(process.cwd(), "prompts", "engineering");
const COG = path.join(process.cwd(), "prompts", "cognitive");
/*
 * 方法部门给的技能文档原件放这里，一个文件一份技能。认知段文件用
 * `{{SKILL:<名字>}}` 引它，不抄它。
 *
 * 抄的代价是静默漂移：S01 一份技能同时管四个 prompt key，抄成四份之后，方法
 * 部门给 v0.5 时改三份漏一份 —— 漏的那一个 prompt 照样跑，照样出格式正确的
 * 议题，只是它按上一版的标准在判断，而结果页上看不出任何区别。
 */
const SKILLS = path.join(COG, "skills");

/**
 * 工程段模板不存在。
 *
 * **不回落到空模板。** 回落的话模型拿到的是一份没有输出格式约束的自由作文题，
 * 而它照样会返回一段 JSON —— 于是「prompt 根本没装上」这件事在结果页上完全
 * 看不出来，只表现为「这个 prompt 效果不好」。
 */
export class PromptKeyError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "PromptKeyError";
  }
}

/*
 * 图谱里没有对应锚点时，塞进 Prompt 第 ② 段（上下文注入）的东西。
 *
 * 这一段不能留空。留空的话模型面对的是一个「上下文位置有个空洞」的 Prompt，
 * 它会去填这个洞——凭常识编出几条听着像公司战略假设的东西，然后正常引用。
 * 那种产出最难发现：格式全对，引用看着也有，只是全是假的。所以这里明确写出
 * 「没有」，并且把「不许编」和「引用必须为空」写成硬约束。
 *
 * **住在这个文件里，是为了让 `FILL.context` 的兜底串就是它。**（原来在 harness.ts，
 * 兜底串是另写的一句「（本次未取到公司上下文）」—— 缺了那两条硬约束，而那两条正是
 * 这段话存在的理由。兜底是防线的最后一层，弱在那里等于没有。）
 */
export const NO_COMPANY_CONTEXT = `（本次没有公司上下文）

GraphKnowledge 里没有与这条输入对应的锚点，因此这次运行**拿不到任何公司内部
信息**：没有战略假设、没有判断链、没有共识记录，也没有任何可引用的 member。

这不代表这条输入与战略无关，而是说明它对公司现有的战略方向来说还太新——
图谱里还没有它的位置。所以你要做的是**纯外部推理**：

- 只依据上面那条输入本身，以及公开可查的通行事实来推理。
- 不要假设公司内部存在任何相关材料，不要写「公司现有战略假设是……」这类句子。
  没有材料就说没有材料，宁可结论更弱，也不许把推测写成公司现状。
- cited_member_ids 必须是空数组 \`[]\`。这次没有任何 member 可引，写进去的一定是
  编的。
`;

/**
 * 锚点没命中、但【公司经营状态】（P0）取到了 —— 塞进第 ② 段的就是这一段。
 *
 * 这是 `NO_COMPANY_CONTEXT` 和完整上下文之间那一档，**必须有自己的说法**。直接把
 * P0 当完整上下文塞进去，模型看到「公司经营状态」四个字就会认为图谱里有这条议题的
 * 既有认识，然后写出「公司现有判断是……」；而继续用 `NO_COMPANY_CONTEXT`，就是明明
 * 手里有 4000 字真实经营状态却告诉模型「什么都没有」。所以这一段说的是三件事：
 * 有什么、没有什么、以及引用照旧必须为空。
 *
 * 引用为空这一条不因为装了 P0 而放松：P0 那条路（`Builder.p0()`）**不产生任何
 * memberId**，连锚定的时候都不产生。所以正文里出现的任何编号都不是可引的 member，
 * 写进 `cited_member_ids` 的一定是编的 —— 跟没有上下文时是同一个结论。
 */
export const wrapCompanyStateOnly = (p0: string): string =>
  `（本次只有公司经营状态，没有这条议题的既有认识）

下面这一段是**公司当前的经营状态**，来自 GraphKnowledge，是真实的公司内部信息，
可以据此推理。但 GraphKnowledge 里没有与这条输入对应的锚点，所以**这条议题本身**
在图谱里没有位置：没有针对它的判断链、没有它的版本演进、没有相关的共识记录。

因此：

- 关于公司整体状况（本期要达成什么、哪些判断在版、当前处在什么阶段），依据下面
  这一段来写。
- 关于**这条输入**，做纯外部推理。不要写「公司现有判断是……」「公司已有研究表明……」
  这类句子 —— 图谱里没有这条议题的既有认识，那种句子一定是从经营状态里推想出来的。
  宁可结论更弱，也不许把推测写成公司现状。
- cited_member_ids 必须是空数组 \`[]\`。这一段不带任何可引用的 member，正文里出现的
  编号也不是 —— 写进去的一定是编的。

---

${p0}
`;

export const PROMPT_SYSTEM =
  "你是使用 GraphKnowledge 公司上下文的 TKOS 专用 Agent。" +
  "严格按给定的输出格式作答，只输出 JSON，不要任何解释性文字、不要 Markdown 代码围栏。" +
  "上下文里没有的事实一律不要写。";

/** runtime = 这次跑传进来的；default = 用了 `prompts/cognitive/<key>.md`；empty = 两者都没有。 */
export type CognitiveSource = "runtime" | "default" | "empty";

export type AssembledPrompt = {
  key: string;
  system: string;
  user: string;
  cognitiveUsed: string;
  cognitiveSource: CognitiveSource;
  chars: number;
};

// 读盘之后缓存。一次 A4 有十几次模型调用，每次都读盘等于十几次同步 IO，而
// prompt 在一次运行里是不变的。改了 md 重启 dev server 生效。
const cache = new Map<string, string | null>();

async function readOnce(file: string): Promise<string | null> {
  const hit = cache.get(file);
  if (hit !== undefined) return hit;
  let text: string | null = null;
  try {
    text = await readFile(file, "utf8");
  } catch {
    text = null;
  }
  cache.set(file, text);
  return text;
}

/*
 * key 会被拼进文件路径，所以先校字符。
 *
 * 今天不可达（`callPrompt` 的四个 key 全是字面量），但 `Harness.callPrompt(key: string)`
 * 是公开方法：哪天有人把外部传来的值接到这里，`../../` 就是任意文件读。校验放在这一层
 * 而不是调用方，是因为拼路径的动作发生在这里。
 */
const KEY_OK = /^[a-z0-9][a-z0-9.\-]*$/;

export async function engineeringFrame(key: string): Promise<string> {
  if (!KEY_OK.test(key)) {
    throw new PromptKeyError(`prompt key 不合法: ${JSON.stringify(key)}（只许小写字母、数字、. 和 -）`);
  }
  const text = await readOnce(path.join(ENG, `${key}.md`));
  if (text === null) {
    throw new PromptKeyError(`没有工程段模板: ${key}（找的是 prompts/engineering/${key}.md）`);
  }
  return text;
}

/*
 * 技能文档原件带 YAML frontmatter（name / version / owner / status）。那是登记
 * 信息，不是给模型看的，装进 prompt 只会多几十 token 并且让它以为要遵守
 * `status: Calibration Draft`。版本号在正文第一行的标题里，所以剥掉不丢溯源。
 */
function stripFrontmatter(md: string): string {
  return md.replace(/^---\r?\n[\s\S]*?\r?\n---\r?\n/, "").trimStart();
}

const SKILL_TOKEN = /\{\{SKILL:([^}]*)\}\}/g;

/**
 * 技能文档不存在 / 名字不合法。
 *
 * **不换成空串。** 换空串的话，那份 prompt 的第 ③ 段只剩下几行「这一次做哪一步」
 * 的引子，认知标准整段消失 —— 而模型照样会产出格式完整的结果。跟
 * `PromptKeyError` 同一个道理：装没装上，必须在跑起来的那一刻就炸。
 */
export class SkillNotFoundError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "SkillNotFoundError";
  }
}

/*
 * 导出只为了能直接测它。测不到的替代方案是在 `prompts/cognitive/` 里放一个引了
 * 不存在技能的夹具文件 —— 那个目录是方法部门在编辑的生产目录，往里塞测试用的
 * 坏文件，早晚有人把它当真实 prompt。
 */
export async function expandSkills(text: string): Promise<string> {
  const names = [...text.matchAll(SKILL_TOKEN)].map((m) => m[1].trim());
  let out = text;
  for (const name of names) {
    // 名字要拼进文件路径，跟 prompt key 同一条规矩（见下方 KEY_OK 那段注释）。
    if (!KEY_OK.test(name)) {
      throw new SkillNotFoundError(`技能名不合法: ${JSON.stringify(name)}（只许小写字母、数字、. 和 -）`);
    }
    const md = await readOnce(path.join(SKILLS, `${name}.md`));
    if (md === null) {
      throw new SkillNotFoundError(`没有这份技能文档: ${name}（找的是 prompts/cognitive/skills/${name}.md）`);
    }
    const body = stripFrontmatter(md);
    out = out.replace(new RegExp(`\\{\\{SKILL:\\s*${name}\\s*\\}\\}`, "g"), () => body);
  }
  return out;
}

export async function defaultCognitive(key: string): Promise<string> {
  const text = await readOnce(path.join(COG, `${key}.md`));
  return text === null ? "" : await expandSkills(text);
}

/**
 * 这次跑用哪一段认知指令：运行时传的优先，否则 `prompts/cognitive/<key>.md`。
 *
 * 独立导出，是因为 A3 预研没走五段装配（它的 user 段是手写的一整份，见
 * `a3/prompt.ts`），但认知段必须和 A1a 走同一条取值路径 —— 两条路径的话，
 * 「A3 的认知段到底装上了没有」得单独查一遍。
 */
export async function cognitiveFor(
  key: string,
  runtime?: string
): Promise<{ text: string; source: CognitiveSource }> {
  if (!KEY_OK.test(key)) {
    throw new PromptKeyError(`prompt key 不合法: ${JSON.stringify(key)}（只许小写字母、数字、. 和 -）`);
  }
  const rt = (runtime ?? "").trim();
  if (rt) return { text: rt, source: "runtime" };
  const fallback = (await defaultCognitive(key)).trim();
  return { text: fallback, source: fallback ? "default" : "empty" };
}

const FILL = {
  input: "（无）",
  // 兜底就是那段带硬约束的话本身。今天四处调用都传了 context，所以走不到这里 ——
  // 但走到这里的那天，「不许编」「引用必须为空」两条必须还在。
  context: NO_COMPANY_CONTEXT,
  evidence: "（本次无外部材料）",
  challenges: "（本次无红队挑战）",
  cognitive: "（本条 Prompt 的认知指令段尚未提供）",
} as const;

/*
 * 替换一律用**函数形式**的 replacer。
 *
 * `String.replace(re, str)` 会把替换串里的 `$&` / `$'` / `$1` 当成引用展开 ——
 * 图谱正文里真出现一次 `$&`，那一处就会被换回 `{{CONTEXT}}` 这五个字符，
 * 而 prompt 看起来只是「有一处怪字符」，没人会往替换语义上想。
 */
function fill(frame: string, token: string, value: string): string {
  return frame.replace(new RegExp(`\\{\\{${token}\\}\\}`, "g"), () => value);
}

export async function assemble(
  key: string,
  parts: {
    input?: string;
    context?: string;
    evidence?: string;
    challenges?: string;
    cognitive?: string;
  }
): Promise<AssembledPrompt> {
  const frame = await engineeringFrame(key);
  const { text: cognitiveUsed, source: cognitiveSource } = await cognitiveFor(key, parts.cognitive);

  let user = frame;
  user = fill(user, "INPUT", (parts.input ?? "").trim() || FILL.input);
  user = fill(user, "CONTEXT", (parts.context ?? "").trim() || FILL.context);
  user = fill(user, "EVIDENCE", (parts.evidence ?? "").trim() || FILL.evidence);
  user = fill(user, "CHALLENGES", (parts.challenges ?? "").trim() || FILL.challenges);
  user = fill(user, "COGNITIVE", cognitiveUsed || FILL.cognitive);

  return {
    key,
    system: PROMPT_SYSTEM,
    user,
    cognitiveUsed,
    cognitiveSource,
    chars: PROMPT_SYSTEM.length + user.length,
  };
}
```

## 附录 B · 认知段的治理规则全文（`prompts/cognitive/README.md`）

````markdown
# 认知指令段（第 ③ 段）

这个目录是**方法部门唯一要编辑的地方**。工程段（`prompts/engineering/`）管输入
契约、上下文注入、输出格式、硬约束；认知段管「你要想清楚什么」——同一个工程
骨架配不同的认知指令，产出的判断质量差得远。

## 目录长什么样

```
prompts/cognitive/
  skills/                        ← 方法部门给的技能文档原件，一个文件一份技能
    m1a-s01-issue-framing.md
    m1a-s02-pre-research.md
    m1a-s03-strategic-deep-research.md
  a1a.triage.md                  ← 按 prompt key 建，每个引一份技能 + 说这一次做哪一步
  a1a.issue.new.md
  a1a.issue.update.md
  a1a.issue.external.md
  a3.pre-research.md
  a4.research.md
```

## 技能文档怎么引

认知段文件里写 `{{SKILL:m1a-s01-issue-framing}}`，装配时会换成
`skills/m1a-s01-issue-framing.md` 的正文（YAML frontmatter 会被剥掉 —— 那是登记
信息，不是给模型看的；版本号在正文第一行的标题里，所以剥掉不丢溯源）。

**引，不要抄。** S01 一份技能同时管四个 prompt key：抄成四份之后，方法部门给
v0.5 时改三份漏一份 —— 漏的那一个照样跑、照样出格式正确的议题，只是它按上一版
的标准在判断，而结果页上看不出任何区别。

技能文件不存在或名字不合法，装配会抛 `SkillNotFoundError`，不会换成空串。跟
`PromptKeyError` 同一个道理：装没装上，必须在跑起来的那一刻就炸。

## 一份认知段文件写什么

两块，顺序固定：

1. `{{SKILL:<名字>}}` —— 完整的方法标准；
2. `---` 之后，**这一次**的落法：走技能里的哪几步、技能里那几块对应输出 JSON
   的哪个字段、这条路上最容易犯的失败模式。

技能文档里的 Output Contract 是文本块（`Sharp Title：` 那种），和工程段的 JSON
schema 冲突。所以技能正文放前面，字段对应表放最后 —— 离紧跟其后的「输出格式」
段最近，模型最后读到的是真正要交的形状。

## 改完怎么生效

改完重启 dev server（`prompts.ts` 首次用到时读盘并缓存）。文件不进 webpack
产物，靠 `next.config.ts` 的 `outputFileTracingIncludes: ["./prompts/**/*.md"]`
带进容器 —— 那个 glob 已经覆盖 `skills/` 子目录。

运行时也能传：`assemble(key, { cognitive })` 或 `new Harness({ cognitive })` 传进
来的优先，用于一次性试不同写法而不改文件。A3 / A4 不走 `assemble()`（它们的 user
段是手写的一整份），但用同一个 `cognitiveFor()` 取值 —— 两条取值路径的话，「这个
agent 的认知段到底装上了没有」得分开查两遍。

S03 那份技能的 §6 Output Contract 要的是**一份可署名分发的正式报告**，而屏幕上要的
是四节。**这两件事现在都交** —— A4 先按 §6 写那份报告（存进 `ResearchDoc.sourceText`，
报告页签默认给的就是它），再把它压成四节 JSON 给判断板和划词溯源取值。`a4.research.md`
第一节写的就是这个两层落法。

**这里踩过一次坑，值得记下来。** 上一版的落法段写的是「这一次的交付不是那份 Word
报告」，于是 §6 整段被关掉了：技能装得好好的、`cognitiveSource` 记着 `default`，跑出来
却永远是四节，没人能从台账上看出那份报告是被我们自己压掉的 —— 它看起来像模型写不出。
**落法段能压掉技能里任何一段，所以「不适用」这三个字要用得比技能本身更谨慎**：写下它
之前先问，这一段是真的和载体冲突，还是只是当时那块屏幕上没有它的位置。后者的解法是
多给一层交付，不是关掉标准。

**技能升版时，落法段里那些 §x.y 要跟着重锚一遍。** v0.4 → v0.5（2026-08-20）这一次
就是活例子：v0.5 重排了 §4、把 §6 的四小节改成五小节、§7 从两栏并成五条、§8 从
十四条收成七条，而 v0.4 的 §4.5（四档强度 + 高强度表达 Gate）、§4.6（Challenge 必须
改变结论）、§4.7（Company Relevance / Recommendation）、§8.8（末尾免责）、§8.9
（Pseudo Precision）在 v0.5 里整条没有了。只换 `skills/` 那个文件的话，落法段照旧
引着一批已经指不到东西的编号 —— 模型读到的是一份自相矛盾的标准，而结果页上看不出
任何区别。v0.5 新增的 §2 研究模式（Mode A / Mode B）也需要落法：内部材料不够时哪个
字段承接哪一块，`a4.research.md` 第三节写的就是这件事。

确定性质量门（`src/lib/agent/a4/validate.ts` 的 A4-01…A4-13、`rules.ts` 的 G-05）
不跟着技能编号动，它数的是字段形状、条数、字数和溯源。技能升版**不要顺手改它** ——
那是两套东西：技能定「该想清楚什么」，质量门定「交出来的形状对不对」。

文件不存在时 `{{COGNITIVE}}` 会被换成「（本条 Prompt 的认知指令段尚未提供）」，
`cognitiveSource` 记成 `empty`，跟着 Run 记录落盘 —— 所以「这次跑的时候还没有
认知段」事后查得出来。**不要为了占位建空文件**：空文件会被记成
`cognitiveSource: "default"`，反而把这件事藏起来。

## 故意不在这里的：A5 判断生成

`a5.judgements` **没有认知段文件，也不去 `cognitiveFor()` 取。** 这不是还没装 ——
把深研报告收成几条待一号位确认的判断，不归方法部门管，它的整份 prompt 写在
`src/lib/agent/a5/prompt.ts` 里（形状照的是 Package 04b 那份 Judgment）。

所以看到这里少一个文件时，**不要为了「补齐」给它建一个**。建了会有两个后果：
台账上多出一条「这一轮带了标准」的记录，而那份标准是我们自己编的；以及下一次
方法部门升版时，有人会去改一份根本不该由他们维护的文件。
````
