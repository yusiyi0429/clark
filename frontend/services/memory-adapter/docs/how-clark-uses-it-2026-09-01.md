# clark 是怎么用这个服务的（2026-09-01）

写给本体这一侧。目的是让你在改投影、改关系名、改打分器的时候，知道哪一头会跟着变。
下面全部按代码里的实际写法讲，接口名、参数值、字段名都是真的。

## 零、总体

clark 每一次调用你的目的只有一个：**把「公司现在是什么状况、这条议题此前已经有什么
认识」装成一段 Markdown，塞进这一次要发给大模型的提示词里。**

装好的那段有字数上限 `MAX_CONTEXT_CHARS = 16000`。超了会裁。

一次装配会打你 4 到 8 次（P0 一次、P1 若干次、P2 若干次、P3 一到三次），全部是读。
每一次打了哪个端点、传了什么参数，都记进这一轮的运行记录，用于复现。

**除了实体编号列表（`memberIds`），别的都被拼成了那段 Markdown。** 判断的 `status`、
召回种子的分数，在拼完之后就不再以结构化形式存在。这一点你要知道：你多发一个字段，
如果 clark 没有专门去读它，它不会自动出现在任何地方。

## 一、什么时候会调你

六条链路，触发各不相同：

| 链路 | 干什么的 | 什么时候触发 | 配方 |
| --- | --- | --- | --- |
| A1a | 把一条信号立成议题 | 一号位在信号页点「立案」 | S01 |
| A3 | 议题的预研 | 议题建立后自动跑一次 | S02 |
| A4 | 议题的深度研究 | 打开议题页时，没有报告就跑一轮 | S03 |
| A10 | 会后落库 | 会议纪要确认后 | S03 |
| 对话（开局） | 一号位跟系统对话 | 每一轮对话开始前预取一次 | S02 |
| 对话（中途） | 同上 | 他提到一个你库里可能有的东西时，模型自己发起一次查询 | 不装配，直接 P1 |

A4 那条最费钱：一轮深度研究要跑 25 到 30 分钟、二十多次模型调用。所以它拿到的上下文
质量，影响的是最贵的那一段。

## 二、一次装配的完整顺序

分两步：**先定锚点，再按配方装。**

### 第一步：定锚点

「锚点」在 clark 这边指的是**一个实体编号**，装配从它出发。三条路，优先级从高到低：

1. **调用方直接给编号**（`anchorCode`）—— 只在复现一次旧运行时用。
2. **按这条议题挂着的判断号**（`judgmentCodes`）—— 目前只有配方 S02 走这条。
   clark 前端的议题对象在你库里不存在（前端那些 `ISS-001…009` 是
   `scripts/gen-seed-from-ontology.mjs` 生成种子时自己编的号），但**议题挂着的判断号
   在你库里是真实存在的**（`01-J3` 这一类）。所以这条路直接拿判断号去取，不猜。
3. **语义检索**（`autopick`）—— 打一次 `/api/v1/context/dynamic`，参数固定
   `k=8, budget=2000`，把回来的种子按分数排序，然后**只保留编号前缀匹配的那些**：
   A1a 认 `CARD-`，其余全部认 `ISS-`。

第 3 条上面还有两道判断，任一命中就当作「你库里没有对应的议题」，不选锚点：

- `FLAT_RATIO = 0.9`：全体种子里最低分 ÷ 最高分 ≥ 0.9，判为「打分器认为这句问题跟
  库里每样东西都一样远」。种子数不足 4 条时不做这个判断。
- `TIE_RATIO = 0.95`：最高的那条 `ISS-*` 的分数 ÷ 全体首名的分数 < 0.95，判为
  「你库里更贴近这句问题的不是一条议题」。

两个都是**比值不是分数**，所以换 embedding 模型仍然成立。绝对阈值换模型就废了。

送进 P3 的 `q` 会先裁到 100 字符（你那边 `max_length=100`，超了 422）。裁过这件事
会写进警告，因为「按前 100 字选的锚点」和「按整条信号选的锚点」不是一回事。

### 第二步：按配方装

三个配方，P3 的参数是**写死的、不随任何东西变**。原因：思考深度只驱动 clark 自己的
研究规模；如果深度也改 P3 的 `k`/`budget`，同一条议题在不同深度下会拿到不同的公司
上下文，两次结果就不可比了。

**S01（立案）**，锚点是一条信号：

```
P0  /api/v1/context/static
P1  /api/v1/entities/{信号编号}?view=latest
P1  该信号关联的每条议题                       ← 逐条
P2  这些议题动摇的每条判断 ?view=chain          ← 逐条
P3  /api/v1/context/dynamic   k=5   budget=3000
```

**S02（预研 / 对话开局）**，锚点是一条议题：

```
P0  静态上下文
P1  /api/v1/entities/{议题编号}?view=latest
P2  它动摇的每条判断 ?view=chain               ← 逐条，取版本链
P1  每条判断的当前版 ?view=latest              ← 逐条，为了读 shakenBy
P3  k=3   budget=1200
```

**S02 的第二条入口（按判断号）**：不取议题对象，直接从判断号出发取版本链。代价是
装出来的正文里**没有【议题定义】那一段**——那一段只有你库里的 Issue 对象答得出来。
这一档会如实写「议题在前端在办，图谱里还没有这个对象」，避免模型把空白读成
「图内对这条议题没有认识」。

**S03（深度研究 / 会后落库）**，锚点是一条议题：

```
P0  静态上下文
P1  /api/v1/entities/{议题编号}?view=latest
P2  它动摇的每条判断 ?view=chain
P1  达成的共识对象（AGR-*）                     ← 逐条
P3  三次：k=3/budget=1200、k=10/budget=6000（按核心问题）、k=5/budget=3000（按议题标题）
```

## 三、clark 从返回里读哪些字段

- **`relations` 里六个关系名**：`hasJudgement`、`shakes`、`shakenBy`、`spawns`、
  `researchForOf`、`resolvedBy`。读不到的走空数组，**不报错、那一段直接空掉**。
  （今天实测你这边发的是 `spawnsOf`，所以 `spawns` 那一段是空的。见
  `handoff-2026-09-01.md` 第一条。）
- **`view=chain` 的 `versions[]`**：`index` / `status` / `at` / `statement`。
- **P3 种子的 `code` 和分数**：`code` 用于前缀筛选和白名单，分数用于上面那两道判断。
- **P0 的 Markdown 正文**：原样嵌进去。

## 四、失败怎么处理

三态，必须分开，clark 这边对三者的反应完全不同：

| 你返回 | clark 判为 | 后果 |
| --- | --- | --- |
| 200 | 取到了 | 正常装配 |
| 404，或检索选不出锚点 | **不是故障** | 转「纯外部」：这一轮不带公司上下文，照跑照出报告，报告里写明没带 |
| 503 / 连不上 / 超时 | 是故障 | A3、A4 就地失败（有一条运行记录）；**对话那条不失败**，只记日志继续说话 |

对话那条与 A3/A4 的分歧是有意的：让一号位因为后台某个服务不在而对不了话，比少一段
上下文糟得多。

「检索这一次没跑出来」和「你库里确实没有这条议题」在 clark 这边是两句不同的话，
不能互相顶替：后者的意思是「这条输入对公司现有方向来说还太新」，那是一个判断；
前者只是一次检索故障。混成一句，会让人把故障读成判断。

对话还有一个额外的超时闸：取上下文超过一定毫秒数就放弃，本轮不带上下文。

## 六、这意味着你改动时要注意什么

1. **改关系名 = clark 那一段静默变空。** 不会报错，屏幕上和正常跑完一样。
2. **改打分器 = 上面那两道判断的行为跟着变。** 它们是比值不是绝对分数，所以换模型
   本身没问题；但如果新模型让分数分布整体变平，会有更多议题被判成「库里没有」。
   这两个常数的实测值每一轮都进运行记录，误判了直接调常数就行。
3. **`q` 的 100 字符上限**是 clark 这边裁剪逻辑的依据，改了要说一声。
4. **P0 的正文长度**直接占用那 16000 字符的额度。它变长，别的段就被裁得多。
