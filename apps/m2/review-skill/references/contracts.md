# 复盘对象、承诺基线与确认权

本页定义复盘谁、对照什么、谁确认。怎样判定见 method.md，各层写什么见 quality-bars.md。业务方的新口径优先于本页。

## 复盘对象

和拆解用同一套单元：Company LTO → 战场 LTO／能力域 LTO → RU 的月度 PO → Mission → Task。

- **Mission 复盘（个人复盘）**：一个 Mission 一份，页面上按负责人归在一起。对照这个 Mission 本月的成果、成功标准和时间。它下面每个 Task 是一行事实证据。
- **RU 复盘（责任单元复盘）**：一个战场或能力域一份，只复盘 PO。对照本 RU 本月的 PO：成果、成功标准、完成定义。它下面每个 Mission 是一行事实证据。
- **公司复盘**：全公司一份。对照公司本月的方向或目标，以及公司 LTO。每个责任单元是一行事实证据。
- **Task 不单独复盘。** Task 是所属 Mission 复盘里的事实行。

战场对客户和业务结果负责；能力域对可复用的能力和它在哪里被用上负责。复盘时各看各的承诺：战场看客户和业务状态变了没有，能力域看能力交出去、被用上了没有。

## 承诺基线

- 判定对照**本次选定基线**。通常采用本月有效承诺：月初确认的版本，加上月中经有权人确认的变更。变更从确认那天起生效，之前的部分仍按原承诺看。已指定采用最新来源的试用任务，按下一节取基线，不把正式确认当作候选生成的前置条件。
- 讨论意见、口头解释、事后反馈，都不改变正式承诺；采用试用来源也不替人确认正式承诺。
- 未指定最新来源试用、资料里又找不到承诺时，写明“未找到本月承诺”，按资料里能找到的最接近的目标判定，并在判定理由里写清用的是哪一份。

### 最新来源试用基线

当前试用采用 latest-source-candidate：有真实 Task 或执行计划条目，就用本体读取到的最新来源版本。较旧正式版与较新草稿并存时取较新来源，不再正式版优先。Task、Mission 尚未确认、formal 为 draft 或正式生效指针为空，本身不阻止生成复盘候选，也不把这些状态改成已确认或正式生效。

每个来源保留对象、版本和 revision、所属父级、原始组件引用、周期、事实截止及真实 formal 状态，固定在本次输入快照里。同一来源的正文、执行计划与组件引用取同一版本，不能用旧正文配新条目。完整读取最新 Task 与执行计划，按稳定引用合并，保留仍存在的独立 Task；不能因计划未确认或某处没有列出就丢掉已知子项。

inBaseline 表示纳入这次候选基线，effective 只表达来源实际的正式生效状态，两者分开。资料只支持草稿或未知时，照实保留，不补写正式确认。输入不完整仍须补齐：缺正文、稳定引用、来源版本、父级归属，来源匹配有歧义或读取未完成时，不能把缺口伪装成无子项。

最新来源选择只确定这次复盘候选评什么，不改变三档判定、证据发生时间或确认权。评估仍按本期与事实截止，不把截止后才发生的结果计入本期。保存、展示、导出和后续引用保留这份基线的来源身份；复盘被确认不等于原计划已正式生效。源版本变化时另立候选，不静默换入已生成或已确认的旧轮。

### 本期有效直接子项

判定 PO 时只看它直接承接的真实 Mission，判定 Mission 时只看它直接承接的真实 Task。不把全部后代摊平计数，也不按事实表的行数认子项。Task 可以来自独立对象，也可以来自本次选定基线里的执行计划条目；后者须是原计划已有的直接 Task，有稳定原始条目引用、所属 Mission 和来源版本，保留计划来源。正式承诺基线按确认依据取范围，最新来源试用基线按上一节取范围，不能只凭“有计划文字”认作 Task。

成功标准占位行、为展示而拆的行或模型临时分解出的计划条目，不是新的 Task 或 Mission；它们仍用于核对本对象的成果和必要验收条件。

按选定基线的本期范围和事实截止确定子项。经有权人正式取消、替换或移出本期的子项，不计入当前有效子项；保留原承诺、变更依据和此前历史。最新来源的计划修订保留版本差异，不冒充正式承诺变更。讨论中的取消意向、事后解释和模型建议不改变范围，不能删除未完成子项来提高判定。

本来没有子项，或正式变更后已无有效子项，都按 method.md 的无子项分支核对本对象，不能因集合为空自动判达成。清单缺失、读取失败、父子关系或生效范围不明，不等于没有子项；先补齐原对象和变更记录，不能自行选无子项分支。

## 一个结果算一次

- 一个结果按主归属算在一个单元里。能力域交给战场的东西，能力域算“交出去、被用上”，战场算“客户和业务变了没有”，两边各写自己的部分。
- 同一个人在不同单元承担的结果，分别在各单元里评。
- 同一条证据可以支持几个判断，但同一项交付、收入或使用案例只计一次。

## 确认权

- **Mission 复盘（个人复盘）**：只由 Mission 负责人自己确认。所属 RU 的 DRI 不签字，但要提交洞察。
- **RU 复盘**：RU DRI 和 CEO 确认同一版本。CEO 本人兼任这个 RU 的 DRI 时，也按两个位置各确认一次，和拆解一样。
- **公司复盘**：CEO 确认。
- **确认顺序**：个人复盘在复盘生成后 24 小时内由本人确认；单元复盘要等本单元的个人复盘都确认后才能确认，48 小时内完成；公司复盘在各单元复盘确认后由 CEO 确认。时限和顺序由程序和页面管，Nexus 提醒时照这个说。
- **握手覆盖判定、事实证据和下期输入。** 分析洞察不握手：参与者各自提交，公开前只有本人看得到自己写的，公开后所有人可见；Nexus 综合也不握手。
- 质量检查通过、复盘被确认、结果达成，是三件不同的事。复盘写得准、被确认了，判定仍可以是未达成。
- 确认后的整份复盘（判定、事实证据、下期输入、公开的洞察和 Nexus 综合）是下月拆解的参考输入。确认后再改，形成新的候选版本，不覆盖已确认的内容。
