# 产品生成整轮复盘候选

产品一次生成整轮复盘候选：各 Mission、各 RU 和公司的复盘，全部完成后交给人讨论、修改和确认。程序只负责按本页调用、校验 JSON 结构、提供测量结果（证据编号核对、证据日期、字数、上下层判定对照），以及展示结果；判定和检查的判断按本技能。

**产品生成时以本页为准。** 本页只写流程、每一步交什么、怎样检查；怎样判定见 method.md，各层写什么见 quality-bars.md，表达见 reader-format.md。

## 流程

```
0. 准备数据：各单元本月有效承诺、Mission 下的 Task、截止前的证据清单（带编号）、负责人自评和周复盘、CEO 反馈（如有）、人员与职责
1. Mission 复盘（个人复盘）：每个 Mission 一次调用，全部同时进行
2. RU 复盘（责任单元复盘）：每个战场和能力域一次调用，全部同时进行
3. 检查与修改：三组检查同时进行 → 修改
4. 公司复盘：一次调用
5. 总校验与修改：查全部类型，超出字数的字段一并改短
6. 输出给程序展示，人开始介入；判定、事实证据和下期输入握手，参与者提交洞察
7. 洞察公开后：Nexus 综合洞察，每份复盘一次调用
```

已完成的步骤可以先展示，标为“草稿·校验中”；整轮完成后才开放评论和确认。

每次检查的交叉验证最多做 1 轮：先验证，再修改，修改后不单独复验，留下的问题由后面的检查接着查。

### 直接子项输入

PO 和 Mission 的输入 unit.childCommitments 提供本次基线中的本期直接子项范围，不改变 review 输出字段。基线选择统一见 contracts.md“承诺基线”。当前试用的来源元信息如下：

- input.basis：整轮的 mode 为 latest-source-candidate，另有 snapshotHash、period、cutoff。
- unit.sourceBasis：这个对象的 basisMode、snapshotHash、objectId、sourceVersion、sourceRevision、sourceStatus、formal（原始 business.formal 或 null）、period、cutoff、effective。
- unit.childCommitments：本对象的 basisMode、snapshotHash、complete、items、excluded，以及有缺口时的 missing。它与整轮基线、unit.sourceBasis 对应同一冻结输入，不能一处取最新、另一处仍指旧正式版。

```json
{"basisMode":"latest-source-candidate","snapshotHash":"冻结输入散列","complete":true,"items":[{"ref":"原始引用","kind":"Task|Mission","parentRef":"所属对象","period":"本期","inBaseline":true,"effective":null,"source":"object|planItem","objectId":"对象来源时提供","version":1,"sourceRevision":"实际来源修订","formal":null,"componentRef":"计划来源时提供原始组件引用","confirmedVersion":null,"status":"来源已有状态"}],"excluded":[{"ref":"移出项原始引用","reason":"正式取消、替换或移出依据","authority":"有权确认的来源","effectiveAt":"生效时间"}]}
```

complete 只表示声明的基线范围已读全、来源与归属可确定且无匹配歧义，不表示正式生效。latest-source-candidate 中的 items 按 inBaseline 纳入范围；effective 为 false 或 null 本身不移除该项，也不使 complete 变 false。effective 只有明确正式依据时为 true；明确未生效时为 false，证据未知时为 null。formal、来源状态和实际确认版本照输入保留，不把候选身份改成正式确认。

不完整时先报告具体 missing，不把缺正文、ref、版本、父级、重复或模糊匹配、读取未完成当作无子项来生成或接受判定。items 的来源资格与 excluded 范围统一见 contracts.md；objectId、版本、修订、组件引用、确认版本和 status 按实际已有信息给，不编补。unit.tasks、expectedFacts 用于完整列事实行，不能取代 items；successCriteria 占位行不进入 items。首次整轮生成可用同轮下级复盘的候选判定，仍整体作为候选展示；讨论后已确认与未确认版本的引用按 revision-loop.md 区分。

sourceBasis 和 childCommitments 是程序保存与传递的来源元信息，不要求模型另造 review 字段或声明。生成、讨论、保存及后续引用沿用冻结元信息；恢复运行使用原输入与技能快照，源版本变化时不能把旧输出拼进新基线。程序负责取数和校验，判定仍由模型按 method.md 作出，不事后改写模型输出。

## 每一步怎么做

**每次生成先写 analysis**（不展示）：逐项列出要写的事实行，每项对上证据编号或写“无证据”；按 contracts.md 核对有效直接子项与成功标准占位行，按 method.md 第 1、4 节选择本层适用规则，并逐项核对本对象成果和必要验收；按第 2 节采信负责人具体陈述，核对自评是否补足事实；再定判定。analysis 不超过 600 字。然后写展示字段，第一遍就写成人话。

**1. Mission 复盘**（个人复盘。每个 Mission 一次调用。输入：这个 Mission 的承诺全文、它的 Task、与它有关的证据、负责人自评、所属 RU 的 PO）：
1. 事实证据一个 Task 一行：输入 unit.tasks 里每一行都要有一行事实，ref 照抄；unit.tasks 里有计划条目也有 Task 对象，都算。某行带 expected（预期产出）、quality（质量标准）、finish（截止日期）或 definition（Task 定义）时，按它们定这一行的 status：预期产出有没有交出、是否达到质量标准、是否在截止日前完成。没有 Task 的，按输入的 expectedFacts 一项一行。
2. 按 method.md 第 1 节定 Mission 总体判定，写判定理由；事实行和有效直接子项的区别按 contracts.md。
3. 按 method.md 第 6 节写下期输入。问题最多 1 个，只问 Mission 负责人自己的事；要单元 DRI 定的、跨单元的写成待决策、不挂问题，由单元或公司复盘去问。

**2. RU 复盘**（责任单元复盘，只复盘 PO。每个 RU 一次调用。输入：本 RU 的 PO 和长期目标、本 RU 各 Mission 复盘、RU 层面的证据、别的 RU 写到本 RU 的需求和交付）：
1. 事实证据一个 Mission 一行，status 照搬该 Mission 复盘的判定，evidence 写一句它的结果，不重抄 Mission 复盘的细节。没有 Mission 的单元，输入里会给 expectedFacts（PO 每条成功标准一项），一项一行，ref 和 item 照抄。
2. 按 method.md 第 4 节，以 PO 为起点定判定，写判定理由。
3. 写下期输入：合并各 Mission 复盘的下期输入里属于本单元的，去掉重复；本单元自己定不了的写成待决策。问题最多 2 个，只问单元 DRI 能定的单元内的事：从各 Mission 复盘留下的待决策里挑真正要拍板的问；Mission 复盘已经问对了人的不再问；Mission 复盘问了本该单元 DRI 定的事，或几个 Mission 问了同一件事，在这里合成一问，这一条写 covers:[{ref:该 Mission 复盘的 ref, index:那一问在它 nextInputs 里的序号（从 0 起）}]。跨单元的不问，留给公司复盘。

**3. 检查与修改**：三组同时检查全部 Mission 和 RU 复盘，然后按单元修改。

**4. 公司复盘**（一次调用。输入：公司本月方向或目标、公司 LTO、各 RU 复盘、公司层面的证据）：
1. 事实证据一个责任单元一行，status 照搬该单元复盘的判定，evidence 写一句它对公司目标的结果。
2. 按 method.md 第 4 节，以公司目标为起点定判定，写判定理由。
3. 写下期输入：只写跨单元的、要 CEO 拍板的事，单元自己能接的不再重复。问题最多 3 个，只问跨单元的事，问 CEO。输入 askedBelow 列出单元和个人复盘里已经问的全部问题（ref、level、title、index、type、text、to、question）。单元内的、已经问对人的不再问；问的是跨单元的事，或几处问了同一件事，合成一问在这里问 CEO，这一条写 covers，列出接过来的每一问（ref 和 index 照抄 askedBelow）。下层那几问由程序去掉，不用回去改。

**5. 总校验与修改**：三组同时查全部复盘，重点查上下层判定是否对得上（按程序给的 verdictFacts）、同一件事有没有在个人复盘和单元或公司复盘里重复提问、证据编号和日期（按 evidenceFacts）、该有的行有没有漏、月初起点有没有被算成本月结果。修改时把程序实测超出字数的字段（lengthFindings）一并改短。

**Nexus 综合洞察**（洞察公开后，每份复盘一次调用。输入：review 里这份复盘的层级、标题、负责人、判定、判定理由和事实证据；insights 里所有参与者的洞察，每条有作者和正文）。照下面写，返回 {text}：
1. **先归纳共性。** 把意思相同的洞察合成一条，写明是谁提的（例如“白田田、于斯一都提到”）。只有一人提、但事实证据里有对应行的，也保留。
2. **再站在公司管理层看。** 不讲某一行为什么没做成，而是问这些原因合起来，说明公司在哪一类上出了问题：目标（承诺不清、太多、没分核心）、理念（默认做法不对，比如先做完再给人用）、机制（缺规则或缺人负责）、流程（步骤和节奏不对）。大家没提到、但事实证据里看得出的共性，补 1 条，写明对应哪几行。
3. **一个问题配一条建议。** 每条写成“**问题：**……（属于目标、理念、机制或流程）**建议：**谁、改什么做法、从什么时候起”，写到下月拆解能接住。
4. 共 2–4 条，全文 300 字左右。不点名批评个人，不评绩效，不重复事实证据的细节；洞察里没有、事实里也看不出的，不编。
5. 没有人提交洞察时，只按事实证据写 1–2 条，开头写“本份复盘没有人提交洞察，以下按事实证据整理”。
6. **单元复盘的综合**：insights 里除了直接写在单元复盘上的，还有各 Mission 复盘公开的洞察，标签是“来自 Mission N 复盘”。一起读，先找几个 Mission 都提到的同一类问题，归纳成本单元的共性，写明出自哪几个 Mission；只在一个 Mission 出现的，属于单元层面的问题才写进来。再按上面 2–4 步写。
7. **公司复盘的综合**：输入里还有所有复盘公开的洞察，按复盘分组。先看各单元的洞察里反复出现的问题，归纳成公司层面的共性问题，写明出自哪几个单元；再按上面 2–4 步写。

## 字段

每份复盘返回 review：

```json
{"verdict":"达成|部分达成|未达成","verdictReason":"一句话",
 "facts":[{"ref":"编号","item":"这一项是什么","owner":"负责人","status":"达成|部分达成|未达成|未开始","evidence":"现状和证据，带日期和证据编号","gap":"没达成时事实上的原因，达成时写空字符串"}],
 "nextInputs":[{"ref":"对应 facts 的 ref","type":"继续|调整|停止|待决策","text":"一句话","ask":{"to":"名字","question":"要回答的问题"},"covers":[{"ref":"下层复盘的 ref","index":0}]}]}
```

facts 的 ref：个人复盘用输入 unit.tasks 里每个 Task 的 ref，每个 Task 都要有一行；没有 Task 的 Mission，输入里会给 expectedFacts（每条成功标准一项），一项一行，ref 和 item 照抄。单元复盘用 missionReviews 里每个 Mission 的 ref，没有 Mission 的用 expectedFacts 的 ref；公司复盘用 ruReviews 里每个单元的 key。

nextInputs：有几条写几条，不凑数，最多 5 条（公司复盘最多 8 条）。每一行事实最多对应 1 条下期输入，同一行的几件事合成一句；对不上具体哪一行、说整份复盘的（ref 为空字符串），每份最多 1 条；已达成的行一般不写。多了就合并同一件事、去掉次要的；判定为达成、也没有未了事项的，可以是空数组。type 只用继续、调整、停止、待决策。ref 写对应 facts 的 ref；说的是整份复盘、对不上某一行时写空字符串。text 一句话，不超过 60 字。ask 要少，个人复盘最多 1 个、单元复盘最多 2 个、公司复盘最多 3 个，只在不回答下月就没法拆、复盘自己又判断不了时写：to 写人员名单里的真实名字（一般是这一项的 DRI 或 CEO），question 一句话、不超过 60 字、以问号结尾；不需要时不写 ask。covers 只在接过下层的问题时写：公司复盘可以接单元和个人复盘的，单元复盘可以接本单元个人复盘的；ref 是下层那份复盘的 ref，index 是那一问在它 nextInputs 里的序号（从 0 起）；可以接几问。写了 covers 的这一条要带 ask。

生成时不写洞察，结果里不带 insights、causes、targets、ltoReview。

## 检查

问题分类：判定偏宽、判定偏严、判定回避、过程当结果、证据不符、漏行、事实混进分析、上下不一致、重复计算、输入接不住、内部用词、结构与表达、其他。

必须修改的问题类型：判定偏宽、判定偏严、判定回避、过程当结果、证据不符、漏行、事实混进分析、上下不一致、重复计算、输入接不住、内部用词。

保留上述分类定义。另外两种问题也必须修改：表达使读者无法看清谁做了什么、结果或限制是什么；遗漏了会影响判定、事实理解或后续行动的关键证据。前者按“结构与表达”分类，后者按已有定义分类，没有对应类型时用“其他”。impact 写清具体误解或遗漏影响。不把一般润色全部升级为必改，也不把同一行内的证据省略一律叫“漏行”。关键证据的取舍见 reader-format.md。

检查分三组，同时进行，每组只查本组的类型：

- 第一组（判定与证据）：判定偏宽、判定偏严、判定回避、过程当结果、证据不符
- 第二组（事实与下期输入）：漏行、事实混进分析、上下不一致、重复计算、输入接不住
- 第三组（表达）：内部用词、结构与表达、其他

**怎样判断：**
- **判定偏严、判定偏宽**：按 method.md 第 1、4 节对应层级的规则核对，实际判定低于或高于该分支应给的档位。不能用公司核心承诺规则覆盖 PO、Mission 的分支；按第 2 节采信的负责人具体陈述属于证据，不算无证据改判。
- **判定回避**：用“尚不能确认”“有待观察”代替判定，或判定理由没说清哪条成立、哪条没有。
- **过程当结果**：把方案、代码、测试、演示、会议写成了承诺的结果，或某行 status 给了达成而 evidence 只到过程。
- **证据不符**：把月初起点算成本月结果；引用的编号不存在、证据日期晚于事实截止（看 evidenceFacts），或证据证明不到句子说的程度（见 method.md 第 2 节的表）；或人名、数字和输入不一致。
- **漏行**：输入里的某个 Task（个人复盘）、Mission（责任单元复盘）或单元（公司复盘）没有一行（看程序给的 rowFacts.missing）；或一行缺 status、evidence。
- **事实混进分析**：evidence 或 gap 里写了分析、评价或建议，例如“缺少机制”“说明能力不足”“建议下月……”。
- **上下不一致**：上层事实行的 status 与所引用下层版本的判定不符，或 PO、Mission 总体判定不符合 method.md 的适用分支。讨论后状态引用按 revision-loop.md；说明分歧不能替代正确状态，未确认草稿不冒充已确认版本（看 verdictFacts）。
- **重复计算**：同一项交付、收入或使用案例在两个单元里都算成了自己的结果。
- **输入接不住**：下期输入超过 5 条（公司复盘超过 8 条），或为了凑数写了次要的事；同一行事实对应了 2 条以上；ref 为空字符串的超过 1 条；已达成的行带了下期输入（程序会在 lengthFindings 里列出“已达成行带下期输入”），除非确实要停止或继续看效果，否则删掉；问题超过上限（个人复盘 1 个、单元复盘 2 个、公司复盘 3 个），或问了能从事实推出、负责人自己能定的事，或同一件事在两层都问了（跨单元的留公司复盘那个；其余留被问的人负责的那一层），或上层接了下层的问题却没写 covers，或一个问题问了两件事、重复 text 里的原因，或问的是下月怎么排（范围、先后、谁牵头、哪个 Mission 承接），或问一条记录算不算证据；ref 不是空字符串却对不上任何一行事实；类型不在继续、调整、停止、待决策四种里；写成了下月计划（新的 Mission、负责人、排期）；没达成的核心一行没有对应的下期输入；或单元复盘漏了下面 Mission 复盘里的未了事项。
- **内部用词**：判定理由、事实证据、下期输入或问题里写了版本号、编号、内部代号、英文缩写或英文词（见 reader-format.md 第 0 条），单元以外的人看不懂。程序会在 lengthFindings 里列出“疑似内部用词”，逐条判断：确实是代号、编号或英文黑话的算这一类；是人名、产品名或通用词的不算。改法：换成大白话的全名；说承诺变更时写清是哪一条承诺。
- **结构与表达**：违反 reader-format.md，比如回避结论的句子、超过 30 字的句子、要人翻译的说法（程序会在 lengthFindings 里列出疑似的地方）。

**每次检查**返回 JSON，issues 必须是数组；没有问题时返回 {"issues":[]}。每条问题写清复盘 ref、类型、问题、影响、是否必改，以及能否通过修改解决：

```json
{"issues":[{"ref":"复盘 ref","type":"问题类型","problem":"具体位置和问题","impact":"对理解、判定或后续行动的影响","mustFix":true,"fixable":true}]}
```

problem 写明受影响的事实行 ref 或字段；没有事实行时指明复盘中的位置。mustFix 和 fixable 都必须给布尔值，含义不同：
- 必须修改类型的 mustFix 恒为 true；其他类型按前述关键影响条件决定，不由 fixable 反推。
- 能据现有输入修正表述、补回关键事实或重新判断的，fixable 为 true。缺少完成证据时，可以修正结论和表述，不能以缺材料为由跳过这些可修内容。
- 确实需要补充事实、消除未解冲突或取得权限才能解决的部分，fixable 为 false。problem 和 impact 写清具体缺什么、影响哪一项，以及仍未解决的限制；已有证据和可作出的判断继续保留，不编造材料，也不把没有记录写成没有发生。

证据编号、日期和字数以程序给的测量为准。不复述复盘全文。不可修的必改问题仍是未解决问题，不能写成已经修复或全部无问题。

**修改**只处理被指出的必须修改的问题：
- 程序检查出的问题（type 为“程序检查”，比如条数超限、缺字段、Task 没有对应的行）一律要改，按 problem 说的改到符合为止。
- 只改被指出的问题和直接牵连的内容，只交回改动的复盘（按 ref 替换）。改了某一行，判定理由里对不上的地方一起改。
- 判定偏宽就降档；判定回避就给出判定；漏行就补行。不靠删掉缺口、换一个更松的标准来“消除”问题。
- 认为问题不成立，可以不改，在缺口里写理由。

## 输出

全部复盘的最终内容、仍未解决的问题和资料缺口，交给程序展示。
