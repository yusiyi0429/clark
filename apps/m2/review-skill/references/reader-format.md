# 表达规范与字数

目标：负责人和 CEO 很快看懂、很快判断。参照简化技术写作规范（ASD-STE100）：一句一事，句子短，用统一的词，先说结论。先在 analysis 里想清楚，再按本页写给人看；分析过程和检查清单不进正文。

## 写法

0. **人一看就懂。** 写看得见的事：谁、做了什么、结果是什么、记录在哪。不用要人再翻译的说法，比如“闭环”“打通”“赋能”“具备条件”“初步形成”“有效支撑”“进一步验证”。例如“数据闭环初步形成”改成“财务数据每天自动进入系统，Agent 能读到，负责人确认后能写回”，并且只在有证据时这样写。
   **不造词，不写代号。** 判定理由、事实证据、下期输入和问题里，不写版本号（如“rev14”）、编号（如“01-1”）、内部代号和说法（如“父 PO”）、英文缩写和英文词（如“Readiness”）。要提就写成大白话的全名，例如“设计稿 rev14”写成“灯塔首次会面体验流的设计稿”，“父 PO 剩余结果”写成“灯塔 10 月目标里还没做成的那几条”。按“这个单元以外的人第一次看也能懂”来写。产品里的模块和功能也写中文说法，不写英文名（如“Context Engine”“Blueprint”“Grounding”），第一次提到时用半句话说清它是做什么的；单元名（如 Method、Talent、Finance）和人名、Agent、TokenHub 这类大家常用的名字照用。证据编号 [E3] 和 ref 字段不算，它们不进正文给人读。
1. **写肯定句，下结论。** 写“未达成：客户还没用上”，不写“尚不能确认是否达成”。证据缺了，写“缺××证据，按未满足处理”。一句话里最多一个“不”。
2. **一句只讲一件事。** 一句不超过 30 个字，超了就拆。每句有主语和动词。
3. **先说结论。** 每个字段第一句就是答案，依据放后面。
4. **主动句，写明谁做了什么。** “于斯一 9/24 交付了备份功能”，不写“备份功能已被交付”。
5. **用统一的词。** 同一个东西全文一个叫法。人名、系统名第一次出现时写全。技能术语只在 analysis 里用，比如“必要条件”“主归属”“过程进展”，正文换成人话。
6. **要点格式**：每个要点是“**短标题：**正文”。短标题点明结论，正文不加粗。一个要点只讲一件事。
7. **证据编号放句尾**：写成 [E3]，几个编号连着写 [E3][E5]。不在正文里贴长链接。
8. **同一件事只写一次。** 下层复盘写过的细节，上层那一行用半句引用，不再复述。
9. **具体代替空话。** 写数字、名单、日期、系统名。未知的写在受影响的句子旁边：缺什么、影响什么。

## 字段字数上限

上限不是写满的目标。

| 内容 | 上限 |
|---|---:|
| 判定理由 | 60 字，一句 |
| 事实行 item | 30 字 |
| 事实行 evidence | 100 字 |
| 事实行 gap | 60 字 |
| 下期输入 text | 60 字 |
| 下期输入 ask 的问题 | 60 字，以问号结尾 |
| Nexus 综合洞察 | 全文 300 字左右，每条 100 字 |

计数按去掉格式标记、证据编号和空白后的可见字符。超长时先删重复和空话，再拆短句；不删判定、数字、日期、责任和缺口。压缩时保留会影响判定、事实理解或后续行动的关键证据和限制；不要求逐字照抄来源，也不重复同一事实。

## 交付前自查

- 只看判定和判定理由，能说出本月做成了什么、没做成什么吗？
- 该列的每个 Task、Mission 或单元都有一行吗？每行都有 status 和证据吗？
- evidence 和 gap 里有没有混进分析和建议？
- 每条下期输入都对得上一行事实，写的是未了事项，不是下月计划吗？
- 有没有“尚不能确认”“仍需进一步”这类回避结论的话？
- 每句是否只讲一件事、不超过 30 字？
