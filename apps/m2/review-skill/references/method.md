# 怎样复盘

本页讲判定、证据、原因、上层综合和下月输入。复盘对象和确认权见 contracts.md，各层字段见 quality-bars.md。

## 1. 判定三档

先列出本月的关键目标：成果里写的状态、每条成功标准，PO 下面还有各 Mission 的结果。逐个对证据，写出每个目标月底的实际情况。然后认出**核心承诺**，再定档。核心承诺怎样认：资料写了 P0、重点或“最重要”的，按资料；没写时，是这个单元本月新要做成、它存在的理由所在的那几件事，不是日常运营和例行工作。

- **达成**：核心承诺的状态已经成立，有证据。次要目标个别没满足，在目标对照里写明。
- **部分达成**：核心承诺本身成立了一部分，而且成立的是结果，不是过程。例如承诺 3 个客户在用，实际 1 个在用。只做成了日常工作或次要目标，不算部分达成。
- **未达成**：核心承诺的状态没有发生。其他目标做得再好，或者只有方案、代码、测试、演示、内部试用这类过程进展，都判未达成。

怎样定得准：

- **按核心承诺判，不按条数判。** 4 项里 1 项成熟的日常工作做好了、3 项新工作没做成，判未达成。核心那件做成了、外围几件没做完，可以判达成。关键目标里一半以上没做成，又说不出核心那件做成了，判未达成。
- **看结果，不看工作量。** 做了很多建设，核心结果没发生，就是未达成。反过来，结果已经满足本月标准，不因长期效果还没证明就降档。
- **看本月承诺的那一步。** 本月只承诺首次试用，首次试用成功就算达成；本月承诺持续使用，一次试用只算部分达成或未达成。
- **外部原因按归属算。** 完全在别人手里的事没发生（例如客户推迟启动），不扣负责人自己那部分结果；自己那部分照样要有证据。
- **“做出来”和“用起来”分开看。** 核心承诺包含“做出来”和“用起来”两步时：做出来达到可以正式使用（已上线或交付，目标用户或 CEO 看过并认可可用），这一步本身是结果；用起来没发生、主要卡在外部（客户没启动、对方排不出时间），判部分达成或达成，在判定理由里写还差的那一步。只有演示、测试环境或本人试用，算没做出来，判未达成。例如“产品已上线、CEO 认可可用，客户项目推迟没用上”判部分达成或达成；“只有 Demo、没部署”判未达成。
- **专项和整体分开判。** 一个单元里某个专项做成了，在关键目标里写“该专项达成”，肯定做成的部分；单元的判定仍按整体核心承诺给出。RU 复盘里各 Mission 的判定照搬 Mission 复盘，不同意时写明理由。
- **负责人自评是一条证据，不是判定。** 自评常见三种偏差，逐个核对：把建设进展算成部分达成；把没做成归为“原计划太高”“前提不具备”“外部原因”；只讲困难，不讲做了什么。
- **证据缺了照样判。** 某条标准找不到证据，就当它没满足，判定照常给出，并在目标对照里写“缺××证据”。负责人后来补了证据，再改判。
- **分清“没做”和“没记”。** 有记录证明没做成的，写实际情况；只是记录停在某天、之后没有记录的，写“记录截至 MM/DD，之后无记录”，判定照样按未满足给出。程序给的 recordFacts 写了每个单元最新一条记录的日期。
- **标准写得含糊时**，按最贴近原文的理解判，在判定理由里写一句“按××理解”。不替负责人换一个更容易的标准。
- **Mission 全部达成，PO 也可能没兑现。** 这时写清是哪个必要条件没有被任何 Mission 覆盖，或者外部前提没有成立。

## 2. 证据

### 三个时间

- **复盘月份**：评哪个月。
- **事实截止**：只算截止前发生的事。截止后才发生的事不算本月结果。
- **取得时间**：截止后才拿到、但能证明截止前发生的记录，可以用，注明取得时间。
- **月初起点**：本月开始前就已经成立的结果（例如上月已到岗的人、上月已上线的功能），是本月的起点，不算本月做成的结果。输入里标为“月初起点”的条目只用来判断本月往前走了多少。

### 证据能证明到哪一步

| 证据 | 能证明 | 还证明不了 |
|---|---|---|
| 方案、文档写好 | 内容已形成 | 被采纳、被使用 |
| 代码、联调、测试通过 | 在测试条件下能跑 | 正式上线、真实用户在用 |
| 正式环境上线 | 可以用了 | 有人持续在用、带来效果 |
| 真实用户用了一次 | 首次使用和反馈 | 稳定持续使用 |
| 一段时间的使用记录 | 这些人在这段时间在用 | 效果是它带来的 |
| 报价、意向、约定入职 | 谈到了哪一步 | 签约、到岗、成本落地 |
| 会议开了、材料备好 | 讨论发生了 | 有权人已经决定 |

### 用证据的规矩

- 每个判断引用证据编号，写成 [E3]。编号来自输入里的证据清单。
- 人名、数字、日期照输入原样写，不改写、不补全。输入里没有的事不写成事实；从证据推出来的，写“推断：”加依据。建议写成要做的事，不写成已经做了。
- 负责人自己的说法写成“负责人报告”，CEO 的意见写成“CEO 反馈”。它们是证据的一种，和底层记录对不上时，两边都写出来。
- 同一件事在几份周报里出现，只算一次。
- 数字写清对象、口径和日期。没有事前基线，就不算偏差，只写实际数。

## 3. 原因

只对影响判定的重要结果和缺口找原因。按下面几问还原，答到能改变下次选择就停：

1. 风险什么时候看得见？看见之后做了什么调整，为什么没扭转结果？
2. 在现有条件下，本可以先做什么？比如先冻结一个最小版本进入真实使用，先用手工和现有方法验证，先建一个粗的模型再补数据。
3. 哪些事负责人自己能决定，却没做或做晚了？
4. 哪些是外部条件：别的单元的交付、客户、审批、资源？负责人有没有及时提出、找人决定、换路径？
5. 几个目标的结果有什么规律？比如熟悉的工作做成了、新问题都没做成；功能做出来了、使用没跟上。规律往往就是最重要的原因。
6. 再往上追一层：这个原因下个月还会不会重复？背后缺的是什么能力或工作机制？例如需求一变就挤掉验收、没有评测办法判断质量好坏、遇到新问题不会拆成可验证的小步。新问题没做成时，分清是专业能力、工作方法、计划判断，还是组织协同的问题。

原因归到四类之一，可以同时有几类：

- **执行**：路径是对的，没有按时、按质做完。
- **打法**：范围、顺序、时间安排撑不起结果，比如把真实验证都放到月底。
- **判断**：月初的前提不成立，比如高估了现有能力，或客户的节奏和预想不同。
- **条件**：缺人、缺数据、缺授权、缺别的单元的交付。

写法：一条原因写清“什么事 → 怎样影响了结果 → 下次要改变什么”。外部条件是原因时，也写负责人自己做了什么、还能做什么。原因证据不够区分时，写出最可能的解释，再在这条原因的 ask 里写要负责人回答的问题，判定照常给出。

## 4. 上层综合

### RU 复盘

- 起点是 PO：PO 的成果成立了没有，每条成功标准满足了没有。
- 各 Mission 的判定是证据，不按 Mission 数量平均。一个 P0 Mission 未达成，PO 通常不能判达成。
- PO 复盘有 Mission 时，目标对照第一行写“Mission 结果”（没有 Mission 的单元不写这一行）：各 Mission 的判定，一行说完，例如“3 个 Mission：1 个部分达成，2 个未达成”。其余各行只写 PO 自己的成功标准，Mission 复盘里写过的细节不再复述，需要时写“见 Mission 2”。
- 看对长期目标推进到哪一阶段：本月这一步跨过去了没有，离到期还差什么。
- 战场看能力域交来的东西用上了没有；能力域看战场的需求接住了没有、交付了没有。

### 公司复盘

- 起点是公司本月的方向或目标：哪几项成立了，哪几项没有。
- 各单元的结果合起来，公司要的结果成立了吗？各单元都有进展，公司要的那条链路仍可能没跑通。
- 找共同的原因：几个单元卡在同一个人、同一项交付、同一个决定上，写出来。
- 审视长期目标：按本月结果，长期目标还能按期达成吗？三选一并写清理由：建议维持（目标和期限都不变）、建议修改（目标方向不变，改某一条的内容或期限，写改哪条、改成什么）、建议重开（目标的前提已经不成立，要重新形成长期目标，写哪个前提变了）。由 CEO 决定。

## 5. 下次要改变什么

写在每条原因的末尾，不单独成块：从本月的成功或失败里提炼一条以后怎么选的做法，写触发条件和做法。例如“主路径够用后，先留出一周真实使用，再加功能”。月初的前提被本月结果推翻时，也在这里点明；月初没有记录的前提，写“本月结果说明……”，不编一个原判断。

## 6. 下月输入

下月输入是复盘交给下月拆解的东西。每条写成：类型、要接住什么、为什么。类型只用下面几种：

| 类型 | 写什么 |
|---|---|
| 欠账 | 本月没做成、下月还必须做成的结果，写清还差哪一步 |
| 继续验证 | 本月有了初步结果、还要真实使用或更多证据才能确认的事 |
| 停止 | 本月证明不值得继续的事，写理由 |
| 约束 | 下月必须考虑的人手、资源、依赖、外部节奏 |
| 待决策 | 本单元定不了、需要上级拍板的事：决定什么、谁决定、不决定的影响 |

- 每条来自本复盘里的一个具体结果、缺口或原因，不写复盘里没讲过的新事。
- 写到“要接住什么”为止。下月的 PO、Mission、负责人和排期由拆解来写。
- 每份复盘 1–4 条。RU 复盘的下月输入要覆盖它下面各 Mission 复盘里的欠账，合并重复的。
