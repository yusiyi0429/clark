# 怎样复盘

本页讲判定、证据、事实行、上层综合、洞察和下期输入。复盘对象和确认权见 contracts.md，各层字段见 quality-bars.md。

## 1. 判定三档

先列出本月的关键目标：成果里写的状态、每条成功标准，PO 下面还有各 Mission 的结果。逐个对证据，写出每个目标月底的实际情况。然后认出**核心承诺**，再定档。核心承诺怎样认：资料写了 P0、重点或“最重要”的，按资料；没写时，是这个单元本月新要做成、它存在的理由所在的那几件事，不是日常运营和例行工作。

- **达成**：核心承诺的状态已经成立，有证据。次要目标个别没满足，在那一行写明。
- **部分达成**：核心承诺本身成立了一部分，而且成立的是结果，不是过程。例如承诺 3 个客户在用，实际 1 个在用。只做成了日常工作或次要目标，不算部分达成。
- **未达成**：核心承诺的状态没有发生。其他目标做得再好，或者只有方案、代码、测试、演示、内部试用这类过程进展，都判未达成。

怎样定得准：

- **按核心承诺判，不按条数判。** 4 项里 1 项成熟的日常工作做好了、3 项新工作没做成，判未达成。核心那件做成了、外围几件没做完，可以判达成。关键目标里一半以上没做成，又说不出核心那件做成了，判未达成。
- **看结果，不看工作量。** 做了很多建设，核心结果没发生，就是未达成。反过来，结果已经满足本月标准，不因长期效果还没证明就降档。
- **看本月承诺的那一步。** 本月只承诺首次试用，首次试用成功就算达成；本月承诺持续使用，一次试用只算部分达成或未达成。
- **外部原因按归属算。** 完全在别人手里的事没发生（例如客户推迟启动），不扣负责人自己那部分结果；自己那部分照样要有证据。
- **“做出来”和“用起来”分开看。** 核心承诺包含“做出来”和“用起来”两步时：做出来达到可以正式使用（已上线或交付，目标用户或 CEO 看过并认可可用），这一步本身是结果；用起来没发生、主要卡在外部（客户没启动、对方排不出时间），判部分达成或达成，在判定理由里写还差的那一步。只有演示、测试环境或本人试用，算没做出来，判未达成。例如“产品已上线、CEO 认可可用，客户项目推迟没用上”判部分达成或达成；“只有 Demo、没部署”判未达成。
- **专项和整体分开判。** 一个单元里某个专项做成了，那一行写“达成”，肯定做成的部分；单元的判定仍按整体核心承诺给出。责任单元复盘里各 Mission 行的 status 照搬 Mission 复盘的判定，不同意时在 gap 里写明理由。
- **负责人自评是一条证据，不是判定。** 自评常见三种偏差，逐个核对：把建设进展算成部分达成；把没做成归为“原计划太高”“前提不具备”“外部原因”；只讲困难，不讲做了什么。
- **证据缺了照样判。** 某条标准找不到证据，就当它没满足，判定照常给出，并在那一行写“缺××证据”。负责人后来补了证据，按第 2 节“负责人陈述”重新判断；不能因为证据来自本人就不改。
- **分清“没做”和“没记”。** 有记录证明没做成的，写实际情况；只是记录停在某天、之后没有记录的，写“记录截至 MM/DD，之后无记录”，判定照样按未满足给出。程序给的 recordFacts 写了每个单元最新一条记录的日期。
- **标准写得含糊时**，按最贴近原文的理解判，在判定理由里写一句“按××理解”。不替负责人换一个更容易的标准。
- **Mission 全部达成，PO 也可能没兑现。** 这时写清是哪个必要条件没有被任何 Mission 覆盖，或者外部前提没有成立。

## 2. 证据

### 三个时间

- **复盘月份**：评哪个月。
- **事实截止**：只算截止前发生的事。截止后才发生的事不算本月结果。
- **取得时间**：截止后才拿到、但能证明截止前发生的记录，可以用，注明取得时间。
- **月初起点**：本月开始前就已经成立的结果（例如上月已到岗的人、上月已上线的功能），是本月的起点，不算本月做成的结果。输入里标为“月初起点”的条目只用来判断本月往前走了多少。

### 证据能证明到哪一步

| 证据 | 能证明 | 还证明不了 |
|---|---|---|
| 方案、文档写好 | 内容已形成 | 被采纳、被使用 |
| 代码、联调、测试通过 | 在测试条件下能跑 | 正式上线、真实用户在用 |
| 正式环境上线 | 可以用了 | 有人持续在用、带来效果 |
| 真实用户用了一次 | 首次使用和反馈 | 稳定持续使用 |
| 一段时间的使用记录 | 这些人在这段时间在用 | 效果是它带来的 |
| 报价、意向、约定入职 | 谈到了哪一步 | 签约、到岗、成本落地 |
| 会议开了、材料备好 | 讨论发生了 | 有权人已经决定 |

### 用证据的规矩

- 每个判断引用证据编号，写成 [E3]。编号来自输入里的证据清单。
- 人名、数字、日期照输入原样写，不改写、不补全。输入里没有的事不写成事实；从证据推出来的，写“推断：”加依据。建议写成要做的事，不写成已经做了。
- 负责人陈述按下面一节处理；CEO 的意见写成“CEO 反馈”。存在相反事实时，写清双方来源与具体冲突；没有记录不属于相反事实。
- 同一件事在几份周报里出现，只算一次。
- 标为“单元层面进展”的记录说的是整个单元，不能单独证明某个 Task 达成；要有能对上这个 Task 的预期产出或负责人的记录。只有单元层面进展时，这一行写“只有单元层面进展，缺这一项自己的记录”，status 按未满足给。
- 数字写清对象、口径和日期。没有事前基线，就不算偏差，只写实际数。

### 负责人陈述

负责人对自己负责事项的亲历陈述，是有来源的证据，可以支持事实、单项状态和总体判定的修正。用事实行的负责人、报告表述和消息引用保留陈述人及来源；陈述时间保留在消息元信息，不必重复进正文。事实发生时间按原话记在具体动作旁，不将发生日期写成陈述日期，也不把陈述时间当成发生时间，不补猜日期、数字或独立核验结果。

- **具体事实要采信。** 对象和结果明确、对得上原承诺，且没有相反事实时，按负责人陈述重判。无需先有本体记录或额外附件；本体尚未补记、读取不全或旧记录停在更早日期，都不是否定新陈述的理由。没有独立核验时注明“负责人报告：……”并保留来源，不将其写成日志或验收已核验。
- **结论与事实分开。** “已经上线”“实际用过”要落到当前讨论的事项；“全部都算达成”“相信我”或反复坚持本身不补足具体事实。缺的信息会改变结论时，只问最关键的一项，不重复索要已经给过的材料。
- **按标准限定修正。** 上线事实支持上线，使用事实支持使用；一次使用不自动证明持续使用、稳定性或经营效果。只有影响本月归属时才追问发生时间；截止后发生的事不算本期成果，截止后补述的本期事实可以采用。
- **冲突要具体。** 新陈述与明确的失败记录、不同范围或时间不一致时，指出哪一事实冲突、各自来源和需要澄清的一点。核对后能解释的按解释修正；仍冲突的保留双方依据，按既有确认权处理。不能把材料缺失说成冲突，也不因职位或强调语气采信无关陈述。

没有负责人陈述、也没有其他完成证据时，仍按第 1 节现有规则给三档判定，在对应行写清缺口。不增加标签、证据状态字段或新的确认角色。讨论中的改稿流程见 revision-loop.md“人工纠正”。

## 3. 事实行

- 一行一项，该列的都要列：个人复盘列每个 Task，责任单元复盘列每个 Mission，公司复盘列每个单元。没开始的写“未开始”，并在 gap 写没开始的事实原因。
- evidence 只写看得见的事实：谁、哪天、做了什么、结果在哪，带证据编号。
- gap 只写表面的原因：什么事没发生、卡在谁或哪一步、哪天。例如“E&O 写回接口 10/27 才交，月底前没来得及接”。不写“为什么会这样”“背后缺什么机制”，那是洞察。
- 负责人自评里的解释，写成“负责人报告：……”，和底层记录对不上时两边都写。

## 4. 上层综合

### RU 复盘

- 起点是 PO：PO 的成果成立了没有，每条成功标准满足了没有。
- 各 Mission 的判定是证据，不按 Mission 数量平均。一个 P0 Mission 未达成，PO 通常不能判达成。
- 事实证据一个 Mission 一行，evidence 一句话写它的结果，Mission 复盘里写过的细节不再复述。PO 自己的成功标准没有被任何 Mission 覆盖时，在判定理由里写明。
- 看对长期目标推进到哪一阶段：本月这一步跨过去了没有，离到期还差什么。
- 战场看能力域交来的东西用上了没有；能力域看战场的需求接住了没有、交付了没有。

### 公司复盘

- 起点是公司本月的方向或目标：哪几项成立了，哪几项没有。
- 各单元的结果合起来，公司要的结果成立了吗？各单元都有进展，公司要的那条链路仍可能没跑通。
- 事实证据一个单元一行。几个单元卡在同一个人、同一项交付、同一个决定上，在各自那一行的 gap 里如实写出，归纳留给洞察。

## 5. 洞察和 Nexus 综合

洞察回答：这些结果和原因合起来，说明公司在管理上哪里要改。参与者写，公开后 Nexus 综合。

找共性可以这样问，答到能改变公司的做法就停：

1. 几项的结果有什么规律？比如熟悉的工作做成了、新问题都没做成；功能做出来了、使用没跟上；都卡在同一类依赖上。规律往往就是最重要的问题。
2. 风险什么时候看得见？看见之后，公司的流程里有没有一个点让人及时收窄范围、换路径或找人决定？
3. 这个问题下个月还会不会重复？背后缺的是哪一类：
   - **目标**：月初定的承诺本身不清楚、太多，或没有分清核心和次要；
   - **理念**：做事的默认想法不对，比如先做完再给人用、把功能当结果；
   - **机制**：缺规则或缺人负责，比如需求变更没有规则、跨单元依赖没人确认、没有评测办法判断质量；
   - **流程**：步骤和节奏不对，比如真实验证都排在月底、复盘和拆解接不上。
4. 一个问题配一条建议：谁、改什么做法、从什么时候起，写到下月拆解能接住的程度。

Nexus 综合时，先把大家的洞察按问题合并，注明谁提的；再看事实证据里有没有大家没提到的共性，补充 1–2 条更深一层的问题。补充的每一条都要能对上事实证据里的行，不凭空推测，不点名批评个人。

## 6. 下期输入

下期输入是复盘交给下月拆解的未了事项和待决问题，不是下月计划。

- 从事实里来：每条对上一行事实（ref），写这一项还剩什么、要接住什么。事实里没有的事不写。
- 选类型：没做完、路子对的写**继续**；路子要变（换做法、缩范围、换人）的写**调整**；证明不值得做的写**停止**并写理由；本单元定不了的写**待决策**。
- 问题要少，按 quality-bars.md“下期输入”一节：只在不答下月就没法定怎么做时问；个人复盘最多 1 个、单元复盘最多 2 个、公司复盘最多 3 个；一件事只问一次，问在被问的人负责的那一层，跨单元的只在公司复盘问 CEO；上层接过下层的问题时用 covers 标明。问题写成一句能直接回答的话。
- 下层的不重复往上抄：单元复盘合并各 Mission 的未了事项，公司复盘只写跨单元、要 CEO 拍板的事。
