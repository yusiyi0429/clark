# 维护本技能

本页给维护者看，不发给生成模型。目的是防止技能越改越长、越改越乱。

## 设计依据

2.0 按 tkos-decoding 3.x 的结构重写。1.1.1 的问题：规则散在 15 个文件、同一条规则重复 5–7 次、以否定句为主（模型照着写，结论不敢下）、没有给程序用的字段和检查约定。2.0 的要点：一个单元一份；判定三档、必须给出；结果先于过程；原因讲到能改变下次选择；下月输入带类型和编号，交给拆解；先想清楚再简洁表达。

## 每条规则只有一个出处

| 内容 | 唯一出处 |
|---|---|
| 复盘对象、承诺基线、一个结果算一次、确认权 | references/contracts.md |
| 判定三档、证据、原因、上层综合、判断变化、下月输入 | references/method.md |
| 各层字段的写法、好坏示例 | references/quality-bars.md |
| 表达规范、字数上限 | references/reader-format.md |
| 产品生成流程、字段名、问题分类、必须修改的类型、检查分组 | references/round-stages.md |
| 讨论中的修改、分歧、上下层回查 | references/revision-loop.md |

其他文件需要这条规则时，写“见某文件某节”，不重新表述。

## 改规则的步骤

1. 先找原出处，在原处改，不在别处新增相近规则。
2. 改完删掉被替代的说法，全文搜索确认没有矛盾。
3. 规则文件里不写历史；版本说明写在本页末尾。
4. 用正面的说法，写“要做什么”；需要禁止时说明原因。
5. 规则里不写具体人名、日期、单元名；示例用通用或虚构内容。
6. 小改动先攒着，凑成一版再跑评测；评测以人工复盘和 CEO 判定为基准，并由人抽查，AI 评审只作参考、每组至少评两遍。

## 产品读取的文件

产品生成时依次发送：SKILL.md、reader-format.md、round-stages.md、contracts.md、quality-bars.md、method.md。round-stages.md 里“必须修改的问题类型：”“- 第N组（名称）：类型”的写法会被程序读取，改动时保持格式。2.1.12 检查结果增加 mustFix 布尔值，保留 fixable；程序须接入逐项必改标记。2.1.13 的“自动修订最多做 N 轮。”用于读取自动修改上限；每轮修改后均须复查，计数按同一份复盘累计，不因阶段或续跑重置。检查契约见 round-stages.md；缺字段或检查失败不得按空问题放行。reader-format.md 字数表的行名会被程序读取，不要改名。scripts/ 的两个脚本只在聊天中使用，产品不调用。
