# 容量、估时与排期

计划要能做成，不只是写得完整。本页是排期规则的唯一出处。

## 1. 本期能承诺什么

- **重要程度和兑现把握分开。** 核心结果可能仍有外部风险，不因重要就算稳妥；已承诺的延伸目标也不能擅自取消。
- **三类候选：**
  - 保底：人手、估时依据、关键供给和时间窗口都有支持。
  - 条件：只有客户参与、审批、供给、人员到岗等条件满足才成立；写清解除条件、最晚判断时点、失败后的选择。
  - 争取或本期不做：不占保底资源，写清为何延后、影响什么。
- **外部效果不能靠我方任务完成来保证。** 客户未同意、候选人未接受、采购未批时，不把采用、到岗、交付写成保底。
- **资料缺口要改变相关判断。** 缺的是事实、投入、外部窗口、交付条件还是通过门槛，会不会改变本期成果；会的话给出有理由的范围候选，并写明补齐后才能定的那一项。只在末尾写一句“待确认”而正文不受影响，不算处理。

## 2. 容量

- **同一个人只有一份时间。** 按实际执行人合并他在所有 RU 的全部工作；负责人不等于全部工作的执行人，未知执行人不默认由负责人补位。
- **默认口径**：输入给出工时口径（如“全职、每工作日 8 小时、无其他工作”）时，按口径计算容量，本人另有说明的以本人为准。没有任何口径时，写明按什么假设估算。
- 只加总最底层的实际投入，上下级不重复计。工作投入和等待时间分开：等客户三天是历时，不是三个人日。

## 3. 估时

- **先看实际做过的。** 优先用本团队相似工作的实际投入、交付时间和返工记录；没有可比数据时，用执行者给的区间和假设，并写明。不报没有依据的完成概率。
- **算上隐形成本。** 每项工作的时长包括：调研分析、准备、实施、联调测试、上线或合并、和他人协作沟通、必要返工、验收。看起来很小的事，只要涉及联调、上线或协作，就不能只排一两天。
- **Mission 按完整工作周期估**，包括前期分析、实施、联调、试用、修正、验收和交接，不只算核心动作。

## 4. 排期

- **PO 的时间边界是整个月份**，不取 Mission 的首尾。月末是周期结算边界，不是默认的交付日。
- **Mission 的时间 = 它下面最早开始的 Task 的开始日，到最晚结束的 Task 的结束日。** Task 还没拆时先给建议窗口，拆完后重算。
- **Mission 的验收和里程碑日期落在它的 Task 里。** Mission 收尾时常要汇总、跨领域配合确认和验收，结束日会比主要工作稍晚。这段时间写成最后一个 Task（如“汇总与验收”），Mission 的结束日就是这个 Task 的结束日；不在所有 Task 之外凭空多出几天，读的人也能看到收尾这段时间在做什么。
- **工作是并行、交叉推进的，不是一个做完再做下一个。** 同一领域的多个 Mission 通常同时推进；同一 Mission 下的 Task 默认错位并行。不要把人当成同一时间只能做一两件事。
- **依赖不等于等上游全部做完。** 每条依赖写清等的是什么、到什么程度就能开始：上游部分可用时，下游就开始调研、方案、用例、环境等准备；只有真正需要上游最终交付的那一步才等待。
- **只有硬前置才首尾相接。** 首尾相接的两项工作，要在依赖里写明后一项需要前一项的哪份最终交付。
- **贯穿周期的工作**（客户协调、运营、问题处理）持续安排，和专业交付一起算进同一人的容量。
- **从硬窗口倒推，从资源正推。** 从客户使用、部署、审批、联合验收等硬窗口倒推上游最迟交付；再从前置可用时间和人手正推最早完成。正推晚于倒推时，明确冲突，给出减项、换顺序、替代供给或申请变更的选择，不暗改正式期限。
- **每个时间边界都写具体日期或起止范围**，不写“待定”。Task 已开始的写实际开始日和预计结束日；未开始的写建议起止日。外部窗口未确认时也给建议日期，并在依赖里写明假设、由谁何时核对、不满足时哪些日期要调整。
- **需要真实使用的 Mission** 要在周期内留出组织参与、使用、反馈和修正的时间，不在最后一天才交可用版本；可以分批交付，写明每批能用的范围。

## 5. 交付前的排期检查

1. 工作周期按工作量和隐形成本估，不是会议日期；一次会议可以一天，包含准备、适配和反馈处理的工作不能只排开会那天。
2. 只有真正受阻的部分等待，其余提前安排；业务能并行不等于同一个人能全职同时做两件事，按工作量判断是否超出这个人的可用时间。
3. 日期逐项核对：PO 等于整月；Mission 等于其 Task 首尾；Activity 落在所属 Task 内；硬前置的可用日不晚于被它阻塞的工作开始日。
4. 首演、第一次验证、部署启动只是节点，后续的使用、修正、推广如需要也要承接；已完成的工作不为填满日历再安排“优化”。
5. 有本地脚本时，用 [scripts/validate_schedule.py](../scripts/validate_schedule.py) 检查最终日期结构，失败先修正。脚本只验证日期结构，不证明工期合理或人手够用。
