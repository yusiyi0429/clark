# 做得成吗

计划要能做成，不只是写得完整。本页用项目管理的眼光检查：人日够不够、关键路径在哪里、依赖接不接得上、风险怎么应对、余量留没留。本页是排期规则的唯一出处。

## 1. 人日

- **同一个人只有一份时间。** 按实际执行人，把他在所有 RU 的全部 Task 投入加起来。默认每个人全职做本次拆出来的 Mission 和 Task，没有其他工作，每工作日 8 小时；可用人日就是拆解日到周期末的剩余工作日。本人另有说明的以本人为准。
- **只加最底层的投入**，上下级不重复计。工作投入和等待分开：等客户三天是历时，不是三个人日。
- **只算人的时间。** 每个人都带着 Agent 干活：很多 Task 和几乎所有 Activity 由 Agent 执行，但人仍要花大量时间提需求、和 Agent 来回沟通、审核结果、联调和做决定。投入按这部分人的时间估，Agent 自己执行的时间不算人日。effort 写成“人约 X 人日（Agent 做什么；人做什么）”。不假设负责人手下还有别的人，资料写明有人协作时才算进去。
- **先按实际要干的活估，再和预算比。** 每个 Task 的投入按它实际要干的活估，研发、联调、上线都要有具体的 Task，不按预算倒推，不为凑数调整估计。程序给出每人本月可用人日（capacityFacts）和本 Mission 的参考预算（personDayBudget）；估出来超了，如实写出来，再按下面的顺序处理。估计正好等于预算的，要在 analysis 里说明是怎么估出来的。
- **装不下时给删减清单。** 超出容量的工作，不硬压估计，也不硬塞进日程。在 gaps 里写清：哪项工作推迟到下月、哪项改为 P2、哪项需要加人，以及各自的影响；总校验时汇总到单元计划的风险里，交 CEO 或 RU DRI 取舍。
- **超了按顺序处理**：先合并同一条工作线里重复的工作；再降档（P1 改 P2、P2 拿掉；P0 不降）；还不行，把冲突写进单元计划的主要风险，交给人决定加人、推迟或取舍。不把彼此无关的事合并凑数。
- 估时优先用本团队相似工作的实际投入；没有时用区间，写明假设。
- **单元计划和 Task 的人日要对得上。** 单元计划里写的人日是各 Task 投入的合计，不另估一套。
- **能力域回应“接”之前先看容量。** 接下来的需求要算进负责人的人日；装不下就回应“部分接”或“接不了”。

## 2. 估时包含隐形成本

每项工作的投入包括：调研分析、准备、实施、联调测试、上线、协作沟通、必要返工和验收。涉及联调、上线或多人协作的事，不能只排一两天。会议只占一天，但准备和会后处理要另算。

## 3. 关键路径和关口

- **从硬窗口倒推，从人手正推。** 客户使用、部署、审批、联合验收等硬窗口倒推上游最迟交付；从前置可用时间和人手正推最早完成。正推晚于倒推时，写明冲突，并给出减项、换顺序、替代供给或申请变更的选择，不暗改期限。
- **关键路径**：在单元计划和 Mission 计划里点出决定能否按期完成的那几步，其余工作围绕它并行。
- **关口是共同结果**，不是串行阶段；各 Mission 可以提前准备，不必等前一个关口全部完成。

## 4. 依赖

- **只连真前置。** 上游部分可用时，下游就开始准备；只有真正需要上游最终交付的那一步才等待。依赖写清等的是什么：等对方做完，还是等初稿、第一批就能开始。等初稿或第一批的，两项的时间要重叠，不首尾相接。
- **Task 的时间是日历上的起止，不是投入。** 每个人都带着 Agent 干活，一个人可以同时推进几个 Task，只要同一段时间里投入加起来装得下。没有在等什么的 Task，从拆解日就开始。
- **质量门禁不挡首次真实使用**：核心路径能用，就先让真实用户用起来，同时修问题；不把“全部评测通过”设为首次使用的前提，除非涉及外部客户的安全、合规或资金。内部测试租户的调用不在此列。
- **跨领域依赖双向登记**：战场在需求里写，能力域在回应里写；没有回应的需求是悬空依赖，要在风险里写出来。

## 5. 日期

- **PO 的时间是整个月份**；月末是结算边界，不是默认交付日。
- **Mission 的时间 = 它最早的 Task 开始到最晚的 Task 结束。**
- **沿用已有节奏，从拆解日起排。** 已经在进行的工作，写实际开始日和既定节点；未开始的工作从拆解日（planningDate）起排，不从生成那天起排，也不空出拆解日之后的日子；已完成的不再安排。
- **每个日期都写具体日或起止日。** 外部窗口没确认时也给建议日期，并在依赖里写一次假设和由谁何时核对。
- **日期不能自相矛盾**：依赖的供给日不晚于使用它的工作开始日；Task 落在 Mission 时间内；关口日期落在支撑它的 Task 里。

## 6. 余量和风险

- **月底留返工时间。** 关键的真实使用和复测最晚在月末前一周开始。P0 Mission 的关键交付在月末最后两个工作日之前做完，最后两个工作日只留给返工和复核，不安排首次交付。
- **外部效果不能靠我方完成来保证。** 档位按结果本身的分量定（见 method.md 第 2 节）。要靠客户同意、候选人接受、采购审批的那一部分，在成功标准里写成“推动到可决策”，在风险里写最晚判断日和失败后的选择。
- **主要风险**写最可能让 P0 落空的 1–3 件事：触发信号、应对、由谁决定。

## 7. 交付前检查

1. 每个人的总投入在容量之内，超出的已按第 1 节处理或写进风险。
2. 关键路径上的每一步都有负责人和日期。
3. 依赖日期接得上，没有悬空的跨领域需求。
4. 日期没有矛盾，已有节奏没有被重置。
5. 月底留了返工时间。
