# 持续修订与握手

适用于首次候选之后的评论、讨论回复、负责人调整、新事实和执行反馈。Agent推进流程，Decoding负责每次拆解与修订的质量；沿用SKILL.md的逐层确认权，不另设审批层级。

## 每次修订怎样做

1. 读取当前有效稿、已确认版本及本次新增反馈。反馈记录保留提出人、所针对的对象／版本、原意和依据；回复要结合前文理解。已完成事实不被旧计划覆盖。
2. 区分事实补充、表达修改、方案建议和有权人的明确决定。多人提出相同建议不等于正式共识，无回复不等于同意；CEO对更下层提出建议也不自动替代该层握手。反馈冲突时说明具体分歧及其后果，先改不受影响部分，不能静默选边或把全部意见拼进去。
3. 判断意见是否成立，结合父目标、实际证据、资源与既有决定说明采纳、部分采纳、不采纳或待判断的理由。采纳后先改受影响成果／验收，再回查子项、交付接口、日期、共享资源及必要性；不是只润色被评论的句子，也不无差别重拆全部对象。
   归因先核对当轮输入：已给而漏用、原资料缺失、来源冲突、仅在对标方案出现分别处理。评论说“与负责人方案不同”只证明有差异，不能单独证明候选错误；找出差异是否影响结果、责任或可行性及其有效依据。PO本身有实质问题时先校准PO，再审Mission，不在错误上级结果下继续打磨Task。
4. 输出更新候选和简短差异，检查Card、Plan、Task及已有图是否一致。保留原确认版本、历史反馈及未决问题；普通局部修订不强制新开一轮，完整新轮按用户约定保留旧轮。内部留反馈与修改的对应关系，不擅自加进人读模板。
   先定位改动会影响哪些结果、验收、责任、供给接口、日期或共享资源，再逐项检查实际影响；检查不等于一律改写。确有影响的授权内候选同步调整，越权或涉及正式承诺的提出变更；没有影响的保留原文、日期及确认状态。影响沿真实依赖传播，不因层级相邻便重写全部上下游，也不能只改被评论的单元格后跳过核对。
5. 把当前候选、影响和所需判断交还Agent工作流：继续讨论、补输入，或在实质分歧和关键缺口已处理后提请有权人确认。缺确认人或授权时停在待确认，不以技能自评通过代替握手，也不固定讨论轮数。

## 已握手后怎样改

- 错别字、排版和不改变承诺含义的表述可在授权范围内整理，不伪造新的握手记录。
- 改变成果范围、验收、责任人、承诺日期或交付接口，形成变更候选，说明原因及上下游影响，由该层有权人重新确认；原确认版本在变更被确认前仍是基线，不能把候选直接覆盖成已确认版本。
- 下层方案调整未改变上层承诺时，由下层按其权限处理并让上层知情；若影响上层成果、验收或必要交付条件，提出对应上层变更，不逐级要求所有人签完整任务清单。
- CEO与RU DRI确认RU PO；RU DRI与Mission DRI确认Mission核心成果及必要验收、时间与接口。Company LTO与RU LTO仍在同一文档由CEO一起确认。下层正式确认权未定义时请求明确，不自行补定。
- 确认只针对准确的对象、版本和约定范围。一次确认不能自动批准其他对象或未来修订，握手、执行完成、验收及业务成果分别记录。

## 检查例

- 两条评论互相冲突、第三条仅修改文字：先处理文字，保留分歧，不能称三条意见已达共识。
- 已确认Mission的日期被建议提前且共享人员超载：提出带影响的变更候选，不更改原确认状态；检查是否影响RU PO交付窗口。
- Task路径变了但Mission成果、验收和日期均未变：回查方案与容量，不自动要求CEO重签Task，也不直接宣称可执行权限齐全。

这些是规则检查例，未实际独立生成和评判前，不称新版行为验证通过。
