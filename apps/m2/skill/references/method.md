# 怎样拆

目标：得到少而准、做得成的结果组合，让人看清为什么这样拆、还有哪些前提没成立。对象见 contracts.md，各层写法见 quality-bars.md，做得成的检查见 feasibility.md。

## 1. 输入与起点

**先读这几样：**

1. **上月计划**：类别 history，或标题以「【N 月 PO】」「N 月 PO（上月…）」「N 月 Mission（上月计划…）」开头的条目，N 是上个月；后面会标出是成果、验收、核心路径还是 Task 计划。用来看上月原本要做什么、做到了哪一步，推出本月该接着做什么。不照抄，也不当本月答案。某单元上月没有单列 PO 的，按缺口处理。
2. **上月结果**：类别 review，是上月复盘，含 CEO 的最终评价。标题写「N 月复盘（已确认第 K 版）」的，是产品里负责人确认过的复盘，以它为准。上月哪些没做成、CEO 点名要改什么、复盘写给下月的输入，本月都要有着落。
3. **拆解日的现状**：类别 state（各单元最新现状、拆解日当天的日进展、补录的事实），以及 resource（人员、关键日期、客户窗口）、organization（职责分工）、dependency（核心供需，只是主要的支撑关系，不是全部）。已经完成的直接引用，不再安排；正在进行的沿用原节奏和日期。 同一件事有新旧两条现状时，以最新的为准；标“较旧”的只作背景。
4. **长期目标**：本 RU 和公司的六个月目标，现在走到了哪一阶段，下一阶段的门槛是什么。
5. **本月目标只有公司方向**：只有公司单元里以“【本月意图】”开头的那一条。有就以它为准；没有不影响拆解。各战场、能力域本月自己的 PO、Mission、Task 不在资料里，要从以上几样自己推出来。
6. **按拆解日的时点拆。** 拆解日之后的日进展不读。少数晚于截止、经人确认读入的条目会标“事实截至”日期，按事实使用。

人员投入默认全职做本次拆出来的事，资料里没写每人投入不算缺口。

**推出本月要跨过的一步**：从整体出发，看长期目标能不能按期达成。在 analysis 里想清楚——长期目标到期时要成立什么；现在卡在哪一阶段；要按期达成，本月必须做成什么（包括该开始新建的能力，不只是补上月没做完的）；以现在的进展和人手，本月能跨过的、最有分量的一步是什么。上月欠账是考虑因素之一，不是起点；没做成又仍然关键的，放进本月这一步里。PO 的成果写这一步做成后的状态。没有 CEO 本月方向时，在握手清单里写“本月方向待 CEO 确认”；方向有明显分叉时，在单元计划的取舍里写出另一种选择和它的代价，供 CEO 选。

**分清四类资料**：有来源的事实（分清计划和已发生）、正式决定、待验证的假设、建议。资料上写的目标只说明被提出过。资料冲突时保留双方，写明影响。

**截止后读入的事实照常用**：资料里事实时间晚于截止日、但已经读进来的条目，是经人确认允许读入的，按事实使用，不因“晚于截止”弃用。

**现状的新旧**：按资料的事实截止日算到拆解当天。7 天以内正常用；7 到 14 天照用，但在依赖里写一次“请负责人核对现状”；超过 14 天只作背景。

**推断只当假设**：没有直接记录、靠推理得出的内容，引用时标“推断”并写依据；靠推断支撑的结果只能放 P1 或 P2，或先安排一个核实它的 Task。

## 2. 定本月台阶

- **先分主次，再拆。** 档位是为了让人一眼看出本月成败系于哪几件事。档位是排序，不是给每件事打“重要”的标签：同一组工作放在一起比，一定分出先后，正常情况下大致三等分，前三分之一 P0、中间 P1、后三分之一 P2。P0 可以略多于三分之一，但全公司不超过四成，绝不能接近一半。全公司的 Mission 放在一起看大致三等分；只有一条 Mission 的 RU，这条按它在全公司里的分量定。每个 Mission 标一个档位：
  - **P0 必达**：做不成本月就算失败。一个 PO 下最多 2 条，1 条还是 2 条按这个 RU 本月的实际情况判断。选本月要跨过的那一步里最关键的；CEO 本月方向写明了核心结果时以它为准。不做就别的都动不了的前提工作（如客户首次体验、架构确认）属于 P0：放进它所支撑的那条 P0 Mission 里作为 Task 或关口；只有它确实是另一个人负责的独立结果时，才单独成一条 P0 Mission。在 analysis 里写理由，并在握手清单里写“P0 选择待 CEO 确认”。要靠外部配合的核心结果仍是 P0，外部部分写进风险和应对。
  - **战场在等的交付优先。** 能力域的结果里，战场本月正在等着用的那一项（比如战场要靠它做决策或交付客户），排在能力域自身的其他事情前面，通常是 P0。
  - **P1**：重要，本月要做成，排在 P0 之后；做不成不等于本月失败。
  - **P2**：本月计划做成，人手紧时最先让出。比 P2 更次要的，本月不写。
  - **档位不进正文。** 档位只写在档位字段。成果、验收、Task 的成果里，不写“P1”“P2”“必达”“争取”“有余力时”“尽量”“视情况”这类词；P1、P2 的事和 P0 一样写成确定的结果。前提、条件和可能做不成的原因，写进风险或依赖，写清缺什么、影响什么、怎么应对。
  三档都要用上。全公司放在一起看，P1 不比 P0 多出很多，P2 也不能只剩一两条：问“人手紧时先让出哪几条”，这几条就是 P2。
  档位只是给已有的结果线排先后，不为了凑出不同档位而多拆 Mission；分不出先后时，问“只能保一件，保哪件”。人手装不下时，先把 P1 改为 P2、P2 拿掉，不压缩 P0 的成功标准。档位按结果本身的分量定，不按资料是草稿还是已确认定。
- **成熟度台阶**：可演示 → 可供使用 → 首次真实使用 → 多轮使用 → 持续采用 → 业务效果。每个结果写清本月到哪一级。不把长期的最高一级平铺成当月硬要求；也不擅自把已承诺的要求降级。
- **公司层写到本 RU 的内容也要读**：公司复盘里对本 RU 的点评、公司的战略判断、本 RU 现状里的阶段判断，和本 RU 自己的长期目标一样要逐条处理。
- **长期目标逐项过一遍，但不逐项承接。** 定完本月这一步后，对照六个月目标和上月缺口，找出被漏掉的、方向冲突的。被漏掉的要么补进本月，要么在 upstream 里写“本月暂缓”和一句理由。不把长期目标拆成几十条逐一承接。
- **承诺量对得上人手。** 档位为 P0 的结果，所需人日要在负责人的容量之内（见 feasibility.md）。容量没核对过不是降档的理由；确实装不下时，在单元计划的风险里写明，交 CEO 或 RU DRI 取舍，不自行把核心结果降成 P1。

## 3. 战场与能力域

- **战场先写。** 依据战场自己的长期目标和本月要跨过的一步，写出 PO 和 Mission；需要能力域的人专门为本战场做的事（部署、适配、专项开发、为本战场做的核算），直接写成本战场的 Mission 或 Task，负责人写那个能力域的人，他的人日照常算进总负荷，不写成能力域对战场的供给。只有能力域本来就要做、多个战场都会用的长线能力，才写成需求（demands），写清提供方、交付内容、需要日期、用途。
- **已知的供需要落地。** 输入里的 knownSupply 是资料里已经记下的供需关系。本月涉及的：主要为某个战场做的，写成这个战场的 Mission 或 Task（负责人可以是提供方的人）；属于提供方长线能力的，接收方写成需求，提供方回应。本月不涉及的，在 analysis 里说明。
- **供需记录只列了主要的支撑关系，不是全部。** 按本月实际需要找出其他支撑：能力域之间也会互相支撑（如产品能力支撑平台能力），职能能力域的人也会参与战场的事。能力域需要别的能力域的长线能力时，同样写进 demands，由对方在检查和修改时回应。
- **“部分接”要说清楚。** 能力域回应“部分接”时，写清接哪一部分、哪天能交；战场在检查和修改时，按回应调整自己依赖这份交付的日期和成功标准，不保留对不上的日期。
- **能力域后写，不只是给战场打下手。** 起点仍是能力域自己的长期目标、本月要跨过的一步和能力发展。战场的需求是另一项输入：先看它是不是只为这一个战场做的，是的回应“转回战场”，写建议由谁做、哪天能做，由战场写成自己的 Mission 或 Task。其余每条明确回应“接”“部分接”或“本月接不了”。接的落到本领域的长线 Mission，部分接写清接哪一部分，接不了写原因和影响，返回给战场。
- 能力域的 PO 写可持续的供给能力，并说明本月在哪个场景被用上、怎样证明有效。
- **一件事放在哪里，看它为谁、管多久。** 为某个战场当下急需、在这个战场里做的事（部署、适配、专项开发、当月必须交给这个战场用的功能），放在这个战场，作为它的 Mission，可以由能力域的人负责。能力域只放长线的能力建设和核心建设本身，能被多个战场复用、跨月迭代。同一主题可以分开放：比如平台能力里，支撑 Token 业务战场当月运行的那部分放战场，平台本身的长线迭代放能力域。能力域定档时参考战场需要什么，但战场的事不搬进能力域。我们自己的人把自己的产品用起来（比如 CEO 和 DRI 用天枢办日常工作），是能力域本身的事，不算哪个战场的事。
- **同一件事只写一次。** 一件事放在战场就不在能力域再写，放在能力域就不在战场再写；另一方需要时写成需求或依赖，不重复安排人和人日。
- **读别的 RU 资料里写到本战场的内容。** 比如产品现状里列出的客户差距、客户反馈、阻塞，同样是本战场要逐条处理的具体缺口。

## 4. 结果线（Mission）

- **Mission 是一条从头到尾的结果线**，通常对应 PO 的一个成立条件。先看业务成立需要哪几条不同的结果线，再定负责人和成功标准。
- **一条线不按阶段拆，也不按侧面拆。** 同一条线的准备、可用、使用、改善这些阶段，以及使用量、成本、稳定性、质量这些侧面，是这条 Mission 里的 Task 或成功标准，不各自成为 Mission。例如“内部调用进入日常使用”和“内部调用降低成本”是同一条线：降本写成这条 Mission 的一条 P1 成功标准或一个 Task。
- **数量跟着结果线走，不定指标。** 战场常见 3–5 条，能力域常见 1–3 条，一个人负责的 RU 常见 1–2 条；这些只是常见情况，不要凑数。同一个人在同一个 RU 负责 3 条以上 Mission，默认合并到 2 条以内；只有每条的成果、用到的人、成败判断都不同时才保留，并在 analysis 里写理由。同一个人负责两条以上 Mission 时，逐条问：这两条是不是同一件事的不同阶段或侧面？是就合并；只有成果不同、用的人不同、可以分别判断成败时才分开。
- **拆开**：结果不同、负责人不同，或有需要单独确认的关键交付接口。**合并**：同一个人的同一条工作线、同一个目标下的相关工作。准备工作并入使用它的那条线。
- **持续职责单独成线**：项目协调、运维发版、周复盘这类持续工作，写成一条“支持工作”Mission，或放进相关 Mission 的 Task，写清必做的频率和触发条件，不硬写成一次性结果。
- **具体缺口变成具名交付物**：资料里点名的差距、客户反馈、阻塞、未签发的文件，逐条落到某个 Mission 或 Task，或在取舍里写“本月不做”。
- **跨 Mission 去重**：同一份实际工作只承诺一次、只计一次投入。

## 5. Task

- **档位**：每个 Task 也标 P0、P1、P2，不高于它所属的 Mission。同样大致三等分：P0 Mission 里，关键路径上的 Task（缺了它 Mission 就做不成、而且没有替代办法）标 P0，约占三分之一，其余分为 P1 和 P2；P1 Mission 下的 Task 分 P1 和 P2 两档；P2 Mission 下只有 P2 Task。不把 Mission 的档位整体照抄给下面所有 Task。
- **工作结果**：下一环节能直接用上的东西，比如一份经确认的方案、一个上线并能调用的接口、一张核对过的账表。写名词性的结果和它能被谁怎样用，不写动作。
- **负责人**：首选 Mission 负责人；只有资料写明这件事在别人职责里，才交给别人。
- **按交付物分，不按动作分。** 一个 Task 是交给别人或下一步直接用的一份东西。日历上一般 3–10 个工作日，人的投入一般 1–5 人日。人的投入不到 1 人日、又是同一个人接着做的，并进相邻的 Task；只有要交给另一个人时才单独成 Task。
- **数量**：一个 Mission 一般 2–4 个 Task。不套“首用—复测—再用—汇总”这类固定模板；验收和汇总只有确实需要单独的时间和人时，才写成单独的 Task。
- **停在 Task**：执行人拿到就能开始做，交付物、完成定义、投入和停止条件清楚，就停。需要更细的执行步骤时，由负责人按需生成 Activity。

## 6. 双向检验

1. **充分**：子项全部做成，上一层的结果就成立吗？不成立就补，或写明本方保证不了的条件。
2. **必要**：删掉一个子项，具体损失什么？没有实质损失就删掉或合并。
3. **唯一**：同一个结果有没有被两个 Mission 或两个 RU 认领？只保留一个负责方，其余写成需求和承接。
4. **做得成**：按 feasibility.md 检查人日、关键路径、依赖和余量。
