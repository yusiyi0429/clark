# 逐层质量标准：生成、审查与修正

依据 TKOS 知识库模板与 What Good／Bad Case 提炼，来源版本见 research.md。只应用本次相关层级，不要求一次生成整条链。质量规则进入生成与交付检查；模板示例不是当前业务事实或必选打法。

## 共用判断

- **结果与验收分开**：Outcome 写届时必须为真的状态；验收回答什么证据、什么口径足以判断状态成立。不能把「完成初稿」的标准写成「初稿完成」，也不能用「完整、合理、质量好」代替可判依据。
- **证据与因果匹配**：方案存在只能证明准备；若承诺真实采用／客户价值，验收须能观察真实使用、判断或效果。没有证据时提出验证安排，不把准备结果自动升级为经营成果。
- **验收检验实际变化**：内部先分清交付节点（什么已交、功能已上线）与本层结果（交付后谁能做什么、什么问题改善）。日志、回读及提交回执用于核对事实，不代替质量和效果判断。逐项反问：“全部交付和记录都有，但内容错误、下游用不了或原问题没改善，能否仍判通过？”若能，补适合该层的质量、实际使用或效果口径及取得安排，不能降目标来通过。能力建设看是否有效支撑约定下游，不强套收入；Task产物可作为结果，但要满足下游使用所需的质量，不只验文件存在。对只承诺试用反馈的任务，取得真实反馈即可判断该结果，不擅自改成必须正面评价或业务增益。业务里程碑可以体现重要状态变化，仍不等于整项Outcome已达成；不要求每个中间节点证明最终客户效果。
- **标准是拆解产物**：已有正式验收约定优先；没有完整制度时，由技能据目标与上下文提出可验证的候选标准，握手时确认。真实未知的关键阈值保留具体核定事项，不编造数据，也不以制度缺失为由空着整个验收字段。
- **数字有来源**：业务要求、有效基线或已确认决策支持的阈值才能作为正式标准。合理的建议阈值标候选并说明依据；未知时保留待定，不从案例复制客户数、百分比或时长，不强迫所有结果量化。
- **验收与排期分开**：计划的时间边界必须有实际或建议日期，未知外部窗口及工时放依赖中待核对；验收中的频次、金额或持续时长等未定标准仍须如实保留。已有信息支持的证据对象、来源与通过／不通过口径立即写清。每项标准回答“查什么、怎样算成立、什么不算”；例如真实采用须能核对真实用户对业务对象的操作及实际使用结果，不能仅以演示、账号开通或内部测试通过。该层PO只写适当的结果验收，不为求清晰强塞Task步骤。证据存在而质量或效果仍未知时，明确不足以通过；缺关键阈值使结果无法判断时，写明谁需结合什么业务依据核定及受影响结果，不留一句笼统“标准待定”，也不擅自降低正式标准。
- **责任与边界可读**：唯一主归属、唯一结果 DRI 候选；协作者和消费者另外表达。Domain长期能力建设与Battlefield客户专项按结果责任区分，不按人员专业所属分配Mission；具体供给、专项交付和使用效果衔接，同一工作不重复认领或计投入。
- **同一结果同一责任口径**：成果和验收不能要求本项对全链路负责，责任边界却只负责接口；供给、消费和持续推进分清，保留必要联合核验。协调者不替专业负责人验收，技术负责人不自动拥有产品取舍权。
- **目标不被风险替代**：Outcome写清要取得的成果；未知条件、风险及应对分开。不得用“看情况／如果客户愿意”代替明确目标，也不保证本方无法决定的客户合作。内部可交付成果仍明确负责；正式目标不可兑现时提交取舍，不把查清风险当作目标成功。
- **完整定义和人读摘要同源**：摘要可短，但不改变承诺强度、范围、时间或标准。结构化定义可展开成功条件，不维护两份正式真相。目标、预计推进与实际 State／风险分开。
- **阶段验证不替代全月目标**：覆盖本期全部必要成果，试点、修正、扩展与最终验收分别有承接。试一个场景不等于全部场景完成；排不下时提交取舍，不自行缩范围。同人同主题的Domain建设和Battlefield专项分别拆实际工作，只去掉真正重复的供给，不省略客户适配或验收。
- **兑现能力有依据**：跨对象汇总实际执行者的可用时间，不重复计父子投入；工作投入与等待历时分开，检查共享瓶颈、关键窗口、返工和验收。未知容量／外部未确认的结果不能标成高确定性保底；详见feasibility.md。完成率不能靠弱化标准、删掉未完成对象或改成材料产出刷高。
- **表达质量独立检查**：业务分析完成后按reader-format.md整理正文。标题具体、每栏只答自己的问题、Plan不复制Card；精简前后核对范围、责任、日期、验收、承诺强度与未决条件。写短但读不懂或丢条件仍不合格，不用内部代号或“已明确”代替工作。

## LTO：长期结果，不是项目清单

| 检查 | 合格依据 | 常见缺陷 → 修正 |
|---|---|---|
| 目标形态 | 跨多个周期仍有意义的经营结果或能力状态 | 罗列系统／Mission → 写它们必须带来的结果 |
| 成功标准 | 能判断长期结果成立；定性／定量均可，有真实口径 | 抽象愿景或假精确 → 指明事实与证据；未决保留 |
| 时间与归属 | 六个月边界明确；Company、Battlefield 或 Domain 一个主范围 | 长期短期混写、多个主归属 → 分清对象与横向贡献 |
| 承接与逻辑 | Company 承接战略选择；RU 说明对公司结果的具体贡献；实现逻辑解释因果阶段 | 把未来 PO／Task 清单当实现逻辑 → 回到阶段条件与关键假设 |

## PO：本期为何做、关键节点与期末什么不同

- 一个 RU、一个月、唯一有效 Parent LTO@版本；不默认建 Company PO。
- Outcome 是本周期应达到的结果状态，不是 Mission 清单；按约定节点与周期边界验收，不重复摘要。周期月份不等于每个Mission／Task的截止日。
- 责任边界明确本RU负责到哪里、其他RU负责什么，不以时间边界或负责人姓名替代。
- 本期必要性由现状、复盘缺口、硬窗口与取舍说明；「一直重要」不足以证明本月必要。
- “存在必要性”同时回答长期目标卡点、本月阶段为何必须推进、所选路径与暂缓代价，以及相关RU交付共同带来的公司推进和剩余缺口。写少量有序要点而非重复成果或罗列全公司事项；有可验收的小成果仍需证明它值得在本期优先承诺。
- 预计 LTO 推进写到什么阶段／状态，不虚构实际进度或百分比，不平均分摊半年指标。
- 每个新增本月成果有当前瓶颈、本期优先理由和关键前提依据；长期终局不自动升级为月度承诺。范围更大不自动更好，范围更小也不自动更可靠；阶段选择按method.md检验，资料缺口按feasibility.md影响相应成果而非仅附尾注。
- 初稿须按LTO如期达成、上月实际结果及剩余差距提出足够推进，不把更容易交付误当正确阶段；DRI修订用于校准候选至可兑现，不是初稿刻意保守或无视硬约束的理由。
- 核心与延伸结果有业务依据，成熟程度分别明确；不能把全部长期条件平铺为当月必要条件，也不能擅自弱化已确认要求。验收能分别判断核心目标及延伸推进，不用核心通过掩盖延伸未完成。
- 实现逻辑只需 Mission 草图与因果关系；正式 Mission 另成候选，不提前塞 Task／Activity。
- 能力域供给结果与战场应用关系具体；只有技术测试时不得声称已证明经营效果。
- 多PO组合须检查公司阶段推进、缺口、重复及供给窗口；局部字段齐全不是整体充分。只测部分RU时，未确认的支撑不算既定承诺；一个月不要求达成六个月终局。该结论写进有关PO的“存在必要性”，不新增人读总览段。

## Mission Card 与 Mission Plan：独立结果与兑现打法

### 先选状态，再写验收

从本期有效目标、现状和责任判断需要哪种状态：可演示、可供使用、首次真实使用、多轮真实使用并迭代、持续采用，或可验证业务效果。这些是判断参考，不是所有项目必须依次完成的六个关卡。分别指出本期承诺、前置条件及后续阶段；接通数据／模型不等于真实使用，多轮使用也不自动证明持续采用或经营收益。能力建设可以承诺适当的能力状态，不强求每项直接证明收入。认为已确认目标过高时提交调整建议，不擅自降级。

核对我方直接交付、需要他人参与才能成立的结果、参与推动责任及实际控制范围。可试用版本、组织真实试用、取得反馈各有必要工作；不能把研发交付验收写成客户必然持续采用，也不能以“愿意就试”代替推进任务。外部条件与风险写入依赖／取舍，目标和责任保留明确。

当输入要求多轮真实使用时，约定有效一轮的证据：真实业务事项及真实参与者，实际讨论／判断／结果使用，形成反馈、材料变化或后续行动；后续轮次能够核对上一轮改进。保留可区分的事项或轮次记录，重复点击、模拟数据、研发自测或重复跑技术流程不自动算新一轮。数量、周期及参与规模由业务输入确定，不默认三轮，也不把每轮一定发生修改当作通过条件；无需修改时保留判断依据。

只有目标确实要求“接近人工”等比较型验收时，写清：同一事项、相同或可比输入；少量影响成果的比较维度；实际使用者或约定业务判断人；主要错误、人工补做、差距和改进记录。不杜撰90%等比例，不把人工答案当唯一真理，也不让标答泄漏进待测生成输入。一般交付用适合自身结果的验收，不全部改成人工比较。

Card 保留名称、DRI、RU、时间、Outcome、贡献／必要性、验收、责任边界。检查删掉该 Mission 是否出现明确 PO 缺口；没有独立端到端结果责任，就合并或降层。材料可以是合理的工作产物，但不自动成为经营结果。

额外检查：Mission组合是否只是项目阶段换名；是否把经营建模、组织落地等独立专业结果压成泛称准备工作；实际应用、客户推动与专业供给是否各有明确责任而非全部推给协调者。分类与人数不决定Mission数量，具体业务结果才决定边界。

Plan 检查：

- 核心路径解释如何兑现 Mission 结果，不抄 Activity 操作步骤。
- 关键取舍说明主动不做什么、为什么；不把一般原则当取舍。
- 关键约束／依赖只保留会改变打法、启动或通过的条件；写提供者、必要状态、需求时点及未满足后果。未确认供给不得承诺已可用。
- 工作关系分清硬前置、可并行及贯穿周期；不让上游整项完成成为所有下游工作的默认门槛。核对实际承载产品／流程、数据、权限及使用者，尤其是演示到正式使用或试行到制度运行的交接。
- 完整 Task 全景通过对象引用呈现：说明、唯一人的 DRI 候选、独立工作结果、质量标准、时间。相同 Task 不维护第二份 Outcome。
- 里程碑是可观察结果，关联必要 Task 与 Evidence；「举行评审」不是通过，「提交方案」不是客户采纳。
- 里程碑反映少量重要状态，可跨多个Task或出现在长期Task中间；不默认与Task同数量或固定三个。按method.md查实际状态，不只比较标题数量。
- 子项全完成仍可能没有兑现 Mission 时，补上联合交付／实际使用验证，或明确外部不确定性；不能靠细化文字宣称充分。
- 验收严而适度：首次应用检查真实完成一次约定工作及反馈；持续使用检查跨次业务活动和后续使用，不靠一次演示；自主运行检查不依赖团队代做与稳定责任安排。按正式本期承诺选用相应标准，不将三者全塞给每项结果；能力供给不冒充客户采用，未知次数／时段由相应负责人核定。
- 验收所需证据有取得安排：若承诺持续采用，计划要承接实际参与人、使用时间／频次、关键工作完成情况、用户反馈、人工补位和调整记录中必要的部分，写清谁收集、何时核对；不是只写“有日志”。按业务选择证据，不固定每周、次数或新增监控系统。涉及正式确认和写回时，核对对象、前置状态、有权动作与可查回执；资料只证明技术能力时不声称真实确认已发生。

涉及跨团队的Plan，按method.md核对结果责任、专业供给、实际载体和必要输入，保留联合验证；同一人可以承担其中多个角色，但不能因是DRI就推定包办。相关Mission共用交付只做一次，独立应用及交接不被去重，按实际人力汇总而非按文字相似度判断。

### 历史多维表模式的投影（仅选择该模式时适用）

PO 与 Mission 内部检查共同的成果贡献、存在必要性、验收标准、责任边界；人读必要性栏统一叫「存在必要性」，不重复已写的贡献。每轮主链为PO→Mission→Task子记录；Mission展示「核心路径、关键取舍、关键约束与依赖、里程碑」。短标题内容加粗，成果描述紧接第二行。稳定引用留在内部记录，正文用实际工作名称表达依赖；Task简洁投影及表格格式见reader-format.md。不因展示精简删除内部时间、边界、贡献关系、权利检查，也不把重复供给复制成多份承诺。

## Task 与 Task Plan：可负责的工作结果、最小必要编排

Task Card 八项齐全与否按当前输出范围判断；正式 Task 必须有独立可验收工作结果，不能拿任务说明、动作串或 Activity 清单替代。工作边界区分该 Task 与相邻 Task；准备可用和后续真实运行不是同一承诺。

Task说明应让该领域执行者看出具体工作对象、需要解决的专业问题及可用结果。若整套Task在无关行业也可原样套用，按method.md核回可用经验和专业内容；允许必要通用任务，不以堆术语、加长文字或强拆步骤充当专业性。

涉及统计、比较或筛选时，只检查相关计算口径：算哪些对象；每条记录代表什么及如何关联／去重；用哪个业务日期和时间范围（含端点）；筛选条件；公式及结果算到谁；并列、空集和缺失值如何处理。平均／比例须说明分子、分母各来自哪批记录，不默认不同集合可以相除。已有业务规则直接采用，不强加统一端点或并列规则。会改变答案的未定项，写清需要明确的解释及影响，暂停相应最终判断；已明确的部分仍可准备。没有数据不编答案，也不把已知规则一并写成待定。以上是条件检查，不给所有Task新增计算字段。

Task 若已可直接交给单一执行主体，在明确输入、权限、产出、验收与停止条件后止于 Task。否则形成必要 Activity／Checkpoint 全景：节点稳定 ID、类型、事项、单一主要主体、产出／判断、通过标准、必要时间、直接前置与退回。依赖不循环、引用存在、时间容纳关键链、人员与外部窗口有依据；不凭无环图证明资源可行。

Plan 只定义业务编排、自主调整与升级边界，Tool／Prompt／技术检索清单交 Runtime。普通风险清单不能替代「何时停止、向谁提交什么判断」。各节点完成还要核对 Task Work Outcome；未经明确授权，不自动把 Task 标 Done 或添加确认关卡。

## Activity：可独立执行，不大也不碎

- 只用 Agent Activity、Human Activity、Human Checkpoint；主要执行主体一个，协作者不等于共同执行主体。
- 拿到必要业务 Context 即可执行；「研究→人与之讨论→改稿→正式确认」隐藏独立交接，应按必要节点分开；「打开文件／复制文字」是工具步骤，应合并。
- 产出可识别、可供下游消费；标准不循环复述产出；输入有来源优先级，权限是外部前提不是 Card 自动赋予。
- Human Activity 承接人的必要互动，Checkpoint 承接真实判断权；人的普通参与不自动变成审批。Checkpoint 说明判断对象@版本、通过／退回证据与后果。
- 自主判断、启动／停止和 Handoff 可判；不影响承诺的执行调整允许自主处理，改变结果／标准／边界时提交相应权利人。

## 交付检查的表达

先修复可由当前信息解决的错误。剩余问题按「对象／字段 → 具体缺陷 → 对上层结果的影响 → 修正或最少待输入」列出，不只打分或宣称“合理”。区分结构合格、候选质量合格、条件可行、正式确认、执行可用、真实结果达成。业务因果未知时，结构合格仍不能证明效果。
