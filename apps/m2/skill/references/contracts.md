# 对象定义与口径

这是可离线使用的定义摘编，不是远端正式对象。内部来源、版本与差异见 research.md；业务新口径优先于此快照。

## 责任与目标

- Company LTO：公司六个月必须进入的经营结果／状态，承接战略选择；RU LTO：具体 Battlefield／Domain 六个月必须成立的结果。战场承担客户与价值创造责任，能力域承担能力建设／供给责任。
- PO：一个具体 RU、一个月、一个唯一且版本明确的 Parent LTO；不默认新增 Company PO。公司月度层可以展示 RU PO 组合。
- LTO 内容：责任范围、承接、Outcome、成功标准、时间跨度、实现逻辑；State 分开记录实际进展、风险、Issues。
- LTO／PO 的 Human View 是同一对象的简洁投影，不独立维护承诺；Structured View 展开正式定义，摘要不能改变范围、时间、标准或承诺强度。逐层质量要求见 quality-bars.md。
- PO 内容：责任范围与周期、上级 LTO 引用、本周期必要性、预计 LTO 推进、Outcome、成功验收标准、责任边界、时间边界、实现逻辑。责任边界区分本RU负责的结果与其他RU的供给或后续责任；预计长期推进不等于实际进展。
- 一个对象只有一个主归属与结果责任；能力域可同时支撑多个战场，以 contribution／dependency 关系表达。责任来自 RU／角色关系，不能凭名字相同推导有确认权。
- Mission主归属看所承担的结果，不看负责人的专业所在。可复用、长期建设的能力Mission归Domain；针对特定客户的演示、部署、专项规划等独立结果归Battlefield，允许由Domain的专业人员承接。客户专项不自动归Domain，支撑人员也不自动成为已确认Mission DRI；同一供给引用一次，专项应用与通用建设分别界定结果、验收和实际投入。
- 同一人可以同时承担同一专业主题的Domain Mission和Battlefield Mission，两者是不同工作，按各自结果生成不同Task及必要Activity。仅真正共用的供给对象作引用；不能复制整套任务，也不能因为主题相同就合并两项结果或省略客户专项。
- 组织责任图不是行政部门树。先区分公司、战场、能力域、能力域内专业分工，再确定对象主归属；不能因为内部职责有单独资料页就生成独立RU PO。RU DRI负责单元结果，Mission Owner名单说明已知承接人员范围，不证明某个新Mission已有唯一DRI或已获授权。跨RU承接需要具体责任依据，不能将所有Owner复制到每个Mission；“暂无”不等于没有工作或DRI拥有无限执行容量。
- LTO／PO的正式定义不因展示新增对象字段。资源与依赖检查保留在内部分析；用户模板含约束、路径或里程碑时，可在该阅读视图中呈现必要信息，不自动创建新的Plan对象或确认关卡。没有指定展示时，不追加独立附表。

## Mission Card

完整内部模板包括：名称、Mission DRI、所属 RU、时间边界、战役结果、贡献／存在必要性、成功／验收标准、责任边界。

用户明确要求本期产品核心卡片投影时，只取前五项；独立文本拆解默认使用本次所需的完整Mission候选，技能不受本期产品范围限制。核心卡片不含Plan，但承接与可验收性仍需在分析中核对。

历史多维表验证曾使用完整Mission及Plan五项：核心路径、关键取舍、关键约束、依赖task、全景里程碑，仅由Mission行填写。这是该表的投影约定，不是所有PO禁止展示下级计划；当前范围及模板优先，也不自动要求展开Task／Activity。

Mission 是兑现 PO 的独立端到端结果责任，不能按部门、功能列表、文件数量或项目阶段机械切分。名称是标识，Outcome 是必须为真的状态，标准是足以核验它的事实，不能互相替代。

## Mission Plan

正式定义：核心路径、关键取舍、Task 全景、Task 预期结果与质量标准、关键里程碑、关键约束与依赖。

Task 全景展示任务说明、唯一人的 Task DRI、工作结果、成功标准和时间边界；通过 Task 引用／投影呈现，不维护第二份内容真相。里程碑是一个或多个 Task 共同支撑的结果状态，不能写成「开会」或「提交材料」。共同里程碑可以有多个参与人，但整体 Mission 仍有唯一 DRI。

## Task Card 与 Task Plan

Task Card：名称、人的 Task DRI、所属 Mission、时间边界、贡献／必要性、工作结果、成功验收标准、工作边界。Mission Plan 的任务说明是一句工作概览；它不替代独立工作结果。

Task Plan：Activity 全景、执行顺序与直接依赖、时间安排、执行上下文与约束、治理点、异常与升级规则。治理点说明触发、Evidence 和 Decision Right；异常规则说明意外发生时的自主边界与升级。

阅读模板中的「Mission Plan」可指PO下属Mission的综合安排；单独Mission文档中的「Task Plan」可指Mission下属Task的安排。这些章节名沿用用户阅读约定：前者不新增正式PO Plan对象，后者的内容仍属于正式Mission Plan，不自动展开Task下的Activity。判断层级看父对象与子结果，不只看章节名；正式Task Plan仍是Task下的执行编排。

若 Task 已能直接由 Agent 执行，保留人的结果责任，执行主体可以是 Agent，停止新增 Activity；用简短执行安排说明输入、验收和交付，不创建空 Activity。若必要 Activity 未证明值得独立管理，可作为计划节点，不能自动升级为正式业务对象。

## Activity Card

Activity 是无需再规划的单一执行单元，类型为 Agent Activity、Human Activity、Human Checkpoint；Checkpoint 仍是 Activity 的计划角色。

基本信息：名称、类型、一个主要执行主体、所属 Task、必要时间边界、启动条件。业务执行定义：必要性、正式输入／业务依据及冲突优先级、执行事项、预期产出、可判断的成功标准、执行边界、自主判断边界、特有约束、完成后 Handoff。

不要把「Agent 起草→人 Review→Agent 改稿→人确认」塞进一个 Activity。Checkpoint 应有通过／退回分支，人类会议应是必要的 Human Activity。单一主要执行主体指谁负责完成该节点，不排除明确的协作参与者，也不让主持人独占参与者的判断权。Activity 的业务输入不保存技术检索路径、Prompt、API 或工具操作手册；必要技术上下文由执行环境另行组装。

## 确认与版本

当前用户明确的LTO确认：Company LTO 与各 RU LTO 在同一文档中由 CEO 一起确认，不设置 RU DRI 先承诺或先审批环节。组合承接可供讨论，但不能据 RU DRI 的意见记录代替 CEO 确认；同文档不合并各对象身份、责任或版本引用。CEO 确认 LTO 不代表结果已经达成，也不自动确认下游 PO。

当前用户明确的核心握手：CEO×RU DRI 确认 RU PO Outcome；RU DRI×Mission DRI 确认 Mission Outcome。下层规划由 Mission DRI 在其空间推进。上述双方握手规则不套用为 RU LTO 的额外承诺关卡。

2026-10-10用户进一步确认：每层只正式确认直接下一层成果及必要交付条件，保持对更下层的知情和修订建议，不因能看见就增加签字义务。CEO确认RU PO、可了解并建议Mission；RU DRI确认Mission核心成果、可了解并建议Task。建议不是直接改写下级已确认承诺；结果、标准、边界或接口实质变化仍由相应有权人确认。默认“握手一层、看两层”是阅读与管理半径，不是新权限授予；更深可见性服从实际授权。

计划与Card可以同源投影：从当前层的交付骨架开始，逐层补子项、依赖、时间和里程碑并回查可行性。未拆到底不等于没有计划；已有字段或一张图也不自动证明排期可行。Mission Plan与Task Plan是否合并尚未定案，继续保留各自定义，不以一个统一视图删除层级责任与计划语义。

双方握手是既有治理规则，不因为Activity需要一个主要执行主体就拆成两道新增审批。可以由一个明确的协作主持节点取得双方对同一Outcome版本的可追溯一致证据；主持人负责组织与记录，不取得双方确认权。某一方同意、会议举行或一方Checkpoint通过都不等于双方握手完成。若既有工作流本来就分开确认，沿用它的权利与版本规则，不另建关卡。

质量检查通过、正式Outcome确认、执行授权三件事分开：每个Checkpoint注明判断对象@版本、判断事项、Decision Right来源及范围、需看的Evidence、通过后的具体后果。Task草稿允许继续不能升格为上级Outcome已确认，Outcome确认也不自动授予数据访问或外部执行权限。

引用保留对象身份、版本、组件和来源；变更形成候选新版本与影响清单。历史确认不能授权新版本，草稿不得覆盖正式有效内容。已确认不代表已达成。
