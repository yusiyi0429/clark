# 分层输入与输出

以下是内部生成契约，按业务需要展开。先选择模式：单独Mission规划用下方三段式模板；公司／RU多轮拆解用轮次文档；简单问答直接回答；用户指定格式优先。内部字段不意味着全部展示。

用户指定最新模板时，仅提取结构与样式，不套用示例业务内容；按reader-format.md检查实际输出。上级Plan表摘要下级成果、负责人、日期及关键验收，不复制完整Card；模板把路径／取舍并入Card时不另加旧版Plan附表。以下是内部定义与无指定格式时的默认展示，不覆盖本次模板。章节命名与正式对象的区别见contracts.md。

| 入口 → 输出 | 必要输入 | 输出内容 | 本层验收重点 |
|---|---|---|---|
| Company LTO → RU LTO | 公司 Outcome／成功标准、战略选择、RU Mandate、当前状态 | Battlefield／Domain LTO 候选及横向贡献关系 | 每个 RU 结果贡献具体、主范围唯一、组合覆盖公司条件、能力供给与客户价值分清 |
| RU LTO → RU PO | 有效 LTO、上期复盘、当期状态／Evidence、本月取舍与资源 | PO 候选及本期必要性、预计长期推进 | 周期内关键节点与期末结果可判、阶段因果成立、不是均分指标、不重复既有成果 |
| RU PO → Mission Card | PO 有效版本、验收条件、已有 Mission、RU 边界 | 必要 Mission 候选及结果承接表 | 独立端到端结果、唯一 Mission DRI 候选、删去有缺口、联合结果无遗漏 |
| Mission → Mission Plan＋Task Card | Mission 结果／验收／边界、约束、已有 Task、资源与外部条件 | 核心路径、取舍、Task 全景、里程碑与必要依赖 | Task 组合足以支持 Mission；真实运行与集成验收被承接；Task 投影保持同一真相 |
| Task → 执行安排或必要 Task Plan／Activity | Task 结果／验收、正式业务输入、执行权限／环境、主体可用性 | 直接执行契约；必要时 Activity 全景与 Cards | 单主体直接可执行；人类判断有独立节点；停止条件和 Handoff 可判 |

## LTO／PO 草稿

对象ID／版本和状态留内部记录，正文按指定模板显示。LTO写责任范围、上级承接、Outcome、成功标准、六个月时间跨度、实现逻辑。Company与RU LTO在同一文档供CEO一起确认，不生成RU DRI先承诺节点。PO内部定义保留所属RU与周期、Parent LTO@版本、本周期必要性、预计长期推进、Outcome、验收、责任边界、时间及实现逻辑。人读输出按模板投影，不自动同时交付摘要和完整定义；约束与资源留内部分析，必要条件放模板现有字段，实际进展放State。

可先给简洁的人读摘要，再展开同对象的结构化定义；摘要不另写一套目标或弱化标准。预计推进与现有状态分开，阈值、Evidence 口径及未知项遵循 quality-bars.md。

PO人读“存在必要性”用少量有序要点承载：长期卡点与本月优先理由；路径取舍及暂缓代价；与相关单元交付共同推进公司目标的方式和剩余缺口。不是复制成果、另加新字段或在总览单列整体判断；内部仍保留Why This Period与Expected LT Progress Advance等正式语义。

## Mission Card

- 名称：
- Mission DRI：一名人或唯一角色候选；未确认注明。
- 所属 RU：
- 时间边界：
- 战役结果：
- 贡献／存在必要性：父条件、因果及删去缺口。
- 成功／验收标准：结果事实、Evidence 来源与口径。
- 责任边界：本 Mission 负责到哪里，其他对象负责什么。

只有用户要求本期产品核心卡片投影时只输出前五项，其余用承接／验收分析说明，不在本期产品新增字段或Plan。独立技能的完整Mission候选按上述完整模板形成。

## Mission Plan

以下是内部结构／完整定义展开，不是默认给人追加两张附表。

核心路径；关键取舍；关键约束与依赖。

| Task 引用 | 名称／任务说明 | 唯一人的 Task DRI 候选 | 工作结果投影 | 验收标准投影 | 时间边界 |
|---|---|---|---|---|---|

| 关键里程碑 | 必须成立的结果状态 | 关联 Task | 时间边界 | 相关人 | Evidence |
|---|---|---|---|---|---|

Evidence 是验收分析补充，正式字段以业务契约为准。

时间边界依据前置、下游窗口、历时与资源形成，不统一设周期末。Task用实际或建议开始日及预计结束日，Mission取Task首尾范围；所有日期字段填具体日期或范围，不写待定。依赖保留提供者、交付及交接条件、需要时点；未知条件及建议依据在路径／依赖中说清，不假称已承诺。里程碑与Task、Mission日期一致；详见feasibility.md。

历史多维表模式：PO与Mission填共同的必要性／验收／边界，仅Mission行另填Plan五项。只在本次选择该表模式时沿用，不限制新模板中的PO路径或下属Mission安排；不自动展开Task／Activity。

## 单独Mission文档：默认三段式

适用于规划／修订一份单独Mission文档。沿用有效目标和用户模板，不为填满字段编内容；简单问答、仅核心Card、公司／RU组合或指定格式不强套此模式。

### 一、Mission Card

| 字段 | 内容 |
|---|---|
| **名称** | **简短、具体的工作标题** |
| **成果描述** | 本期做成后的具体状态，区别交付、真实使用与业务效果。 |
| **Mission DRI** | 一名人；未知写唯一角色候选及待确认，不写团队共同。 |
| **所属责任单元** | 有效Battlefield／Domain名称。 |
| **时间边界** | 最早Task开始日—最晚Task收尾日；未细化时先给建议窗口，随后重算，不留待定。 |
| **存在必要性** | 为什么必须做、删掉会缺什么，不重复成果。 |
| **验收标准** | 有序列表写查什么、怎样通过，匹配本期状态。 |
| **核心路径** | 多个阶段用有序要点讲清任务如何组合、必要先后及可交叠部分；简单路径用一句话。 |
| **责任边界** | 本项负责到哪里；其他专业、载体、数据及参与推动由谁供给。 |
| **关键取舍** | 真实选择及暂缓代价，不写空泛原则。 |
| **关键约束与依赖** | 关键条件、提供者、需要时点及未满足影响。 |
| **里程碑** | 少量重要状态及其日期／需要窗口，不逐Task复述。 |

字段名加粗，内容不层层加粗，单元格顶端对齐。内容有多个独立成果、理由、分工或条件时用有序列表，不把它们挤进一段；单一意思用短句。此表汇集Card与必要Plan信息供阅读，不合并正式对象或改变确认权。

### 二、Task Plan

| Task／任务 | Task DRI | 成果描述 | 时间边界 | 验收标准 |
|---|---|---|---|---|
| **Task 1：具体工作标题** | 一名人或角色候选 | 可核对的工作结果。 | 实际或建议开始日—预计结束日；单日写日期 | 有多个标准时用有序列表。 |

任务数量按结果需要，不固定四五项。必要依赖、权限及停止条件放相关Card或验收，不因精简消失；不逐Task输出内部ID、启动判断或责任边界。甘特图是否展示及其样式统一按reader-format.md：用户取消图或指定模板未含图时不补加。图、表、Card及里程碑同源。此章节名表示Mission的任务安排，不是Task下正式执行编排，见contracts.md。

### 三、依据

简短列实际采用的有效资料（名称／版本／日期）和重要用户决定。候选日期的依据、关键输入缺口在相关条目说明，不堆分析报告。内部仍留输入及技能版本记录；产物前部的模型版本行按reader-format.md填写。没有多轮比较或用户要求时，不额外加整套轮次元信息、评分、审计、通用免责声明或意见区。

## Task Card 与执行判断

内部完整定义：Task 名称、人的 Task DRI、所属 Mission、时间边界、必要性、独立工作结果、成功验收标准、工作边界。正式对象必需字段不因人读精简而删除。

内部判断：可以直接执行／需要必要 Activity／待输入。可直接执行时明确正式输入、执行主体、交付、验收、权限、自主边界及何时停下或交给谁。涉及统计、比较、筛选时检查quality-bars.md中的计算口径；不把检查项变成固定新字段。

给人看的独立Task和Task列表均按reader-format.md简短展示，不逐项输出内部定义或判断记录。用户只问具体答案，先给答案和必要依据；要求工作安排时展示标题、负责人、成果、时间、验收。影响执行的所缺输入、依赖或权限在相关内容处说清，用户要求详细计划／审计时再展开。

## 必要的 Task Plan

| 节点 ID | 名称 | 类型 | 一个主要执行主体 | 执行事项 | 预期产出／判断 | 成功／通过标准 | 必要时间 | 前置 | Handoff／退回 |
|---|---|---|---|---|---|---|---|---|---|

计划级约束、自主调整边界、治理点与异常升级分开写。治理点必须说明判断对象@版本、判断事项、权利来源与范围、需看的Evidence，以及通过或退回后果，分别标明质量检查、正式Outcome确认或执行授权。Activity是否独立对象及每行成熟度放外层标记，不能因有计划行就声称已创建正式对象或已可执行。

## Activity Card

基本信息＋必要性；正式业务输入与优先级；具体执行事项；可识别产出；可核验停止条件；执行边界；自主判断边界；特有业务约束；启动条件；Handoff。Checkpoint 写通过／不通过条件与流向；技术运行手册另置。

## 交付附表

承接表使用 method.md 结构。假设表写假设、为何影响结果、验证方式／证据、责任候选、何时需判断、失败后的方案。依赖表写提供者、交付状态、消费者、最迟需求、风险及替代；资源表写必要投入、可用性来源、冲突、待核实与取舍。

内部汇总最少的人类判断：受影响对象@版本、问题、Evidence／缺口、备选、建议、Decision Right 或待决权利。给人看时仅列会改变当前结果或执行的判断，说明“谁需要决定什么、建议怎么选、何时需要”；判断人未知就说明，不臆造审批，也不把文字润色变成 CEO 待办。用户未要求，不自动追加全部附表。

同一RU文档按一级标题保留不同轮次，最新轮次在前；标题下依次只列资料版本、技能版本、模型版本、本轮优化四点。资料版本明确实际读了哪些类别及日期／版本，如LTO、上期复盘、最新现状、资源与已定取舍，不只写“基础资料”。模型版本按reader-format.md记录实际型号及推理强度，无法核实的字段如实标注。迁移后的资料版本不冒充已冻结输入；表达更新不改实际生成版本。旧正文与评论保留，不追加通用确认或意见说明。

人读PO／Mission Card按reader-format.md及最新指定模板呈现。必要性统一叫“存在必要性”，说明为何必须做及删掉后的缺口，不重复成果贡献；内部贡献关系仍检查。列宽、加粗及顶端对齐不在本文件另定义第二套规则。
