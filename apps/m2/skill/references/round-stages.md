# 产品逐层生成整轮候选

产品一次性生成整轮候选：从各 RU 的 PO 一直拆到 Task 和必要的 Activity，全部完成后再交给人沟通、确认和修改。过程中按层推进，每层都检查、修改。程序只负责按本页顺序调用、校验 JSON 结构、提供测量结果（字数、负荷、排期、上级要素覆盖），以及展示结果；拆解和检查的判断都按本技能。

**产品生成时以本页为准。** 本页只写流程和检查；对象和负责人见 contracts.md，拆解方法见 method.md，验收和各层标准见 quality-bars.md，容量与排期见 feasibility.md，表达与字数见 reader-format.md。整轮生成完再交给人确认，过程中不停下来等人逐层确认。

## 流程

```
0. 准备数据（程序从本体取数）
1. PO 层：各领域并行生成 PO → 交叉验证（三组并行）。必须修改的问题留到 Mission 层生成时一并改
2. Mission 层：各领域并行，先按 PO 层的问题改本领域 PO，再拆 Mission → 交叉验证（同时核对 PO 层的问题是否解决）→ 修改
3. Task 层：每个 Mission 单独拆 Task 和必要的 Activity，所有 Mission 同时进行；本层不单独交叉验证
4. 总校验：查全部类型（含 Task 层的必须修改类型）→ 修改，超出字数的字段一并改短
5. 精简：修改后仍超出字数或格式不合规范的字段，再改 1 遍
6. 输出给程序展示，人开始介入
```

每层交叉验证最多做 1 轮。每一轮都是“验证 → 修改”；修改后不再单独复验，留下的问题由下一层的验证或总校验接着查，最后仍未解决的随结果交给人。

## 交付标准

- **每个字段都写全，写出明确的结论。** 资料不足时写有依据的候选，并写明待谁、何时确认；不留空，不编造。缺字段的版本比带着待确认项的版本更差。
- **边界和条件在生成时就写清楚。** 写明本项负责什么、不负责什么、和谁交接；依赖未确认的客户窗口、审批人、确认人、到岗或供给时，标为条件候选，写出解除条件、最晚判断时点和失败后的选择。
- **表达简练，每个字段在字数上限内。** 生成和修改时都守住上限。

## 各层生成

PO 层和 Mission 层每个领域单独生成一份（一次模型调用），Task 层每个 Mission 单独生成一份；同层同时进行。每次只写自己负责的那份；其他领域、其他 Mission 的内容只作依赖和边界参考。

**PO 层**（输入本领域和其他领域的全部资料）：
1. 逐条列出本领域的上级要素：六个月目标的每一项要求（并列的多项逐项列）和上期复盘的每条未达成缺口。每条选一种处理：本月承接、本月暂缓（写理由和影响）、由其他领域承接（写领域 key）。写成 upstream 数组，程序会给每条编号（如 eo-U3），后面各层用编号引用。
2. 写出本领域的 PO（字段见 contracts.md）。上级 LTO 版本只用资料里明确的有效版本，没有就写来源和“待确认版本”。
3. 列出会和其他领域共同参与的具体事件或交付（如“某日客户首演”“第一次真实写回”），写明本领域负责哪一部分。

**Mission 层**（输入全部资料、本领域的 PO 和上级要素、所有领域的 PO，以及 PO 层交叉验证指出的本领域问题 poIssues）：
0. 先改本领域 PO：按修改的规则逐条处理 poIssues 里必须修改的问题，交回改后的 PO；认为不成立的不改，在缺口里写理由。其他领域 PO 里涉及本领域的问题，由那个领域自己改，本领域按改后的分工写。
1. 本领域标为“本月承接”的每条上级要素，以及其他领域标为由本领域承接的要素，都落到具体 Mission，并在该 Mission 的 upstreamIds 里写编号；暂缓的写进关键取舍。
2. 按 method.md 第 4 节划分和合并；时间按 feasibility.md 估完整周期。
3. 共同事件中本领域不是主负责方的，只写自己那部分或写成依赖。

**Task 层**（每次只拆一个 Mission。输入：这个 Mission 的全文、本领域资料和公司层、组织资料、本领域 PO、本领域其他 Mission 的简表、其他领域 Mission 的简表（标题、负责人、时间、成果），以及每人本月负责的 Mission 数 missionLoad。简表用于写依赖、避免和别的 Mission 做成同一件事；跨 Mission 的重复和冲突由总校验统一查）：
1. 为这个 Mission 拆 Task，全部 Task 完成后它的成果应当成立；收尾的汇总与验收按 feasibility.md 写成最后一个 Task。
2. Task 量按人分：一个人全月负责的 Task 一般不超过 12 个，这些 Task 分布在他负责的各个 Mission 里。按 missionLoad，本 Mission 给某人的 Task 一般不超过 12 ÷ 他负责的 Mission 数；Task 很大时更少，很小的可以略多。超出时先合并同一结果的步骤，再交给 Mission 里的其他人。
3. 每个 Task 的依赖（dependsOn）只写两种：本 Mission 内的前置 Task（写标题），或其他 Mission 的交付（写那个 Mission 的标题和要交的东西）；并写到什么程度就能开始。没有就留空数组。不依赖别的 Mission 内部的某个 Task。排期按 feasibility.md：默认错位并行，时长算上隐形成本，只有硬前置才首尾相接。
4. 返回本 Mission 的时间：取所有 Task 的首尾；和 Mission 原时间不同时在缺口里说明。
5. 按 method.md 第 6 节判断是否需要 Activity。

## 交叉验证与修改

问题分类：真重复、边界不清、放错地方、负荷、漏接上级要素、验收太松、条件未标、时间矛盾、排期失真、结构与表达、其他。

必须修改的问题类型：真重复、放错地方、漏接上级要素、验收太松、负荷、排期失真。

交叉验证分三组，同时进行，每组只查本组的类型：

- 第一组（跨领域与排期）：真重复、放错地方、边界不清、时间矛盾、排期失真
- 第二组（承接与验收）：漏接上级要素、验收太松、条件未标
- 第三组（负荷与结构）：负荷、结构与表达、其他

PO 层和 Mission 层只查必须修改的类型；Task 层不单独验证。总校验查全部类型：必须修改的类型要修改，其余类型列出供人参考。

**怎样判断：**
- **真重复**：两处承诺了同一个成果、按同一个验收计了两次。同一主题、同一负责人但结果不同的不算；同一事件中提供方和使用方各管一部分也不算。只是验收边界写重叠，归为“边界不清”。
- **放错地方**：客户专项写在了能力域，或长期能力建设写在了战场（标准见 contracts.md）。
- **验收太松**：按 quality-bars.md“验收”一节判断。
- **负荷**：同一人在所有领域合计，一般同期负责的 Mission 不超过 3 个，兼任多个 PO DRI 的更少，Mission 很重时 3 个以内也可能过载；Task 层同一人全月负责的 Task 一般不超过 12 个；Task 很大时应更少，很小的可以略多。并行是常态，不按同一周并行几个 Task 判断过载。处理按 method.md 第 4 节的顺序：先合并被拆散的同一目标，再改派，都不行才标为不可修改、交给人决定；不合并彼此无关的事。一个 PO 下的 Mission 多于 4 个时，也按“负荷”检查是否拆散了同一目标。
- **漏接上级要素**：程序给出的 upstreamFacts 中未被任何 Mission 引用的编号；或 Task 全部完成后 Mission 的成果仍不成立。
- **排期失真**：没有硬前置却首尾串行；时长只够做核心动作，没算调研、联调、上线、协作和返工；把同一人的工作排成单线程。程序给出的 scheduleFacts 中“串行却未写依赖”的 Task 对是重点线索。
- **条件未标**：依赖未确认的条件却没标为条件候选，或没写解除条件、最晚判断时点、失败后的选择。

**交叉验证**同时看本层所有领域和上一层的定稿。每个问题写清哪个领域（需要修改的那个领域的 key；两个领域都要改就各写一条）、哪张卡片、什么类型、问题、影响、能否通过修改解决。负荷、排期、上级要素覆盖以程序给出的统计（loadFacts、scheduleFacts、upstreamFacts）为准，不自己数；字数由程序测量，不报。资料缺失或冲突不能靠改稿解决，标为不可修改，写进缺口。只有 1 轮，尽量一次找全。Mission 层验证时先逐条核对 PO 层指出的问题是否已解决，未解决的照报；总校验同样先核对 Mission 层留下的问题。一句话说清，不复述卡片全文。

**修改**只处理被指出的必须修改的问题：
- 只改被指出的问题和直接牵连的内容，其余原样保留。只交回改动的卡片（按编号替换、新增或删除），程序按编号合并。
- 不靠删范围、降目标、放宽验收、把事情挪给别人却不说明来“消除”问题。
- 改完自查：有没有引出新的必须修改的问题，有没有超出字数。
- 认为某条问题不成立，可以不改，在缺口里写明理由。
- 下层发现的问题出在上层时（如两个 Mission 承诺同一结果、Mission 时间与其 Task 不符），可以连带调整上层：合并、拆分、改名或改时间，并在缺口里说明。调整后每个 Mission 仍须有 Task。

## 总校验

看整体效果：上级要素从 LTO 到 PO、Mission、Task 是否一路有着落（参考编号覆盖统计）；各领域合起来能否推进公司本期目标、还缺什么；前几层修改后有没有新产生的问题。Task 层没有单独验证，总校验要按“交叉验证与修改”的分组把 Task 层的必须修改类型查全：跨 Mission 的真重复、负荷（按 loadFacts）、排期失真（按 scheduleFacts）、Task 做完 Mission 成果是否成立。分组与问题写法同交叉验证，做 1 轮验证和修改，只修改必须修改的类型。修改时程序附上实测超出字数的字段（lengthFindings），同一次修改里一并改短，改法按 reader-format.md。

## 精简

总校验修改后，程序再测一次，附上仍超出字数上限的字段，以及要点没写成“**短标题：**正文”等格式问题。每个领域只改清单里的字段，改法按 reader-format.md。改 1 遍，仍超限的随结果交给人。

## 输出

全部层次的最终内容、仍未解决的问题和资料缺口，交给程序展示。
