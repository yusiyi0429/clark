# 产品生成整轮候选

产品一次生成整轮候选：各 RU 的 PO、单元计划、Mission 和 Task，全部完成后交给人沟通、确认和修改。Activity 不在整轮里生成，由 Task 负责人按需生成。程序只负责按本页调用、校验 JSON 结构、提供测量结果（人日负荷、日期、依赖对账、上级要素覆盖、字数），以及展示结果；拆解和检查的判断按本技能。

**产品生成时以本页为准。** 本页只写流程、每一步交什么、怎样检查；怎样拆见 method.md，各层写什么见 quality-bars.md，做得成见 feasibility.md，表达见 reader-format.md。

## 流程

```
0. 准备数据：上月复盘和反馈、当前进展、长期目标、人员、外部日程、跨领域供需，以及 CEO 给的本月方向（如有）
1. 战场：各战场同时写 PO、单元计划、Mission 和对能力域的需求
2. 能力域：各能力域同时写 PO、单元计划、Mission，并逐条回应战场需求
3. 检查与修改：三组检查同时进行 → 修改
4. 拆 Task：每个 Mission 单独拆，全部同时进行
4b. 全局对齐：人日超出容量的人，把他全部工作放在一起排先后，定哪些留在本月、哪些降档、哪些推到下月
5. 总校验与修改：查全部类型，超出字数的字段一并改短
6. 精简：修改后仍超出字数的字段再改 1 遍
7. 输出给程序展示，人开始介入
```

已完成的步骤可以先展示，标为“草稿·校验中”；整轮完成后才开放评论和确认。

每次检查的交叉验证最多做 1 轮：先验证，再修改，修改后不单独复验，留下的问题由后面的检查接着查。

## 每一步怎么做

**每次生成先写 analysis**（不展示，可以用技能里的术语想事情）；展示字段第一遍就写成人话（reader-format.md 第 0 条），技能术语不进展示字段。analysis 要想清楚：本月要跨过的一步是什么、依据是什么（有 CEO 本月方向时以它为准）、上月欠账是什么、哪些已完成或在进行、本月台阶怎么定、人手够不够。然后再写展示字段。analysis 不超过 600 字。

**1. 战场**（每个战场一次调用。输入：本战场全部资料、公司层资料、组织资料、其他 RU 的本月意图摘要（如有））：
1. 按 method.md 第 1、2 节推出本月要跨过的一步，定档位。
2. 写 PO、单元计划和 Mission（字段见下）。
3. 列 upstream：本 RU 六个月目标和上月复盘的要求，每条写“本月承接”（写承接它的 Mission 标题）、“本月暂缓”（写一句理由）或“他域”（写领域 key）。只列真正的要求，不把一句话拆成多条。
4. 列 demands：只写多个战场都会用的长线能力，写清需要哪个能力域在什么时候交什么、用来做什么。只为本战场做的事，即使要能力域的人来做（比如为王总首次使用做的先行版验收、为灯塔做的资料收集规范），也直接写成本战场的 Mission 或 Task，负责人写那个人，不写成需求。

**2. 能力域**（每个能力域一次调用。输入：本领域全部资料、公司层资料、组织资料、各战场写给本领域的 demands、各战场的 PO 和 Mission 标题）：
1. 起点是本领域本月要跨过的一步和长期目标，战场需求是另一项输入。
2. 写 PO、单元计划、Mission、upstream。
3. 写 responses：每条需求先问“它是不是只为这一个战场做的”。是的，回应“转回战场”，在 note 里写建议由谁做、哪天能做，不在本领域建 Mission，由战场把它写成自己的 Mission 或 Task。不是的，回应“接”“部分接”或“接不了”：接的写承接的 Mission 标题，部分接写接哪部分、哪天交，接不了写原因和影响。本领域自己的 Mission 也一样：主要为某一个战场当下做的，不写在本领域。
4. 需要别的能力域交付时，写 demands（写法同战场）。

**3. 检查与修改**：三组同时检查全部 RU 的 PO、单元计划和 Mission，然后各 RU 修改。

**4. 拆 Task**（每个 Mission 一次调用。输入：这个 Mission 全文、本 RU 的 PO 和单元计划、本 RU 其他 Mission 的简表、其他 RU 的 Mission 简表、每人本月已排的 Mission 数）：
1. 按 method.md 第 5 节拆 Task。
2. 返回 Mission 的时间（Task 的首尾）。发现 Mission 写得不对，可以交回改后的 Mission，并在 gaps 里写明改了什么、为什么；不降档、不放宽成功标准。

**4b. 全局对齐**（每个人日超出容量的人一次调用。输入：这个人本月全部 Task（跨 RU，带档位、投入、依赖）、他的容量、全部需求和回应）：
1. 把这个人的全部工作排一个先后：P0 Mission 关键路径上的 Task 最先；其次是战场正在等的交付；再次是其他 P1；最后是 P2。
2. 从前往后装进容量，装不下的：P2 推到下月；P1 降为 P2 或推到下月；投入估多了的可以按实际重估，写理由。
3. P0 Task 装不下时不推，也不压低估计凑数，写进 decisionsForCEO：缺多少人日，可选加人、推迟哪个 P0，或改由谁做。
4. 每条改动写一句理由。只改这个人的 Task。

**5. 总校验与修改**：三组同时查全部类型，重点查跨 RU 的重复、人日负荷（按程序给的 loadFacts）、日期和依赖（按 scheduleFacts）、悬空需求、上级要素覆盖（按 upstreamFacts）。修改时把程序实测超出字数的字段（lengthFindings）一并改短。

## 字段

**PO**：title、owner、result（成果）、checks（成功标准，1–3 条）、contribution（对长期目标的贡献，一句）、done（完成定义，1–2 条）、parentLtoReference（上级 LTO 版本）。

**单元计划 plan**：path（关口序列，3–5 条，每条“**关口名（MM/DD）：**哪几个 Mission 共同支撑、关口成立时什么为真”）、tradeoffs（≤3）、dependencies（关键依赖）、risks（1–3 条，含应对）。

**Mission**：title、owner、tier（P0、P1、P2）、time（字符串“YYYY-MM-DD—YYYY-MM-DD”）、gate（“MM/DD 关口标签”）、result、why（贡献，一句）、checks（1–3 条）、boundary（1–2 条）、upstreamIds、route（一句实现路径）、risks（0–2 条）。

**Task**：title、owner、tier（P0、P1、P2，不高于所属 Mission）、time（同 Mission 的写法）、result（工作结果）、checks（完成定义，1–2 条）、effort（投入）、stop（停止条件）、dependsOn。

## 检查

问题分类：真重复、拆散、档位倒挂、放错地方、边界不清、负荷、漏接上级要素、验收太松、过度承诺、时间矛盾、排期失真、悬空需求、结构与表达、其他。

必须修改的问题类型：真重复、拆散、档位倒挂、放错地方、漏接上级要素、验收太松、过度承诺、负荷、时间矛盾、排期失真、悬空需求。

检查分三组，同时进行，每组只查本组的类型：

- 第一组（跨领域与排期）：真重复、放错地方、边界不清、时间矛盾、排期失真、悬空需求
- 第二组（承接与验收）：漏接上级要素、验收太松、过度承诺
- 第三组（负荷与结构）：负荷、拆散、档位倒挂、结构与表达、其他

**怎样判断：**
- **真重复**：两处承诺了同一个成果。同一事件里提供方和使用方各管一部分不算。
- **拆散**：同一条结果线按阶段或侧面拆成了几个 Mission，常见于同一个人在同一个 RU 负责两条以上 Mission（看程序给的 splitFacts）；或 Task 拆得太碎：人的投入不到 1 人日、又是同一个人接着做，或一个 Mission 超过 4 个 Task（看 scheduleShapeFacts 的 smallTasks、crowdedMissions）。改法是合并，阶段和侧面改成 Task 或成功标准，碎 Task 并进相邻的 Task。
- **档位倒挂**：Task 的档位高于所属 Mission；或档位没分出先后——全公司某一档明显多于三分之一或 P2 明显少于三分之一，或一个 P0 Mission 里 P0 Task 超过一半，或 Task 照抄 Mission 的档位（看程序给的 tierFacts）。
- **结构与表达**：用了要人再翻译的抽象说法（见 reader-format.md 第 0 条；程序会在 lengthFindings 里列出疑似的地方），或句子不通、重复。
- **放错地方**：主要为某个战场做的事写成了能力域的 Mission 或供给（看程序给的 placementFacts：只回应了一个战场需求的能力域 Mission；也要看能力域自己写的、贡献只讲某一个战场的 Mission），或长期能力写在战场；或把本 RU 上月的欠账推给别的 RU。放错的要写两条问题：一条给能力域，删掉这条 Mission；一条给战场，写清要加什么 Mission 或 Task、负责人是谁（可以是能力域的人）、哪天交。
- **漏接上级要素**：本月要跨过的那一步没有落到 Mission；或上月 CEO 点名的缺口没有着落；或程序给的 upstreamFacts 里没被引用的编号。
- **验收太松**：按 quality-bars.md“成功标准与完成定义”判断。
- **过度承诺**：一个 PO 下 P0 超过 2 条；P0 超出负责人人日；依赖还没就绪；或要求外部决定在本月发生却写成本方必达。
- **负荷**：按 capacityFacts，同一人的计划人日超过可用人日；或一人负责的 Mission 明显过多。同一个人只报一条，写给他投入最多的那个 RU。
- **时间矛盾**：依赖的供给日晚于使用它的工作开始日，或 Task 不在 Mission 时间内。
- **排期失真**：Task 一个做完才开始下一个，但后一个只要前一个的初稿或一部分就能开始；没有在等什么却晚开工；P0 Mission 的最后一个 Task 落在月末最后两个工作日，没留返工时间；已在进行的工作被重新排；时长没算隐形成本（看程序给的 scheduleShapeFacts：finishToStart、lateStarts、p0AtMonthEnd）。改法：能重叠的重叠，依赖改成“等初稿”或“等第一批”；P0 的关键交付提前，月末只留返工和复核。
- **悬空需求**：战场的需求没有能力域回应，或回应“接”却没有落到 Mission。

**每次检查**写清每个问题是哪个 RU（需要修改的那个）、哪张卡片、什么类型、问题、影响、能否通过修改解决。负荷、日期、依赖、覆盖以程序给的统计为准，字数由程序测量。资料缺失或冲突不能靠改稿解决，标为不可修改，写进缺口。一句话说清，不复述卡片全文。

**修改**只处理被指出的必须修改的问题：
- 只改被指出的问题和直接牵连的内容，只交回改动的卡片（按编号替换、新增或删除）。
- 不靠删范围、降目标、放宽验收、把事情推给别人来“消除”问题。降档要写理由。
- 修改时不新增“演示不算”这类通用排除条款，它们只在 PO 的完成定义里写一次。
- 负荷问题改不动时，给出删减清单（见 feasibility.md 第 1 节），写进单元计划的风险。
- 认为问题不成立，可以不改，在缺口里写理由。
- demandFacts 里写给本 RU、还没回应的需求，在修改 po 时补上 responses。
- handBack 里是能力域“转回战场”的需求：战场把这件事写成自己的 Mission 或 Task（负责人按 note，可以是能力域的人），并从 demands 里删掉这条需求。

## 输出

全部层次的最终内容、仍未解决的问题和资料缺口，交给程序展示。
