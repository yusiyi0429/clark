# 给人看的拆解文档

目标：负责人能快速看懂要做成什么、谁负责、何时交付、怎样验收。不是追求最少字数，而是用最少必要表达保留准确业务含义。

## 范围和格式

- 简单问题先答结果和必要依据，不铺完整卡片或流程。按用户当前交流语言写；必要术语和指定字段名保留，一件事只用一个名称。
- 本次明确要求／最新指定模板优先于包内默认格式。读取实际模板的章节、列数与列宽、字段顺序、列表、加粗及顶端对齐；模板案例不是本次业务答案。
- 无指定模板的单独Mission按templates.md写「Mission Card、Task Plan、依据」。轮次文档最新在前，旧正文与评论保留；轮次标题下依次仅写资料版本、技能版本、模型版本、本轮优化，每点一句。资料版本列实际读过的类别及日期／版本；整理表达不冒充重新拆解。
- 不为显示分析而加栏、加表、加总览或意见区。用户要求详细分析／审计时才展开相关内部记录。

## 模型版本记录

每次生成或修订拆解产物，在前部说明中写「模型版本：具体型号；推理强度：实际值」。轮次文档放在技能版本之后；单独PO／Mission等产物在正文前简写这一行，不因此扩成整套轮次说明。简单问答不强套产物格式。

- 型号使用运行时明确提供的实际模型标识，不能只写“ChatGPT”“GPT”或供应商名称；推理强度保留实际配置值，如`high`，不要误写成`hight`。
- 依据本次调用记录或运行环境明确暴露的执行元数据填写；不能从默认配置、历史轮次、示例或自我推测反推。哪个字段无法核实，哪个字段写“未提供／无法核实”；模型不支持该设置时，仅在有依据时写“不适用”。
- 起草与修订确实使用不同模型或推理强度时，在同一行分别注明；仅排版改动保留原生成配置，不把当前模型追记为原作者。历史配置没有记录时不补猜。
- 对比实验分别记录各组实际配置；型号或推理强度不同，必须说明不能把差异直接归因于技能。配置相同也不代表资料、调用机会等其他变量已排除。

## 分析完成后再整理表达

先按method.md、quality-bars.md和feasibility.md确定候选结果、分工、标准与安排，再整理正文。不要为了写短而提前省略分析，也不要把分析过程、评分或检查清单搬进正文。

1. **先说具体结果。** 短标题说清动作与对象；成果描述写做成后的状态。不用“已明确”“形成闭环”“具备可执行条件”代替具体工作，不把动作完成当经营成功。
2. **一句只讲一个主要意思。** 明确人／对象和具体动词。独立的多项成果、验收、理由、分工或条件用有序列表，统一为 `1. **短标题：**说明`：短标题点明这一项的具体主题，冒号后正文不加粗；不把整句加粗，不用“事项一”等空标签。相关因果留在同一点，不按逗号机械拆点，不为凑点数拆句。日期、姓名、单句成果及里程碑短标签不强套列表。结构化输出用字符串数组，每项写 `**短标题：**说明`，序号交给界面生成，不能拼成长段。中文阅读长度按下节字段上限检查，不照搬英文词数或语法限制。
3. **每栏各司其职。** 成果＝做成什么；存在必要性＝为何本期必须做及其目标衔接；路径＝怎样组合与先后；关键取舍＝选什么、暂不做什么及代价；验收＝查什么、怎样通过；边界＝本项与相邻工作分别负责什么。必要性只简述选择理由，详细取舍放关键取舍。必要对象引用可重复，整段解释不能跨栏复制。
4. **总览短，Card准。** 上级Plan表摘要下级成果、负责人、日期与关键验收。成果通常一句话，验收留影响通过的关键条件，不搬入完整Card；详细标准在对应Card／依赖保留。没有下级明细时，摘要须足以支持本次判断，不能把必要内容删到无处可查。
5. **删重复，不删含义。** 路径将交接、并行与必要条件融入对应阶段，不另附补充条件；跨阶段约束放约束与依赖。核对精简前后的范围、责任、日期、验收、承诺强度和未知条件；“首次使用”不能变“持续采用”，“候选”不能变“已确认”。

用具体内容替代黑话：
- “承接父PO、形成闭环” → 帮助哪个目标、谁交什么、之后谁处理。
- “组合充分性不足” → “这些任务都做完，客户仍可能没使用；还要检查实际使用记录。”
- “待补Context／Handoff／Decision Right” → 缺哪份资料、交给谁、谁需决定什么。

专业术语、数字、阈值、公式和必要例外不能模糊成“做好、合理、可用”。未知项在受影响字段说明具体缺口及影响，关键限制不只藏在内部记录。同一未决事项在最合适位置完整写一次，其他位置只作必要引用。不得以删除不确定性制造简洁或确定性。

## 字段字数上限

以下是面向人的拆解正文默认上限，不是写满的目标；用户明确指定其他上限时按本次要求。内部分析与追溯记录不受这些展示上限约束，也不能借此额外输出长附录。

| 内容 | 上限 |
|---|---:|
| Card短标题、分点短标题 | 12字 |
| 成果描述／工作结果／预期产出 | 每字段100字 |
| 存在必要性、责任边界、核心路径、关键取舍、约束与依赖 | 每字段合计150字，每点50字 |
| 验收标准 | 每字段合计200字，每点50字 |
| 上级Plan中的下级成果摘要 | 每个下级50字 |

计数采用去掉Markdown格式标记、列表序号与空白后的可见字符数；汉字、英文字母、数字和标点各计一字符，分点短标题与正文都计入该点和字段总量。保留正式对象名及必要专业术语，不为了12字上限改名或造缩写；正式名称超长时保留，并按例外检查。

超长先删除重复、空话与无关解释，再改为短句。总览只留摘要，已有下级Card保留具体标准，必要引用必须能定位。不得直接截断、为绕上限增加字段、机械拆成更多Task，或删除业务范围、质量阈值、责任、日期及关键风险。精简后仍无法安全满足时，保留最短的完整表述，在交付检查中指出具体超长字段及必须保留的理由，不将其判为达标；先建议调整现有结构，不擅自增加附表或逐字段免责声明。

## 表格和日期

- 默认PO字段列加粗；RU轮次三列Mission表前两列加粗。两列Card加粗字段名，五列Plan加粗任务短标题。指定模板覆盖默认样式；所有单元格顶端对齐。
- Card名称／短标题加粗，成果描述接下一行／下一字段。必要性统一叫“存在必要性”，不重复成果贡献；短标题不加【】。负责人写一个姓名；未明确派工但职责资料足够时提出最适合的具体人选，信息不足时才写唯一角色候选，候选状态不冒充已派工。
- 名称与编号按指定模板；无指定时用具体标题，不用内部代号代替工作。Mission标题下不放Parent、主归属、内部ID或版本链；责任边界只写分工，不写通用确认免责声明。
- 时间格必须放具体日期或起止范围，不留空、不写“待定／待确认”，不全部设月末。Task填已记录的实际开始日＋预计结束日；未开始则填建议起止日。Mission取其Task最早开始日到最晚收尾日，未细化Task时先给粗排期，细化后重算。未知客户窗口、容量与工期不阻止给建议日期，但推导、假设、核对人及不满足时的处理写在现有路径／依赖／依据，不把建议冒充已预约或正式承诺。PO仍保留有效周期边界；各投影日期同源。
- Task默认五项：标题、负责人、成果、时间、验收。任务名称加粗，正文仅分点短标题加粗，不整段加粗；不另列内部ID、直接前置、责任边界或启动判断。影响执行的输入、权限和停止条件放相关成果、验收或Mission依赖。正式内部定义仍检查。
- 完整Plan无指定格式时默认给当前层紧凑甘特图／着色时间矩阵；简单问答、纯目标候选、用户取消图或指定模板不含图时省略。图与Card／任务表同源，未定节点和建议安排不能画成已确认承诺；不重复里程碑表，不用图证明容量可行。

## 修订与交付前人读验收

先读用户当前版本，按method.md和revision-loop.md同步受影响的Card、Plan及已有图。未指定有效来源的实质冲突请求判断，不恢复旧稿；同步表达不授予改变正式承诺的权利。

业务检查后，用实际正文再检查：
- 只看标题和成果，能否说出本项要做成的具体事情？仍像“开展推进、优化提升”的改具体。
- 看负责人、时间和验收，能否知道谁交什么、何时需要、查什么才通过？关键未知是否就在受影响内容旁？
- Plan能否快速看出下级结果及衔接，不必在多个格子重复读同一段？每句话是否提供新结果、判断依据或必要条件？无作用就删。
- 精简前后的范围、责任、日期、验收、承诺强度和未决条件是否一致？有变化就恢复或提出明确变更，不当文字整理。
- 章节、列数、字段顺序、列表、加粗和对齐是否实际符合最新模板？不只核对标题。
- 分点是否为“序号＋加粗短标题＋普通正文”？字段总量和单点长度是否满足上限，例外是否确有必要且已记录？不能靠删关键条件或重复拆点刷通过。
- 当前层模板的必填字段是否齐全？空字段区分原资料缺失、生成漏项和显示漏项，不一律写“数据不足”。确实没有额外取舍或依赖时，简写判断依据；资料未知时写具体缺口和影响，不编造填满。不适用于当前层的字段不填写，也不按漏项处理。
- 产物前部是否记录实际模型型号和推理强度？未知是否如实标注，修订是否保留原生成信息？
- 所有时间边界是否为具体日期，Mission是否等于Task首尾范围？日期变化是否同步上下游及里程碑，未确认的外部窗口是否只作建议而非事实？

CEO等负责人原稿可作表达样本，学习具体对象、业务判断和句子结构，不直接迁移人员、日期或答案；盲测仍排除同案例既有PO／Mission。作者改稿检查不等于独立读者测试，字数减少不等于质量提高。
