# 表达与字数

目标：负责人很快看懂要做成什么、谁负责、何时交、怎样验收。用最少必要的文字保留准确的业务含义。先按 method.md 等完成分析，再整理表达；不为写短而省略分析，也不把分析过程、评分、检查清单写进正文。

## 写法

1. **先说具体结果。** 标题用简短的名词短语点明做成的结果（如“架构路径采纳”“首个客户部署”），不写成“让……”“完成……”的长句；成果写做成后的状态。不用“已明确”“形成闭环”“具备条件”代替具体工作。
   “条件候选”“推断”“待确认”“建议”等标注写在约束与依赖或责任边界里，不放在标题、成果和里程碑里；成果和标题只写结果本身，读的人先看到要做成什么。
2. **一句只讲一个意思。** 写明人或对象和具体动词。多项成果、验收、理由、分工、条件写成要点，每个要点是“**短标题：**正文”：短标题点明这一项的主题，冒号后的正文不加粗。结构化输出用字符串数组，每项一个要点，序号由界面生成。
3. **每个字段只回答自己的问题。** 成果 = 做成什么；存在必要性 = 为何本期必须做；核心路径 = 怎样组合和先后；关键取舍 = 选什么、不做什么、代价；验收 = 查什么、怎样算通过；责任边界 = 本项和相邻工作各负责什么；约束与依赖 = 需要谁在何时提供什么。标题不加日期、对象前缀或重复的领域名称；日期、验收、分工写在各自字段。
4. **同一件事只完整写一次**，其他地方需要时简短引用。上级 Plan 只摘要下级，不复制完整 Card。
5. **删重复，不删含义。** 精简前后的范围、责任、日期、验收、承诺强度和未知条件必须一致：“首次使用”不能变成“持续采用”，“候选”不能变成“已确认”。

用具体内容代替术语堆砌：“承接父 PO、形成闭环”改成帮助哪个目标、谁交什么、之后谁处理；“待补 Context／Decision Right”改成缺哪份资料、谁需要决定什么。数字、阈值、公式和必要的例外照写，不模糊成“做好、合理”。未知项写在受影响的字段旁，说明缺什么、有什么影响。

## 字段字数上限

上限不是写满的目标。用户明确指定其他上限时按用户的。

| 内容 | 上限 |
|---|---:|
| Card短标题、分点短标题 | 12字 |
| 成果描述／工作结果／预期产出 | 每字段100字 |
| 存在必要性、责任边界、核心路径、关键取舍、约束与依赖 | 每字段合计150字，每点50字 |
| 验收标准 | 每字段合计200字，每点50字 |
| 上级Plan中的下级成果摘要 | 每个下级50字 |

每个里程碑写成“MM/DD 结果标签”：一个日期，空一格，再写不超过 10 字的结果状态（如“10/23 首次真实调用”）。不写日期范围、“前／后”或括号备注；日期是建议的或待确认的，在约束与依赖里说明。计数按去掉格式标记、序号和空白后的可见字符，汉字、字母、数字、标点各算一个，短标题计入该要点和字段总量。

超长时先删重复、空话和解释性措辞，再改成短句。不截断，不删范围、阈值、责任、日期和关键风险，不为凑字数增加字段或拆出更多卡片。正式对象名确实无法缩短的保留原文，并说明理由。修改补充内容时同步删减，不让字段越改越长。

## 交付前自查

- 只看标题和成果，能说出这项要做成的具体事情吗？
- 看负责人、时间和验收，能知道谁交什么、何时要、查什么才通过吗？关键未知是否就写在受影响内容旁边？
- 每句话是否提供了新的结果、依据或必要条件？没有作用就删。
- 要点是否都是“**短标题：**正文”？每个字段是否在上限内？
- 精简前后的范围、责任、日期、验收、承诺强度和未决条件是否一致？
