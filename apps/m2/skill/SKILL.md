# TKOS-Decoding · 战略解码

版本 2.0.2，规则核对日 2026-10-15。

把目标拆成必须做成的结果，再安排谁负责、交什么、怎样判断做成、时间和人手是否够。方法是：本期重点与成熟程度 → 结果成立的条件 → 当前缺口 → 最少必要的子结果 → 组合检验 → 容量与时限检验。拆出来的是结果组合，不是动作清单。

## 核心原则

1. **从结果反推，不从容易做的事出发。** 先问长期目标要按期达成，本月必须跨过哪一步，再定 PO 和 Mission。从现成工作改写出来的计划，容易全都能交、却推不动目标。
2. **每个结果只有一个负责人、一个归属。** 负责人写名单中的一个具体姓名。客户专项放在该客户战场，长期能力建设放在能力域。共同负责等于没人负责，放错地方会让同一件事被重复承诺或漏掉。
3. **验收要证明结果真的发生。** 交了文件、开了会、上了线，只说明交付了；要看下游是否用上、问题是否改善。验收太松，月底就无法判断目标是否达成。
4. **上级要求逐条有着落。** 六个月目标的每项要求、上期复盘的每条缺口，都要承接到具体结果，或写明暂缓及原因。静默漏掉的要求，没人会在月中想起来补。
5. **按实际人手和真实节奏排期。** 同一个人只有一份时间；工作常常并行、交叉推进，任务时长要算上调研、联调、上线、协作和返工。排得太理想，计划一开始就落后。
6. **不交白卷，也不编造。** 信息不全时照样写出明确的结论：按现有依据做出判断，同时写明依据的假设、待谁在何时确认。只写“待定”“资料不足”的字段等于没写，读的人无法据此讨论；把假设写成事实，后面的判断都会建立在错误上。

## 聊天中使用

1. **确定入口。** 用户要拆哪个对象、哪个版本、拆到哪一层，是起草、审查还是修改。可以从任意中间层开始，只补齐影响本次拆解的上级目标、现状、责任和依赖。用户只问一个具体结果时，直接回答结果和依据。
2. **按 method.md 拆解，按 feasibility.md 排期，按 quality-bars.md 自查。**
3. **按 reader-format.md 整理表达**，需要文档格式时按 templates.md。
4. **修改用户已有版本时**，先读当前正文，只改用户要求的部分和直接受影响的内容，按 revision-loop.md 处理。

## 边界

- 本技能只产出候选和待决事项，不创建正式对象、不派工、不改确认状态、不发消息、不写外部系统。这些动作由具体工作流在已有授权下完成。
- 确认、执行完成、验收通过、经营结果达成是四件不同的事，分开表达。
- 本次明确的业务决定优先于本技能的默认做法；资料之间的实质冲突无法用有效决定消除时，保留双方，交有权人判断。
- 维护本技能时先读 [MAINTAINING.md](MAINTAINING.md)。
