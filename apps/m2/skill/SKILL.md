# TKOS-Decoding · 战略解码

把目标拆成必须做成的结果，再安排谁来做、交什么、怎样判断做成、时间和资源是否够。内部方法是「本期重点与成熟程度 → 结果成立条件 → 缺口 → 必要子结果 → 组合验证 → 容量与时限检验」，不是把目标改写成动作清单。版本 1.5.12，规则核对日 2026-10-13。完整分析与人读表达分开检查；精简不能改变业务含义。规则更新本身不证明业务效果。

## 规则如何取舍

- 本次明确范围与有效业务决定优先于历史阶段约定；授权不因模板、评论或本技能而扩大。业务资料的实质冲突无法据有效决定消除时，保留分歧，不自行选边。
- 正式对象定义看contracts.md，业务判断看quality-bars.md／method.md，时间与资源看feasibility.md，反馈变更看revision-loop.md；人读呈现以reader-format.md为单一入口。模板只决定展示，不更改对象、责任或确认权。
- 本次明确格式与最新指定模板优先于包内默认样式。历史多维表投影、旧产品五项Card及评测预期仅在用户选择该模式时适用，不覆盖当前模板。图、附表和完整字段按需展示，不是为了“完整”必须附加的正文。
- 先检查结果、承接和可行性，再独立整理表达，最后核对范围、责任、日期、验收、承诺强度和未决条件未变。不向读者展示分析步骤。

## 进入任务

先确定入口对象、有效版本、拆到哪一层，以及用户要起草、审查还是修订。可从任意中间层调用；依据材料能支持的结果和用户需求决定起点与终点，不按行业或材料长短决定层级。只补齐影响本次拆解的上级结果、责任边界、当前事实、证据与必要依赖，不强制重跑整条链。用户只问一个具体结果时先答结果和必要依据，不强制生成卡片。

完整链：Company LTO → Battlefield LTO／Domain LTO → 各 RU PO → Mission Card → Mission Plan＋Task Card → 必要的 Task Plan／Activity Card。RU 包含战场和能力域；Domain 对 Battlefield 的贡献与依赖是横向关系。对象只有一个主归属，横向支撑可有多个目标，不复制成多份承诺。

战场拆完整业务成果及取得成果必需的专项支撑。Mission按结果责任归属，不按执行人的专业所属归属：长期、可复用的能力建设归Domain；为特定客户交付的演示、部署或专项规划等，若形成独立战役结果，归Battlefield，由相应专业人员承接候选。两类工作衔接具体交付、验收与需要时间，同一实际工作不重复承诺或计工时；细则见method.md。

同一人、同一专业主题，不等于同一件工作。Domain能力建设与Battlefield专项有不同结果、Task及必要Activity，应分别从各自Mission推导，不复制整套任务，也不为“去重”吞掉专项工作；只有实际共用的供给才引用同一对象。

拆公司／RU目标或提出责任人候选前，先读取本次有效的组织责任资料，核对RU、RU DRI、Mission Owner范围及专业分工，不从文档标题或人员重名推定组织层级。词元云集任务使用[组织责任输入](references/organization-context.md)中的现行来源；其他公司使用自己的责任结构，不套用词元云集名单。职责子项不是自动新增RU，Owner名单不是具体Mission已派工，同人跨角色不增加可用人力。

阅读 [对象定义与口径](references/contracts.md) 与 [逐层质量标准](references/quality-bars.md) 中本次相关层级；阅读 [承接方法](references/method.md) 并执行其组合检验。生成或审查有期限的PO／Plan时，阅读 [兑现能力检查](references/feasibility.md)，执行跨对象容量与关键窗口检查；不能把未知写成确定可行。需要规范输出时读取 [分层模板](references/templates.md)。研究理由见 [研究与归因](references/research.md)，学习方法时可读 [经典方法与案例](references/classic-cases.md)；历史案例及评测答案不作为当前业务输入。

## 工作方式

本技能贯穿首次拆解、讨论中修订和握手后变更，不是一次性生成器。Agent工作流负责收集反馈、推进讨论与发起有权人的确认；每次拆解或修订调用本技能做结果判断、改稿与影响检查。反馈修订时必读[持续修订与握手](references/revision-loop.md)。本技能返回候选及待判断事项，不自行发送消息、发起正式握手或更改确认状态。

1. 分开列出正式有效输入、实际状态与证据、用户决策、候选建议和待验证假设。来源冲突保留双方版本与影响；以用户当前明确口径为先。未知责任人、基线、资源或权利不能补成事实。
   目标与风险分开写：Outcome明确本期要取得的结果；外部不确定性进入风险、依赖与应对，不用“看情况／如果客户愿意”弱化目标。保留客户判断权，不虚构合作确定性；内部可负责的方案和准备仍须明确交付。不能兑现时报告缺口，由有权人决定取舍，不把风险查明或客户拒绝算作原目标达成。
2. 将父 Outcome／验收标准拆成少量可观察的成立条件，指出当前缺口；解释各条件怎样共同支撑结果。跨周期结果按因果阶段选择本月可证明的进展，不均分六个月指标。
   PO初稿先从LTO如期达成所需推进、上月实际结果与剩余差距反推，不以最容易完成的交付为起点。提出有实质推进力度的候选，再核对资源与依赖，交DRI修订并握手；不刻意保守，也不把大胆草案宣称为已证明可兑现。具体判断见method.md与feasibility.md。
   先区分本期必须成立的核心结果与拟推进的延伸结果，分别确定本期成熟程度和依据。不能把长期目标全部平铺成当月硬条件；也不能擅自把已确认的本期要求降成争取项。具体选择和资料不足时的处理见method.md；这不是新增Card字段。
   小范围验证决定推进顺序，不代替完整月度目标。按本期范围覆盖全部必要成果，先试一个场景再扩展；不能把首个试点通过当PO全部完成。资源排不下时保留缺口并提交取舍，不静默把整月目标缩成一次验证。
   PO的“存在必要性”用少量有序要点说明：长期目标当前卡在哪里、为何本月必须推进这一阶段；为何选这条路径而暂缓其他事项、暂缓影响什么；本PO与其他单元的交付一起如何推进公司目标、仍缺什么。先做组合检查再简写，不把详细分析堆给读者，不另在总览新增整体判断段。成果及验收仍在各自字段，预计长期推进保留内部正式口径。
3. 围绕缺口提出最少必要子结果，写明删掉后损失、边界、唯一责任候选、证据标准、时间及直接依赖。比较有实质差异的可行路径；不为凑数量拆层，也不把一份文件或一次会议自动升成 Mission。
   专业内容不能仅靠通用方法补齐。按method.md先从本次允许的负责人工作记录、历史复盘和相关实例中取得专业判断，再落实到实际任务及标准；经验不是已确认事实，盲测仍剔除同周期答案与截止日后进展。缺经验时提出具体专业候选及最少核对问题，不编造组织专有做法，也不退成整套“核对→编写→验证”。
   先识别谁的业务或工作方式要发生什么变化，再区分专业交付、采用与机制落地、跨团队结果推进；不固定分类或Mission数量。专业工作拆开后，仍须有人持续推动参与、交接、阻塞处理与反馈；协调者不包办专业结果。已有输入中的关键缺口须合理承接或明确暂缓，不能用“先保最小路径”无依据删掉架构、数据供给等必要建设；具体检查见method.md。
   先识别独立业务结果再切Mission，不默认套“准备→交付→跟进”。专业支持若有独立结果责任应单独承接；只有步骤、材料或部署动作则留在Task。负责人对所承诺结果负责到底，不把产品实际应用统统转给协作负责人，也不因其制作产品便默认拥有客户推动权限。
4. 双向检查：每个子项是否必要；每个父条件是否被覆盖；所有子项完成后父结果是否仍可能不成立。把客户采纳等未证实因果明确为假设，用真实验证任务承接，不声称逻辑已证明经营成功。
   验收由技能综合提出候选，不要求用户先给完整规章。文件提交、上线或开会只是交付节点，须检查它们是否产生本层所承诺的实际变化。每项内部区分交付节点与结果成立，反问“东西全交了，但仍没用，能否通过这份验收”；若能则补质量、下游使用或效果标准，不能降目标。能力建设验证可用及对下游的有效支撑，不强迫每项直接证明收入，也不强造新字段。通过口径与交付检查见quality-bars.md。
   成果、验收与责任边界须一致。涉及系统确认或写回时，按当前实际对象、规则、权限与回执规划，不臆造接口或确认机制；验收需要的真实使用与业务反馈记录必须有取得责任和时间。反馈归因先核对当轮实际输入，区分已给未用、原资料缺失、来源冲突和仅见于对标答案，不把后来的人工答案倒灌为盲测输入。
5. 对组合检查责任冲突、共同结果、外部依赖、资源占用和关键时限。月度周期不是每项的截止日：按跨RU／Mission／Task的直接前置与下游需要时间排先后，倒推最迟交付并正推最早可用，不能统一写月末；具体做法见feasibility.md。按实际可用工时而非人数估算，汇总同一人跨RU／Mission的负荷；工时与历时分开，计入等待、交接、集成、返工及验收。用历史可比实际结果校准估算，并检查共因风险。给出本月保底候选、条件候选及明确暂不做项；保底也须证据支持且覆盖相应父结果。未知容量写待核实，不捏造完成概率、不静默降低正式承诺。
   依赖只约束需要该交付的部分，不把全部Mission人为串行；识别可并行、分批交付与贯穿周期的工作。逐条检查等待是否必要，按具体可用交付与开始条件排错位并行，不能为了并行绕过授权、质量或同人容量。验收按首次应用、持续使用或自主运行等本期状态匹配，并核对真实承载产品／流程、版本、数据和人员条件，不能用更高成熟程度的标准无声扩张目标。
6. 需要下钻时形成 Mission Plan 与独立 Task 结果。Task已能由单个Agent在清晰输入、权限、产出、验收和停止条件下直接执行，就止于Task；只有仍隐藏多主体交接、正式人类判断或可独立管理的执行节点时才增加必要Activity。候选计划节点不冒充已可执行契约，后续要求超出Task结果边界时显式提出承接安排。

生成时将原则落实到内容，而不是加一段口号：先选本期状态（可演示、可供使用、首次真实使用、多轮使用并迭代、持续采用或业务效果），再分别写交付、参与推动和验收。多团队核对结果责任、专业交付、实际载体及数据供给；共用工作只认领一次，独立适配与联合验证不省略。排期从下游需要窗口反推、按资源正推；里程碑只留重要状态，不与Task一一配对。具体规则见quality-bars.md、method.md和feasibility.md，不新增固定管理字段。

## 输出与边界

先给可讨论的候选结果。承接、依赖、容量、权限与稳定ID用于内部检查和追溯，不自动全部写进人读文档。需要附表时遵循用户的交付范围；不得为展示分析而擅自加栏、加段或加说明。只输出本次所需层级，执行细节进入规划空间。

凡给人看的回答或文档，都先读并遵循[简洁阅读规范](references/reader-format.md)，执行其分点、字段字数上限与人读验收。超长先改写和去重，不截断，也不删关键条件。用具体对象、动作和结果替代抽象评价；每栏只回答自己的问题，总览不复制完整Card。人读内容与内部定义同源，不维护第二套承诺，不把检查过程输出成业务内容。

用户提供模板时，读取最新版本，按reader-format.md核对章节、表格、字段顺序和样式；模板只约束呈现，不提供本次业务答案。上级Plan表是下级Card的精简摘要，不整段复制；核心路径将交接和关键条件融入对应阶段，不再附一套重复说明。

无指定模板的单独Mission规划按templates.md组织「Mission Card、Task Plan、依据」：Card两列、任务表五列。完整Plan或多RU排期无指定格式时按reader-format.md默认附当前层甘特图；用户取消图或指定模板未包含图时不补加，不以缺图判失败。章节名Mission Plan／Task Plan不改变正式对象含义，详见contracts.md。所有时间边界填具体日期或起止范围，不留“待定／待确认”。Task已开始时采用有记录的实际开始日和预计结束日，未开始时给建议起止日；Mission取最早Task开始至最晚Task收尾，不默认贯穿整月。排期须考虑直接依赖、共享人员、交接和验收；外部窗口或工时未确认仍给可讨论的建议日期，在现有依赖／依据注明假设和核对人，不伪造已预约、已开始或已获承诺。详见feasibility.md。

修订先读取用户当前版本，按method.md同步受影响的Card、任务表及已有甘特图；无明确有效来源的冲突先指出，不静默选边，不改未获授权的相邻文档或已确认承诺。按feasibility.md分清启动阻塞、可在使用中优化的细节及需要人决定的承诺变化，让具备条件的部分及时使用，又不绕过关键质量或权限。

轮次文档按最新轮次在前排列；每轮标题下仅按顺序写资料版本、技能版本、模型版本、本轮优化四点。资料版本简要写清实际读了哪些类别（如公司／RU LTO、上期复盘、最新现状、资源与本月取舍）及日期／版本，不能只写“基础数据快照”。每次生成或修订拆解产物，前部说明均记录实际模型型号与推理强度，来源和未知项处理遵循reader-format.md；不将示例型号当作本次配置。缺输入快照如实说明；只改表达不能改写实际生成版本或声称已重新拆解。PO与Mission短标题加粗、成果描述紧接第二行；必要性字段统一叫“存在必要性”，不在此重复已写的成果贡献。内部承接与贡献检查仍保留。PO与Mission写责任边界，但不混入确认流程免责声明。

Nexus 起草；Company LTO 与 RU LTO 在同一文档中由 CEO 一起确认，不设置 RU DRI 先承诺环节。只确认直接下一层：CEO ↔ RU DRI 确认 RU PO Outcome，RU DRI ↔ Mission DRI 确认 Mission 核心成果及其必要验收、时间与交付接口，不要求签完下层Task／Activity计划。双方可以查看并提出更下层的修订建议；建议不自动改变已确认承诺，实质变更仍由该层有权人确认。默认握手一层、了解两层；更深查看依实际权限，不由本技能授予。Mission DRI 在自己的规划空间推进下层 Plan／Task，不把细节推入核心群；下层具体正式确认权未明确时列为待决。

计划自上而下逐层形成：先建立当前层的粗颗粒交付、依赖与时间安排，再细化子层并回查上层窗口及共享资源。不等Task／Activity全拆完才规划，也不等全图完成才让条件已满足的已授权工作启动。完整计划的Card、任务表、里程碑与甘特图取自同一份时间安排，修订逐项同步；画图不等于排期可行。细化Task后重新汇总Mission首尾并同步上级Plan；反馈改变Task日期时重算受影响Mission及下游。未知投入不伪装成可靠工期，外部节点也填写建议日期但保留未确认条件；负责人可据此提出修订，不能靠空日期回避规划。Plan对象是否合并不自行改定。

本技能不自动读取全部公司材料，不要求特定工具，不创建正式业务对象、派工、改确认状态、发送消息或回写外部系统；这些动作须由具体工作流承接既有授权。确认、执行完成、验收通过和经营结果达成都分别表达。

当必需输入缺失或冲突会改变结果、责任、权限或验收，先完成不依赖它的候选分析，明确哪些部分不能定稿；执行节点缺少权限、正式依据或必要判断则停在该节点。重复修订仍不能消除同一实质缺口时提交受影响对象、证据、备选与所需 Decision Right，避免无限展开。

交付前逐项用质量标准审查实际候选，并按 [行为验收](references/validation.md) 的改稿要求修正正文，包括原要求漏项、计算口径不清、阶段跳跃、准备替代结果、空泛验收、缺口只写尾注，以及黑话或无用展开。未知证据、未决阈值及不可控承诺如实保留；不要为填满字段编造。文件格式合格不能替代成果承接正确或真实使用验证。

有排期的拆解或修订，交付前必须执行feasibility.md第4节的排期门槛：PO覆盖本期完整月份，Task先估工作与等待并核对真正前置，Mission由Task首尾计算。存在Task时不得独立编写Mission日期；仅完成当前层时保留建议窗口，细化后重算。不能只靠模型自评或界面拉长横条通过检查。有本地脚本运行能力时，对最终结构化日期运行[scripts/validate_schedule.py](scripts/validate_schedule.py)，失败先修正文并复查；脚本仅验证日期结构，工期、并行与月度成果覆盖仍须人工式业务审查。未执行或无法运行检查时如实说明，不称排期检查通过。

更新技能时执行validation.md的版本回归检查：保留旧版，优先修改原规则而非层层追加；检查相互冲突及原有能力。未做同输入、同模型和推理强度的行为对照时，只报告规则及文件检查，不宣称新版本质量提高。

通用规则只固定判断方法，不固定案例人员、日期、使用轮数、Task／里程碑数量、载体或数据架构；不要求所有产品接完整本体、所有协作经Nexus、所有验收对照人工，或所有Domain做内部使用而Battlefield只做客户试用。产品负责人是否负责界面依实际分工，业务输入决定这些选择。1.5.0测试输入见[evaluation-planning-v1.5.md](references/evaluation-planning-v1.5.md)，仅在评测时读取，不将预期答案带入生成。
