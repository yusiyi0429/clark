# TKOS-Decoding · 战略解码

版本 3.1.5，规则核对日 2026-10-16。

## 月度计划是什么

月度计划是一个因果论证，加一组承诺：

- 本月要让什么发生变化，为什么这能推动长期目标；
- 靠哪几条结果线做到，每条线谁负责、什么时候过哪个关口；
- 每条线由谁在什么时候交出什么；
- 怎样算真正做到，而不是演示；
- 为什么做得成：人手、关键路径、风险和余量。

读的人打开计划，应当马上看懂五件事：公司目标被拆成了什么，本月要达到什么，要做成什么，通过什么去做，什么算真正做到。

## 八条原则

1. **从本月必须跨过的一步出发。** 看长期目标现在卡在哪一阶段、上月复盘和 CEO 反馈点名了什么、当前进展到哪里，推出本月必须跨过的那一步，这是 PO 的起点。资料里有 CEO 给的本月方向时，以它为准。不把六个月目标的字句逐条拆成本月承诺。
2. **每层只回答一个问题。** 总览回答“拆成了什么”，PO 回答“要达到什么”，Mission 回答“要做成什么”，Plan 和 Task 回答“通过什么去做”，完成定义回答“什么算真正做到”。答完就停，不在每层把所有问题再答一遍。
3. **结果在上，交付物在下。** PO 和 Mission 写什么状态发生了变化；Task 写下一环节能直接用上的工作结果。工作项不变成下一层的目标。
4. **承诺分三档，一定分出先后。** P0 做不成本月就算失败，P1 次之，P2 人手紧时最先让出，同一组工作大致三等分；P2 以下本月不做。档位只写在档位字段里。写进计划的每件事，正文都写成确定要做成的样子；前提、条件和可能做不成的原因写进风险或依赖。按就绪程度承诺，不按覆盖率承诺。
5. **具体胜过完整。** 资料里每条已知缺口、客户反馈、阻塞，要么变成具名交付物，要么明确写“本月不做”。
6. **“做成”只定义一次。** PO 写全局完成定义，下层引用；验收少而够用，数字门槛保留。
7. **一个结果一个负责人，按人日算得过来。** Task 首选 Mission 负责人自己做；只有这件事明确在别人的职责里，才交给别人。每个人的投入跨领域按人日汇总。
8. **一开始就写成人话。** 分析在不展示的 analysis 里做；每个给人看的字段，第一遍就按 reader-format.md 第 0 条写：简单、直白、精炼、准确，人一看就懂，不靠后面的检查来改。

## 聊天中使用

1. 确定入口：拆哪个对象、哪个版本、拆到哪一层，是起草、审查还是修改。只补齐影响本次拆解的上级意图、现状、责任和依赖。
2. 按 method.md 拆，按 feasibility.md 检查做得成，按 quality-bars.md 和 reader-format.md 写。
3. 修改已有版本时，先读当前正文，只改要求的部分和直接受影响的内容。

## 边界

- 只产出候选和待决事项，不创建正式对象、不派工、不改确认状态、不发消息、不写外部系统。
- 确认、执行完成、验收通过、经营结果达成是四件不同的事，分开表达。
- 本次明确的业务决定优先于本技能的默认做法。资料实质冲突、又没有有效决定时，保留双方，交有权人判断。
- 维护本技能前先读 [MAINTAINING.md](MAINTAINING.md)。
