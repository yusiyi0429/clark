# 个人记忆怎么召回：调研、实验与结论

分支 `feat/memory-recall`（从 `feat/memory-integration-v1` 的 f9bcdf4 拉出）。日期 2026-10-18。

## 一句话结论

把每轮的「按字面重合挑记忆」换成「快模型读本人记忆目录挑条目」。做法是：分诊用的那个快模型拿到本人全部现行记忆的目录（编号、日期、类别、标题、正文前 60 字），从里面挑出最多 12 条。偏好类每轮常驻。挑选和分诊同时跑，失败或超时就退回字面重合。

300 条记忆、79 条查询、每种方案跑 3 次取平均，结果如下：

- 召回率从 0.69 升到 0.94–0.96；
- 精确率从 0.25 升到 0.88–0.94；
- 干扰问题的误召回从 100% 降到 0%。

这套做法不需要新的基础设施，在约 500 条以内成立。超过以后的扩展办法见第 6 节。

## 1. 问题

现状（`personalMemory.ts` 的 `select`）的做法：本轮原话切成中文二字词，跟每条记忆算重合个数；偏好、做法和标题带「协作 / 沟通 / 表达 / 偏好」的条目，就算不重合也一律带上；总量限制在 8 KB。

10/18 的真实模型冒烟里，「还有哪些没定」对不上「还没想好……扩编」，「销售扩编」那条没有被选上。原因有两层：

- **换个说法就找不到。** 选取只看字面重合。
- **无关问题也会塞一堆记忆。** 「我们」「什么」这类常见二字词几乎每条都能重合，再加上做法类兜底，每轮固定塞进约 25 条。问量子力学也照样会带上。

（【官】为官方说明，【三】为第三方逆向。）

对天枢的含义：每人几十到几百条、每条几十个字，300 条的目录约 1.5 万 token。这正好落在「直接给模型看全貌」的范围内，向量库和图在这个规模上的优势用不上。人豪的设计（architecture.md 4.3、5.3）也定了本期不建向量库，并且要求「只给索引，按需展开」，和这里的结论一致。

## 3. 实验设计

全部代码和数据在 `.scratch/memory-recall/`，都是编的，没有用真实记忆。

**数据**
- 虚构人物林舟（远帆智能 CEO），记忆时间从 2026-08-03 到 10-15，共 302 条，其中现行 300 条：
  - 92 条目标条目由手写设计（`data/targets.mjs`）；
  - 210 条填充条目由 claude-opus-5-5 生成，覆盖 27 个话题（`data/fillers.json`）。
- 类别分布：想法 46、立场 62、未决问题 74、理由 31、做法 79、偏好 8。
- 设了 7 组被替代的说法：
  - 2 组已经正式标成 superseded；
  - 5 组没有标出（新旧两条都是现行），模拟后台提炼漏判。
- 话题 anchor 的写法故意不统一（如 `topic:渠道下沉`、`topic:县域市场`、`topic:下沉`），模拟提炼时自由命名。

**查询**：79 条，每条标注了必须召回的 gold 条目（`data/queries.mjs`）。

| 类型 | 条数 | 例子 |
|---|---|---|
| 1 换说法 | 16 | 「小地方的试点市场，我原来打算从哪类城市切进去？」（记忆写的是「县城样板」） |
| 2 只提上位概念 | 14 | 「渠道这块我目前的整体思路是什么？」 |
| 3 跨话题间接相关 | 16 | 「下季度要不要多招 20 个销售？」（相关的是现金、Q4 不扩编、人效、扩编方向未定） |
| 4「还记得我说过的 X 吗」 | 17 | 「我两个月前提过一个灯塔客户的说法，还记得吗？」 |
| 5 干扰（不该召回任何记忆） | 16 | 翻译、编程、常识；也有字面上沾边的，如「县城的房价」「美团骑手工资」「越南的历史」 |

**补标注（pooling）**：各方案选过、但不在 gold 里的条目，交给 claude-opus-5-5 逐条判 0、1、2，共 7,172 对，其中判为相关的 1,686 对。判为相关（≥1）的并入 related，只影响精确率，gold 不动。gold 条目也让它复核过，全部判为相关。

**规模**：每条查询的候选池按 50、150、300 抽样。300 条就是全集；50 和 150 条时 gold 必含，其余随机抽。1000 条是在全集上另加 702 条同人物、同话题的追加条目（时间铺到 3 月）。

**指标**
- 召回：gold 被选中的比例（字面方案的选中集合约 25 条，另列只看前 5 条的 R@5）。
- 精确率：选中的条目里，属于 gold 或 related 的比例。
- 干扰题误召回：干扰题选出了任意非偏好条目的比例。
- 旧说法当现行：只选了旧条目、没选新条目的次数，共 9 个陷阱。
- 延迟：选取这一步的 P50 / P90，在本机跑，经过网宿网关。
- 每轮 token：选取调用的输入和输出（含命中缓存的部分），以及装进上下文的估算 token 数。
- 每种配置跑 3 次取平均。少数参照配置只跑了 1 次，表里标「×1」。

**参比方案**
- a：现状，原样照抄 `select`。
- b：轻模型从目录里挑，网关上可用的快模型都试了。
- c：分层目录，先挑话题组，再在组里挑条目。
- d：向量。网关没有 `/embeddings`（实测所有路径都 404），改用本地 ONNX 的 bge-small-zh 和 bge-m3。
- e：混合，向量取前 20 或 50 条，加 BM25 取前 10 或 15 条，再交给轻模型重排挑选。

### 4.3 端到端（15 条查询，真实主对话运行时）

**怎么跑的**
- 用分支上的 `createPiConversationRuntime`：真实系统提示、真实工具、主答模型 gpt-5.6-sol，分诊用 terra。
- 把各方案选出的记忆放进上下文包，主 Agent 也可以调 `search_personal_memory`。
- 由 claude-opus-5-5 逐条判断：每条应当用到的记忆，回答里有没有体现；有没有把旧说法当现行；有没有硬扯无关记忆；有没有编造本人说过的话。判断时把助手手里的全部记忆都给它看。
- 标记由程序统计。
- 结果在 `results-e2e/`。

| 方案 | 应用记忆覆盖 | 换说法 / 上位 / 间接 / 还记得 | 旧当新 | 硬扯无关 | 编造 | 标记指向应当用到的记忆 | 标记 id 都有效 | 干扰题出现标记 |
|---|---|---|---|---|---|---|---|---|
| a 现状（×3 = 45 答） | 0.72 | 1.00 / 0.46 / 0.58 / 0.83 | 1 | 1 | 3 | 26/36 | 39/45 | 0/9 |
| b terra 8 条（×3 = 45 答） | **0.79** | 1.00 / 0.45 / **0.86** / 0.83 | **0** | **0** | **0** | **36/36** | **44/45** | 0/9 |
| b flash 8 条（×1） | 0.78 | 1.00 / 0.53 / 0.75 / 0.83 | 0 | 0 | 0 | 12/12 | 14/15 | 0/3 |
| 全部 300 条常驻（×1，参照） | 0.87 | 1.00 / 0.80 / 0.83 / 0.83 | 0 | 1 | 0 | 12/12 | 15/15 | 0/3 |

- 两种方案的所有回答都写了 `[记忆](cite:pmem:…)`。
- 现状下有 10 个回答的标记，没有落在任何一条应当用到的记忆上。
- 现状下另有 6 个回答把标记 id 抄错了：UUID 前半段对，后半段是编的，界面会把这种标记藏掉。b 只有 1 个。推测是上下文里条目多了，抄错的机会也多了。
- 回答层面的提升（0.72 → 0.79）小于选取层面的提升（0.69 → 0.94），有两个原因：
  - 现状每轮塞约 25 条，碰巧也带上了不少 gold；
  - 主模型对上位概念类问题本来就只用一部分记忆。即使全部常驻，这类问题的覆盖也只有 0.80。
- q25「明年的打算」上 b 只覆盖 1/4。这是标注口径问题：b 挑了另外几条同样是「明年」的规划条目。去掉 q25，b 是 0.83，现状是 0.69。
- 全部常驻的覆盖最高，但现在上下文包每轮整包写进模型历史，300 条约 2 万 token，十轮下来就是 20 万。要走这条路，得把个人记忆挪到可缓存的系统提示里，改动面大，干扰题也更容易被硬扯，这次没有采用。

## 5. 为什么选 b

1. **效果最好。**
   - 300 条以内，召回和精确率在所有方案里同时最高。只有 haiku 和 b 打平，但它慢 3–5 倍。
   - 换说法、上位概念、间接、「还记得」四类都稳定；干扰题不会误召回。
   - 「较新的说法一定要选」这一条写进了提示词，旧当新几乎没有。
2. **不加基础设施。**
   - 用的是已有网关和已有的快模型通道，复用分诊的 `streamFastResponse` 和备用模型重试。
   - 不需要嵌入服务、pgvector，也不需要迁移（这次没有用到 081 和 082）。
3. **延迟基本藏在分诊后面。**
   - 选取在路由里就开始了，运行时拼上下文包时才等它。分诊本身要 1.6–3.2 秒（最多 5 秒）。
   - 用 flash 时，P90 1.7 秒，基本不额外等待。
   - 用 terra 时，P90 3.3 秒，偶尔会比分诊多等一两秒。所以召回模型单独配（`MEMORY_RECALL_MODEL`，推荐 flash），不跟分诊走。
4. **成本可控。**
   - 每轮选取输入约 1.6 万 token。旧条目排在前、新条目追加在末尾，目录前缀稳定，DeepSeek 命中缓存 97%。
   - 输出约 25 token。
   - 装进上下文的从约 2,000 token 降到约 500 token。

其他方案的问题：

- **向量（d）**：换说法和「还记得」很好，但上位概念类只有 0.37；干扰问题靠阈值挡不住（见 4.1）；而且要新增嵌入服务。
- **混合（e）**：上限被第一阶段卡住，上位概念类掉到 0.56–0.72；规模大了掉得最快。
- **分层（c）**：两次调用。它依赖提炼写出的话题名，话题名本来就不统一，上位概念类会漏掉没被选中的组。

## 6. 成立范围与扩展

- **300 条以内**：用 b 的现状配置。
- **300–800 条**：还是 b。目录长到 2.5–4 万 token，延迟和成本线性上升。需要时快模型可以换成 terra：1000 条时 terra 召回 0.90，flash 只有 0.80。
- **800 条以上，或目录超过约 4 万 token**：换成分层目录（c），先让快模型挑话题组，再在组里挑条目。1000 条时召回 0.85、输入 5,500 token、P50 2.0 秒，同样不需要新基础设施。前提是提炼时把话题名归一：给提炼提示词一份已有话题清单，让它优先复用。
- **几千条以上**：加一层向量预筛，取前 100 条左右，再交给 b 挑。需要的东西：
  - 网关没有 `/embeddings`，要接一个外部嵌入服务（需要新的密钥），或者在 API 容器里跑本地 bge-m3（ONNX q8 约 570 MB 内存）；
  - 向量存进 Postgres。每人几千条以内在应用里直接算余弦就够了，不需要 pgvector 索引。生产库镜像是 `postgres:17-alpine`，不带 pgvector；换成 `pgvector/pgvector:pg17`（Debian）要注意 musl 和 glibc 的排序规则差异会影响已有文本索引，换之前要重建索引。
- **上位概念类问题的根本解法**在写入侧：定期给每个话题写一条摘要条目（RAPTOR 式），让「渠道整体思路」这类问题直接命中摘要。

## 7. 分支上的实现

- `apps/api/src/personalMemoryRecall.ts`（新文件）：召回提示词、目录格式、解析（编号换回真实 id，编造的编号丢掉）、`createMemoryRecall`。具体做法：
  - 复用分诊的 `streamFastResponse`，关掉思考，读到第一个完整 JSON 就停；
  - 出错时，只要时限内来得及，就换 LIGHT_MODEL 再挑一次；
  - 整次限时 6 秒。
- `personalMemory.ts`：
  - `createPersonalMemory({ pool, recall })`；
  - 配了召回时，`select` 的顺序是：钉在当前对象上的条目、模型挑出的条目、偏好类（常驻），总量仍限 8 KB；
  - 没配、失败或超时，就退回原来的字面重合，原样保留；
  - 记日志 `personal_memory.recall`，带候选数、挑出数、耗时和错误码，不带正文；
  - `search_personal_memory` 也走同一套召回。
- `routes/conversations.ts`：不再先等选取完成；交给运行时的是一个 Promise。id 在这个 Promise 里记进 memory_used，运行时等的正是记完 id 之后的那个 Promise，所以模型看到的条目一定已经记下。
- `piConversationRuntime.ts`：拼上下文包时才 `await`；`conversations.ts` 的输入类型允许传数组或 Promise。
- 配置（10/18 定）：召回模型与分诊分开配。新增 `MEMORY_RECALL_MODEL`，没配时依次退回 TRIAGE_MODEL、LIGHT_MODEL，出错时换 LIGHT_MODEL 再挑一次（`memoryRecallModels`）。`.env.example` 推荐值写 `deepseek-v4.1-flash`，`infra/docker-compose.yml` 把它传给 api。分诊模型不动。
- `app.ts`：按上面的配置建召回。测试替身入口是 `personalMemoryRecall`，传 null 表示不用模型。`test/helpers.ts` 默认传 null。
- `conversationRouting.ts`：只把 `streamFastResponse` 和 `ResponsesClientOptions` 改成导出。
- 测试：

## 8. 拍板情况

已定（10/18）：
- 召回模型单独配 `MEMORY_RECALL_MODEL`，推荐 deepseek-v4.1-flash：召回 0.96，P90 1.7 秒，缓存命中 97%。分诊不动。线上要在部署环境里填上这个变量，不填就退回 TRIAGE_MODEL、LIGHT_MODEL。
- 做法类不再每轮常驻，改为按相关性挑。
- 每轮把本人全部现行记忆的目录发给快模型。

还没定：

1. **人豪：话题名要不要归一。** 在提炼提示词里给出已有话题清单，让它优先复用。这是 800 条以上换分层目录的前提，现在还不急。
2. **主模型只用了一部分召回到的记忆。** 上位概念类问题的端到端覆盖，在全部常驻时也只有 0.80。要不要在系统提示里加强「用上 personalMemory 里的每条相关条目」，属于主提示词的改动，这次没有做。
