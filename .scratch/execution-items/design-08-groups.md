# 工单 08 · 群聊通用化：议题群、会议群、进群介绍 · 设计

日期：2026-09-28。依据：
- 成员工作台规划 `.scratch/member-workspace/spec.md` §11（2026-09-26 确认的二级页框架与群组规则，本单照做）。
- 用户 2026-09-28 的新要求与决定：
  - 右列除了自己的 Agent，协作对象多一个群聊页签。
  - 新人进群时，Co-Agent 先讲清这件事是什么、为什么跟你有关、前因后果。
  - 会议群：主持人和参会人自动进群。
  - 议题群：CEO 拉人（群里的人也能再拉）。
  - 两件像的执行事项不做智能合并。
- 已有的底子：
  - 通用群组表（thread_members / thread_messages / thread_reads）和 `/api/threads/:objectType/:objectId` 读、发、已读，已支持 issue、signal、task、meeting 四种对象（迁移 024）。
  - 右列的群组频道已推广到个人卡和执行事项（工单 05 W3：`DetailGroup`、`useTaskGroup`、`TaskGroupTranscript`）。

## 0. 本单做什么、不做什么

**做**：
- 议题群；
- 会议群；
- 成员能打开的议题页和会议页（只读）；
- 各类群的「拉人」和「自己退出」；
- Co-Agent 进群介绍：模型生成，失败时用兜底，执行事项也换用它；
- 通知：被拉进群、群里有新消息、成员的「会议安排」。

**不做**：
- 材料区的上传、删除和 Agent 改材料：工单 09。
- 安排会议、接受或拒绝邀请、飞书忙闲、附加议程：以后的会议工单。
- 信号群：「发送信号」那一单一起做。
- 智能合并。
- 把别人移出群。

## 1. 群的成员从哪来

| 对象 | 谁在群里 | 怎么进 |
|---|---|---|
| 议题 | CEO 加被拉的人 | CEO 在议题页点「拉人进群」，选人、可以写一句为什么；第一次拉人时群才建起来，CEO 自动在群里。群里任何人都能再拉人 |
| 会议 | 主持人、CEO 参会人、参会人 | 建会和改参会人时自动同步：新加的进群，被移出参会名单的退群。迁移里给已有的会补建成员 |
| 执行事项 | 推进人加协作者 | 沿用工单 05 的「邀请协作」；进群介绍换成本单的 |

- 被拉即加入，不用对方先接受（沿用 spec §11.2）。
- 每个人都能自己退出，但对象的「主人」不能退：执行事项的推进人、会议主持人，以及议题群里的 CEO。
- 执行事项里退群就等于退出协作。
- 退出后再被拉进来，照常进群，能看到全部记录。
- 可以拉的人：人员名单里的成员，CEO 也可以拉进议题群和会议群。
  - 执行事项仍然不能拉 CEO（工单 05 的决定），CEO 兼 DRI 用 DRI 视角的情况见工单 07。

## 2. 成员能看到的议题页和会议页

**议题**：`/me/issues/[id]`。只有群成员能打开，其他人一律 404。
- 能看：议题的标题、为什么现在、所在位置、紧急程度、研究结果和 CEO 的判断（有的话）、状态。
- 看不到：CEO 专用的操作，包括决定、驳回、移出、安排会议、改内容。
- 页面框架和 CEO 的议题页一样，是只读的样子。

**会议**：`/me/meetings/[id]`。只有群成员能打开。
- 能看：会名、时间、主持人、参会人、会议目的，会前材料的列表（能下载、能看解析后的文字），预审摘要（有的话），会后结论（有的话：决定、待办和各自负责人）。
- 看不到：CEO 专用操作，包括录音、确认、编辑会议、替换逐字稿。

右列：
- 这两个页面和 CEO 的议题页、会议页，右列都是「我的 Agent / 群聊」两个频道，和个人卡、执行事项同一套。
- 「我的 Agent」的上下文带上这个页面的内容，但只带成员有权看的部分。
- CEO 页面只有在 CEO 是群成员时才出现群聊频道。议题拉人之前没有群，就只有「我的 Agent」。

## 3. Co-Agent 进群介绍

**触发**：有人被拉进任何一种群（议题、会议、执行事项）时。一次拉几个人，就只写一条介绍，点名这几个人。

**内容**：3 到 6 句中文，讲：
- 这件事是什么；
- 为什么拉你们进来，优先用拉人者写的那句话；
- 前因后果和现在进行到哪；
- 接下来希望你们做什么（有的话）。

只能用群里所有人都能看到的信息：对象页上成员能看的部分、群里之前的聊天、拉人者的话。不写 CEO 专用的判断材料以外的东西，不编造。

**生成**：
- 用现有的模型通道，走 candidate agent 的写法，light 档位，结构化提交 `{message}`。
- 加入的请求先返回，介绍在后台生成，20 秒超时。生成好后作为 kind=co-agent 的消息写进群里。
- 对拉人者和原有成员记为已读，对新人算未读。

**兜底**：模型失败、超时或提交不合格时，发固定格式的说明：

> 「{拉人者} 把 {新人} 拉进了这个群：{对象标题}。{一句对象描述}。{拉人者说：「…」}」

- 对象描述按类型取：
  - 议题：为什么现在；
  - 会议：时间和目的；
  - 执行事项：所属个人任务、截止。

**审计**：写 agent_runs，和其他 Agent 一样。

## 4. 通知

- **被拉进群**：新的通知类型 `thread_member_added`，payload 为 `{objectType, objectId, inviterId, note?}`。
  - 成员通知栏「新的执行事项」这一组更名为「分给你的事与邀请」，文案：
    - 议题：「{拉人者} 拉你进议题「…」」
    - 会议：「{拉人者} 拉你进会议「…」」
    - 执行事项：沿用「邀请你协作」
  - 点开进对应的页面。
  - 会议自动进群不发这条，改由「会议安排」提示。
- **群里有新消息**：成员通知栏加一组「群聊新消息」，按群列出，例如「议题「…」 · 3 条新消息」，点开进对应页面并切到群聊频道。
  - 不存通知行，按 thread_reads 现算。
  - 执行事项和个人卡的群也算在内。
  - 每 20 秒刷新。
- **会议安排**（成员）：通知栏最上面一组，列出我在群里、还没开完的会，按开始时间排，每条写日子、几点到几点、谁主持。样式照 SSOT DRI-05 的「会议安排」卡：深灰底，一场会一行，整行就是按钮。

## 5. 契约（等工单 06 交回后由 Claude 冻结）

- `ThreadObjectType` 已有 issue、meeting、task、signal。
- `AddThreadMembersRequest {personIds (1..10), note? (≤200)}`。
  - 返回 `{members: ThreadMember[]}`。
  - 路由 `POST /api/threads/{objectType}/{objectId}/members`：群成员才能调。议题群第一次由 CEO 调用时建群，此时 CEO 可以不是成员。
- `POST /api/threads/{objectType}/{objectId}/leave`：返回 204；主人调用返回 409。
- `MemberIssueView`：议题的只读投影。字段照 IssueCard 的 payload，去掉 CEO 的动作。路由 `GET /api/me/issues/{id}`。
- `MemberMeetingView`：会议的只读投影。材料只给列表和下载地址。路由 `GET /api/me/meetings/{id}`。
- `GET /api/me/meetings`：我在群里、还没开完的会，给「会议安排」用。
- `GET /api/me/threads/unread`：`{threads: [{objectType, objectId, title, unread, href}]}`，给「群聊新消息」用。
- `NotificationKind` 加 `thread_member_added`。
