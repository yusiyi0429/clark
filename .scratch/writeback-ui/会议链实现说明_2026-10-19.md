## 一、之前缺什么（main a7ad0b8 的现状）

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 会议本身不连任何对象：本体里只有「一条决定一条事件」，没有整场会议的事件 | 架构页要求「每场会 1 条会议事件，会议至少连着一个对象」，这一条不成立 |
| 2 | 决定影响到的对象在本体里对不上时，非 E&O 的会直接跳过 | 跳过时不报错、界面也不显示，大部分决定实际没写进去：world-02 里只有 5 个 Mission 带天枢外部引用，Task 一个都没有 |
| 3 | 没有「不写进本体」：迁移、接口、界面都没有 | 0.3 在 scope 内不做读隔离，敏感会议挡不住 |
| 4 | 主持人、CEO 看不到每条决定会写到哪个对象、写没写成 | 契约 `MeetingDecisionView` 里没有落点，也没有写入状态 |
| 5 | 代判只有一种状态标「Agent 代判，Host 尚未确认」 | 分不出代判成了「定了」还是「没定」；代判之后这条就从首页待办里消失，主持人只能去会议页改判 |

## 二、补了什么

### 1. 会议挂点 + 会议事件（设计稿 3.1）

**界面**：会议页「会上定了」下面加一条：

- 「挂到」+ 落点标签（类型 名称 + 状态点）；
- 「改」：只有主持人和 CEO 能用；
- 状态：待写入 / 已记 · 时间 / 没对上 / 写入失败；
- 「不写进本体」开关。

参会人只看到挂点，看不到状态和开关。

挂点、写入状态、每条决定的落点都不放进会议卡，会议页另外取：`GET /api/meetings/:id/world`。这个接口只有主持人、CEO 和实际参会的人能用，其他人返回 404。这样读会议的 SQL 能保持原样，原因见第六节。

**挂点怎么定**：候选按顺序分三组，写入时取第一组里在本体对得上的对象。

1. 主持人或 CEO 改过的挂点；没改过就用生效的决定影响到的 Mission。来源是影响卡落到的 Mission，影响卡落在 Task 上时取它所属的 Mission。
2. 主持人负责的责任单元，即能力域负责人是主持人的那个单元，本体里按 `capability:<code>` 对。
3. 公司：实例配置里的 company；没配就取类型为 Company 的对象。

**改挂点**：

- 只能选会议所在月的 Mission 和责任单元；
- 可以「恢复自动」；
- 已经写进本体的，改完以后记一条 correction。

**写入时机和顺序**：

- 等主持人的条目都办完（或者已经代判），而且生效决定的影响卡都推完，才写。
- 先写会议事件，再写各条决定事件；决定事件的 `content.refs` 指回会议事件。
- 一条主持人条目都没有的会照样写，挂到主持人的单元。
- 战略项不用等。CEO 确认之后，会议事件记一条 correction，把这条加进「会上定了」。

**会议事件正文**：

- 依次是：会议、时间、主持人、参会人、天枢会议 id、挂到、摘要、会上定了（只列已生效的）。
- 原文不进正文。`artifacts` 放会议页地址，后面带 `#sha256=<逐字稿摘要>`。这一条是待定项，见下面第四节。

**是否要重写**：按「挂点 + 摘要 + 逐字稿 + 生效的决定」算一个摘要；摘要没变就不重写，变了就记 correction 并 supersede 上一条。

### 2. 不写进本体（设计稿 3.1，第 7 节第 2、3 条）

- **谁能用**：主持人和 CEO；其他人调接口一律返回 404。
- **还没写进本体时打开**：会议事件和等着写的决定都记 skipped，什么都不写。
- **已经写进本体后打开**：会议事件和已写的决定事件各记一条撤回（correction，正文第一行是「撤回：某人标为不写进本体」）。本体只能追加，原事件不删。
- **取消**：已撤回的再各记一条 correction 恢复，跳过的重新排队写。
- **幂等键**：同一版本上再写一次（撤回或恢复）时，幂等键另起一个，免得重放上一次的回执。

### 3. 每条决定的落点 + 写入状态（设计稿 3.2，第 7 节第 4、5 条）

- **落点**：已生效的决定，下面列出它落到的 Mission 和 Task（取自这一版影响卡）。
- **对不上就挂会议**：影响到的对象在本体里一个都对不上时，决定挂到会议的挂点上，界面显示会议的挂点，并标黄点。
- **状态点**：灰点等写、绿点已记、黄点挂到会议或没对上、红点写入失败；划掉表示不写进本体。状态只给主持人和 CEO 看，参会人只看落点。
- **代判拆成两种**：「Agent 代判 · 定了」和「Agent 代判 · 没定」，后者划掉。代判过的条目会一直留在主持人首页「会上定了」里，直到主持人点过为止。

## 三、方案里的取舍

- **决定事件晚一点写**：决定事件改成等会议事件写完以后再写，最晚晚一个工作日，也就是代判的时刻。这样做是为了让会议事件的挂点包含所有决定影响到的 Mission，决定事件也才能指回会议事件。架构页的写法是「Host 确认后 30 分钟内写入」，和这一点一致。
- **E&O 兜底保留**：原来「E&O 的会对不上就挂 E&O 单元」的逻辑没删。现在先走会议挂点，没有会议事件时才用到它。
- **不加「会议关联 Mission」字段**：挂点直接存在会议上，也就是第 7 节第 1 条的推荐。
- **怎么验证**：开发和测试只用假本体。本机演示在 4830 起了一个假本体，写进来的事件只记在内存里。

## 六、走查中发现的问题：读会议变慢（已按修法 A 修好）

- **表层现象**：3 个会议相关的测试刚好超过 5 秒上限。和 main 对比，同一台机器、单进程：
  - 「不同意发 strategic_rejected」从 1.66 秒变成 4.4 秒；
  - 「散会后的通知生命周期」从 1.63 秒变成 4.3 秒。
- **直接诱因**：在演示库上读一次会议，从 2.2 ms 变成约 1.2 秒。执行计划显示，查询真正执行只要 0.76 ms，其余约 1.29 秒全花在 Postgres 的 JIT 编译上：217 个函数，优化 657 ms，生成 583 ms。
- **根本原因**：每次读会议都带上的两段相关子查询（「决定落点」和「挂点候选」），把估算代价抬到了约 54 万。这超过了 JIT 的两个阈值：`jit_above_cost`（10 万）和 `jit_optimize_above_cost`（50 万）。代价虚高有两个来源：
  - `jsonb_array_elements` 默认按每次展开 100 行估算；
  - `tk.id::text = …` 用不上索引，被估成全表扫描。

  实际数据量很小，按理很快。生产库只要是默认的 `jit=on`，也会这样。

| 修法 | 做法 | 副作用 |
|---|---|---|
| A. 移出热路径（推荐） | 读会议时只带几列普通字段。落点和挂点候选单独查，只在三处查：会议页卡片、本体同步、挂点接口。每处几条简单 SQL | 改动中等：会议卡的投影要分成两步。列表、动作回执里的会议卡不再带落点（这些地方本来也不显示） |
| B. 改写 SQL 压低估算 | 把 id 转成 uuid 走索引，用 LATERAL + LIMIT，去掉嵌套的 CASE 子查询 | 估算本身不可控，数据一涨或以后改几行，又可能越过阈值，不保险 |
| C. 关掉 JIT | 在连接池上设置 `jit=off`，或者写一条迁移 `ALTER DATABASE … SET jit = off` | 改动最小，但会影响全局。业务查询基本都是 OLTP，JIT 几乎用不上，关掉多半没坏处；不过它是数据库层面的设置，等于连部署也改了 |

### 用了修法 A（10/19 你选的）

**改了什么**：

- 读会议的 SQL 恢复成 main 原样，只多带 8 列普通字段。
- 挂点候选和决定落点挪到 `apps/api/src/meetingWorld.ts`，用几条简单查询算，只在三处用：
  - 会议页的 `GET /api/meetings/:id/world`；
  - 本体同步；
  - 挂点相关的接口（改挂点、取可选对象）。
- 会议卡和决定视图里不再带这些字段。
- 会议页「会上定了」打开时自己去取一次。主持人办完一条后，马上再取一次，5 秒后再取一次，等影响卡在后台推完。

**结果**：

| | 修之前 | 修之后 |
|---|---|---|
| 读会议 | 1.3 秒（JIT 编译） | 0.72 ms，不再触发 JIT；main 是 2.2 ms |
| 新接口 `/world` | — | 约 9 ms |
| 读会议卡接口 | — | 约 7 ms |
