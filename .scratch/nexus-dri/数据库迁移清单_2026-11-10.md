# 11/13 上线的数据库迁移清单

2026-11-10。比的是集成分支（`claude/new-home-integration`，已含 B 这条线到 `f2f4253f`）和 `origin/main`（`37f742de`，迁移到 218）。只读分析，没碰任何库。

## 结论

- 天枢 api：多出 **46 个**迁移，编号 220–238、240–265、270（219、239、266–269 没用）。安排里写的「237–264」不全，是从 220 起。
- Chat：多出 **2 个**（008、009）。
- **没有耗时长的，也不用停写。** 46 个里只有 9 个动了线上已有的表（`tasks` 7 次、`personal_tokens` 2 次），都是加可空列、加带常量默认值的列、加一个部分索引、换一条取值检查；`tasks`、`personal_tokens` 都是小表，每条是毫秒级的短锁。其余全是新建表，或改这一批里新建的表（上线时是空的）。
- 两处带数据的语句（252 改伙伴性格取值、258 给已有子会话补字母）操作的都是这一批新建的表，线上是空表，等于不做事。
- 没有删表、删列、改列类型。
- **都是加法**：迁移跑完以后，旧版 api（main）照样能用这个库，所以应用回退不用回退库。没有写反向迁移。

## 怎么跑

- 天枢 api 启动时自己跑（`server.ts` 里 `migrate()`，监听端口之前）：持库级咨询锁，按文件名顺序，一个文件一个事务，记在 `schema_migrations`；按编号集合判断跑没跑过，不要求连号。某个文件失败就回滚那一个、api 起不来，前面成功的保留。
- Chat 的迁移是另一套（带校验和）：照之前的做法用 `chat_migrator` 跑，见下面的坑。

## 周四在预发上怎么先完整跑一遍

1. 从正式库导一份当前数据（只读导出），恢复到预发用的库里。要用正式的数据，不能用空库：要验的就是「218 的库加上这 46 个」。
2. 恢复完先看起点：`SELECT max(id), count(*) FROM schema_migrations;` 应该是 218。
3. 起集成分支构建的 api，让它自己跑迁移。看启动日志有没有 `migration … failed`，记下从启动到开始监听用了多久。
4. 核对结果：

```sql
SELECT count(*) FROM schema_migrations WHERE id >= 220;
```

应该是 46。再看 `SELECT id, filename FROM schema_migrations WHERE id >= 220 ORDER BY id;` 和上面的编号对得上。

5. Chat：在预发的 chat schema 上跑 008、009，核对它自己的迁移账本多了这两条，再起 Chat。
6. 走一遍冒烟：登录、新首页、打开一个老的执行事项（`tasks` 加了列）、个人令牌列表（`personal_tokens` 换了检查）、伙伴对话一轮。
7. 回退演练（可选但建议）：迁移跑完后把 api 换回 main 的版本，确认老界面照常能用。

## 要注意的坑

- **Chat 迁移文件的换行**：在 Windows 上打 Chat 源码包要用 `git -c core.autocrlf=false archive`，否则迁移文件变成 CRLF，校验和全变，报 `Applied migration checksum mismatch`。
- **Chat 迁移的权限**：迁移开头的 `CREATE SCHEMA IF NOT EXISTS chat` 要库级 CREATE 权限，之前的做法是临时授给 `chat_migrator`、跑完收回。
- **3700 的开发库**已经跑到 265，下次重启 api 时只会补 270；它不能代替预发这一遍，因为它不是从 218 起步的正式数据。
- **顺序**：正式库会一次把 46 个按编号顺序跑完，270 排在最后，不依赖前面新首页的表。
- 没查的：正式库 `tasks`、`personal_tokens` 的实际行数（按用量估是几百到几千行），和正式库现在 `schema_migrations` 的最大编号是不是 218。第 2 步会核到。
