# 会议写本体切到 Nexus：切换方案（只是方案，没动线上）

2026-11-10。计划 11/13（周五）切。依据是 main（37f742de）上的代码，行号指 `apps/api/src/`。

## 1. 旧链现在怎么写本体

妙记或逐字稿 → 模型生成会议卡（决策、行动项）→ 责任人逐条确认 → 冻结 → 写本体。

- 冻结：任务 `meeting.card_freeze`。决策都有了结果时立刻排；另外每张卡生成时就排了一条 48 小时后的（`meetingCard.ts:268`）。
- 写本体：任务 `meeting.world_sync`，一场会一条会议事件，幂等键 `tianshu-meeting:<会议 id>:v<版本>:event`（`worldMeetingEvent.ts:43`）。
- 写不写只看一个条件：本体配了、而且实例配置允许写（`meetingFollowThrough.ts:86`）。

## 2. 怎么关：用 `MEETING_WORLD_WRITES_OFF=1`

11/10 用户选了做法 A，已经做了（`claude/new-home-api-16ccf0` 的 `b9f83793`）：环境变量 `MEETING_WORLD_WRITES_OFF=1` 只关会议写本体，缺省不关。关着时会议卡照常生成和冻结，不再找人逐条确认（11/11 定，见第 5 节），回执一律记「不写入」；主持人整卡确认选了写入也按不写入记；网页收起「不写进本体」开关。下面的坑已经一起处理。切换那天在 `infra/.env` 里设上、重启 api；改回去重启即恢复。

下面是当时比较的三个做法，留作记录。原先现有的手段都是整个本体写入一起关（实例配置 `writes:false`、换成只读实例、不配凭证），会连带停掉周复盘写本体和周期目标代记。三个做法：

| | 做法 | 副作用 |
|---|---|---|
| A（建议） | 加一个只管会议的开关（环境变量，照 `TKOS_WORLD_PERIOD_GOAL_GATES` 的写法）：`meetingFollowThrough.ts:87`、`:95` 各加一个判断，`server.ts` 和 `infra/docker-compose.yml` 各一行 | 要发一版。会议卡照常生成、照常逐条确认，只是不再写本体。要同时处理一个坑，见下 |
| B | 实例配置 `writes` 改成 false | 不用改代码，但周复盘写本体、周期目标代记一起停 |
| C | 连会议卡生成也停（撤掉妙记轮询和 `meeting.*` 任务） | 会议页、通知栏的会后确认、Chat 读已确认会议都受影响，第一步不建议 |

A 要一起处理的坑：只关写入、读还开着时，主持人整卡确认或修改时选「写入」，回执会记成「写入中」，但没有任务去写，会一直停在那（`meetingCardConfirm.ts:264、291`）。开关关着时要按「不写入」记，网页上「写进本体」那个开关也要收起来。

开关关上以后的行为（已核对）：新冻结的卡回执记「不写入」（`:395、405`）；队列里遗留的 `meeting.world_sync` 任务空跑一次就结束，不会写（`:497`）。

## 3. 切之前查在途

在生产库只读执行。

还在排队或在跑的任务（冻结任务的执行时间在 48 小时后，也要看）：

```sql
SELECT id, kind, status, run_at, attempts, last_error, payload
  FROM jobs
 WHERE kind IN ('meeting.world_sync', 'meeting.card_freeze') AND status IN ('pending', 'running', 'dead')
 ORDER BY run_at;
```

已经冻结、会议事件还没写成的：

```sql
SELECT m.id, m.title, m.feishu_meeting_id, m.ended_at, s.revision, s.event_status, s.event_error
  FROM meeting_cards k
  JOIN meeting_card_syncs s ON s.meeting_id = k.meeting_id AND s.revision = k.current_revision
  JOIN meetings m ON m.id = k.meeting_id
 WHERE s.event_status IN ('pending', 'failed');
```

还没冻结、之后会冻结并写入的（等逐条确认，或等 48 小时到期）：

```sql
SELECT m.id, m.title, m.feishu_meeting_id, m.ended_at, k.write_to_world
  FROM meeting_cards k JOIN meetings m ON m.id = k.meeting_id
 WHERE k.draft_status = 'draft_ready' AND k.current_revision IS NULL AND k.decisions IS NOT NULL;
```

## 4. 怎么保证同一场会只有一边写

和溪南约一个切换时刻 T，按这个顺序做：

1. T 之前，Nexus 新链在联调环境验通。没验通就报阻塞，不关旧链（溪南 11/10 第 5 条）。
2. T 之前，把第 3 节第二条查出来的（已冻结、没写成）处理完：重试写成，或者列给溪南由 Nexus 补。原因是开关一关，天枢不会再写它们。
3. T 时，把第 3 节第三条查出来的（没冻结的）连同飞书会议 id 列成清单发溪南，约定这些会全部归 Nexus，天枢不再写。然后关开关、重启 api。
4. T 之后核对：天枢这边 `meeting_card_syncs` 没有 T 之后新写成的；本体那边按幂等键前缀 `tianshu-meeting:` 查没有 T 之后的新事件。
5. 回退：把开关改回去重启即可。关着期间冻结成「不写入」的卡，主持人可以在会议卡上逐场改成写入（现有功能）。

- **已定（本人 11/11 上午）**：切过去以后天枢自己的逐条确认也停掉，会后判定归 Nexus，免得同一条决策被问两次。挂在同一个开关 `MEETING_WORLD_WRITES_OFF=1` 下，缺省不关时行为不变。开关打开时：
  - 天枢不再找人逐条确认：通知栏、新首页「等你」、飞书推送里都不出会议卡的决策和行动项（三处同一个来源 `pendingFor`）；切换前就在等的也一起不出（按第 4 节第 3 步归 Nexus）。
  - 会议卡页面不出「确认 / 不对」「交给谁确认」，不标「待某某确认」「待接下」；决策只写责任人，已经确认或退回过的照旧显示。
  - 会议卡照常生成、照常能看，照常 48 小时冻结（主持人仍可整卡确认）。冻结版里没人确认的决策不进 payload，所以新冻结的卡 `decisions` 为空；Chat 读「已确认的会议」用的是摘要、段落和行动项，不读决策，照常能读到。
  - Nexus 推来的待定事项（「等你」里的「会后确认」）不受影响。
  - 确认接口本身没关（页面上已经没有入口）。回退时把开关改回去重启，没冻结的卡又会出现逐条确认；关着期间已经冻结的，决策不会再补问。
- Chat 读「已确认的会议」的接口还在读天枢的会议卡，切换后要不要改成读本体，另外定。
