# 设计：资料预授权与分领域验收（2026-11-03 草稿 v0.1，等孙铭泽定）

> 起因：你 11/03 看交付面板时提的两件事——①公司直接连的外部资产（GitHub 等）应该在给客户配置时就授权好；②财务、人力、产品、技术的验收标准各不相同，要懂行才能验收。
> 依据：`调研_资料授权与分领域验收_2026-11-03.md`（同目录，带来源）；你 11/03 定的「评审只作参考，不卡交付、不当进展」（spec v0.8）。
> 写法：标「（我定的）」的是我替你做的选择，可以改；第 6 节是只有你能定的。只写方案，不改代码。

## 0. 一句话

- **授权**：客户上线时，管理员把通道开好、把范围圈好（飞书应用的读文档权限、GitHub App 装到组织并选仓库）；每个人第一次用时再连一次。读的时候一律用**上传人本人的身份**，本人看不到的天枢也读不到，不拿公司身份兜底。
- **验收**：AI 只给参考——逐条找证据、说怎么补、认出放错 Task 的材料，不下结论。要专业判断的条目标「要人看」，交给这个领域的负责人。某个领域攒够人的判断、AI 和人的一致率达标之前，这个领域的 AI 评审一直只作参考。

## 1. 要解决的两件事

| | 现在 | 问题 |
|---|---|---|
| 内部资产读不到 | 公开网页服务端去取；飞书链接标「飞书文档请导出后上传」；GitHub 私有仓库、内网系统都标「打不开 · 请导出后上传」 | 你 11/03 那版 3 个链接全打不开，评审只能判 0/2。交付物越真实，越可能是内部链接 |

## 2. 授权

### 2.1 三条原则

1. **用本人身份读。** 评审是「替上传人看他交上来的东西」。用他自己的飞书 / GitHub 授权去读，读到的天然就是他本来能看的，不用天枢自己判断谁能看什么。
2. **公司层只开通道、圈范围，不给天枢一把读全公司的钥匙。** 用公司身份读全部资料再按人过滤（Glean、Copilot 那套），要维护整套权限镜像，重而且一错就越权，评审用不上。
3. **报告不能比原文更公开。** 原文的权限由飞书、GitHub 管；评审报告会被 DRI、Co-Agent 看到，以后还要进本体。报告里只写结论、理由和证据位置（第几节、哪个文件哪一行），引用原文最多一两句。

### 2.2 为什么个人那一下省不掉

你的直觉是「配置客户时就全配好」。公司层确实能在上线时配好，但每个人还得自己连一次：那一下是在告诉天枢「这个人是谁、他能看什么」。想连这一下也省掉，只有两条路：

- 用公司身份读，自己判断谁能看——就是上面原则 2 不做的那套；
- **把授权并进登录**：天枢本来就要每个人连飞书（约会议、会后拿妙记都要），读文档的权限加进同一次授权里，大多数人只会看到一次飞书授权页（我定的，推荐）。以后客户有统一身份系统（飞书本身就是很多客户的身份系统）时，可以做到首次登录自动带上，参照 Claude 企业版的托管授权（调研 2.1）。

### 2.3 客户上线时配（管理员做一次，写进上线清单）

| 资产 | 管理员做什么 | 圈多大 |
|---|---|---|
| 飞书文档、知识库、表格 | 天枢的飞书自建应用加三项用户身份只读权限（新版文档正文 `docx:document:readonly`，知识库、表格的只读档按开发者后台的实际名字），发新版本，租户管理员批准。加进现有的 `.scratch/tianshu-v1/飞书开发者后台配置清单.md` | 用户身份：只读得到本人有权看的；不需要把文档分享给应用 |
| GitHub 仓库、PR | 天枢注册一个 GitHub App，只要「代码、PR、仓库信息」三项只读；客户组织的 Owner 装到组织，**只勾要评审的仓库** | 能读的 = App 装了的仓库 ∩ 本人能看的仓库。不用 OAuth App（权限太大、不能选仓库），不收个人 token（离职就断） |
| 公开网页 | 不用配 | 服务端匿名取，只放 http/https、不连内网地址、限大小和超时（已做） |
| 内网系统、其他 | 不读 | 照旧标「打不开 · 请导出后上传」；页面截图上传（已支持图片） |

### 2.4 每个人第一次用时

- **飞书**：读文档的权限并进现有的「连接飞书」那一次授权（账号菜单、约会议、会议卡上都有这个入口）。已经连过飞书、但授权里没有读文档这一项的人，第一次贴飞书链接时，链接下面出一个「连接飞书」，点了重新授权一次就好（我定的）。
- **GitHub**：第一次贴 GitHub 链接时，同样在链接下面出「连接 GitHub」，本人授权这个 App 一次。
- 设置里能看到连了哪些、能断开；断开就删掉天枢存的令牌。

### 2.5 读的时候

```
贴进来的链接
  ├─ 飞书文档 ── 本人连了飞书、授权里有读文档 ── 用本人身份读正文 ── 读到：进评审
  │                │                                         └─ 403：「你在飞书里没有这篇的读权限」
  │                └─ 没连 / 授权里没有 ── 「连接飞书」，连好后重评这一版
  ├─ GitHub ──── 同上，换成 GitHub App 的本人授权
  ├─ 公开网页 ── 服务端去取（已做）
  └─ 其他 ────── 「打不开 · 请导出后上传」（已做）
```

- **读取记录**：每读一次外部链接记一行：谁、哪个链接、用的哪种身份、什么时候、读到没有（读不到写原因）。版本上能看到「这一版读过哪些链接」。这就是审计，源系统那边（GitHub 审计日志、飞书）也各有一份。
- **读到的正文**：存在天枢自己的库里，跟着这一版走（重评、「我不同意」都要用），只给能看这个 Task 的人；不写进本体（我定的）。
- **撤销**：本人在设置里断开；离职由客户在飞书、GitHub 停用账号，令牌自然失效（飞书约 2 小时、GitHub 8 小时过期，续期也会失败）。

### 2.6 先做什么

| 批次 | 做什么 | 为什么 |
|---|---|---|
| 先做 | 飞书：加读文档权限、按本人身份读正文、链接下的「连接飞书」、读取记录 | 已经有本人飞书授权和续期，只差一项权限和一个读正文的函数；公司里交付物大多是飞书文档 |
| 有人真交仓库链接再做 | GitHub App | 是一条全新的集成（注册 App、安装回调、本人授权、存令牌），大约一个独立小单 |
| 以后 | 首次登录自动带授权；内网系统的取件程序；本人读不了时由管理员明确授权、用应用身份读一次（默认关、记审计） | 要看客户的身份系统和网络，按客户单独设计 |
| 不做 | 全公司资料索引和权限镜像；Google 那种能冒充任何人的服务账号 | 评审本人交的东西用不上，而且越权风险最大 |

## 3. 分领域验收

### 3.1 先分清谁定什么

| 谁 | 定什么 | 现在 |
|---|---|---|
| 本人 | 什么时候交付 | 已做：参考评审跑完就能交，不看达没达到 |
| AI（参考评审） | 每条有没有证据、缺什么、怎么补；材料是不是放错了 Task | 已做；11/03 起只作参考 |
| 人（验收） | 这个 Task 到底算不算做完 | Task 的确认完成在本体里只能由人记；谁来记还在 spec 第 7 节第 1 条待定 |

这一节只管两件事：让 AI 的参考更懂行；以及哪些条目 AI 根本不该下结论、要直接交给人。

### 3.2 给评审的领域知识，分四层

1. **Task 自己的验收标准**（最重要）。调研里「针对这一题的细则」把和人的一致度从 0.42 提到 0.83（代码评分），HealthBench 用医生逐题写的细则，模型和医生的一致度接近医生之间。验收标准写得越具体、越可检查，评得越准。这要 M2 拆 Task 时就写好（spec 第 7 节第 2 条）。
2. **领域短清单**，每个领域 5–8 条，写进评审提示词。只写「这个领域交付时人人都会查的」，**只用来补问和提醒，不扣分**。草稿（我定的，要找懂行的人改一遍）：
   - 技术：有没有测试或运行证据；改动范围和描述对不对得上；有没有安全或数据风险；
   - 财务：数字的口径和期间写清了没有；能不能和来源对上；有没有审批或复核痕迹；
   - 人力：涉及具体员工的结论有没有依据；有没有敏感个人信息外露；
   - 产品：有没有真实用户或试用的证据；验收场景走没走通。
3. **客户自己的领域资料**（以后）：上线时上传客户的月结清单、职级标准、技术规范，作为评审依据，每家客户一套。
4. **过往人的判断**（以后）：评新交付时，带上同领域、相近标准的过往人判（好的、差的各一两条）。来源见 3.5。

**领域标签**：Task 带一个领域：财务、人力、产品、技术、其他。M2 拆 Task 时给；没给时评审第一次评时判一个，本人可以改（我定的）。

### 3.3 什么时候 AI 不下结论：「要人看」

每条验收结果在「达到 / 部分 / 未达到」之外加第四档 **「要人看」**，写一句为什么判断不了、该谁看。什么时候算「要人看」写死在代码里，不让模型自己决定（调研 3.4：模型自报的信心系统性偏高，靠不住）：

- 这条标准要的是专业结论，不是「有没有这个东西」，比如「税务处理合规」「薪酬方案公平」「架构选型合理」；
- 人力领域里，任何对某个具体员工的评价；
- 财务领域里，要判数字对不对、但材料里没有可核对的来源；
- 同一条评两次结论不一样（最便宜的一招：调研里「多次采样看一致」比让模型自报可靠）。

显示在参考评审里那一条下面；交给谁：客户上线时每个领域指定一位验收负责人。第一步先只标出来、不转人（我定的）。

### 3.4 隐私（人力、财务）

- 报告只写结论和证据位置，不摘录含个人信息的原文；交付物全文不写进本体。
- 上线文档写明「评审结论不是最终决定，最终由人确认」。个保法第 24 条：对个人权益有重大影响的自动化决策，个人有权拒绝「仅通过自动化决策」作出的决定。
- 涉及人力、财务敏感信息的客户，提醒他们按个保法第 55 条做影响评估。

### 3.5 怎么知道 AI 准不准

- **攒人的判断**：每次「我不同意」、每次人的最终验收结论，连同领域、标准原文、AI 原判存一条。现在「我不同意」已经存了，缺的是人最终的结论。
- **按领域算一致率**：人豪当「给 AI 做考核的人」（10/29 上午录音 94:35），按领域算 AI 和人一致的比例。只拿人的判断量，不拿几个模型之间是否一致量（调研 3.1：把细则改清楚能让模型之间更一致，和人的一致度却没变）。
- **门槛**（我定的，可改）：某个领域攒满 30 条人判、一致率到 80% 以前，这个领域的 AI 评审一直只作参考；到了再讨论要不要让它的结论有分量，比如成为 Co-Agent 的依据。一致率低的那类标准，默认划进「要人看」。

## 4. 客户上线清单（两件事合起来）

1. 飞书应用的读文档权限：客户的飞书租户管理员批准。
2. GitHub App：客户组织的 Owner 安装、只勾要评审的仓库（有人真交仓库链接时再做）。
3. 每个领域指定一位验收负责人：财务、人力、产品、技术。
4. （可选）上传客户自己的领域资料。
5. 隐私说明：评审结论不是最终决定；人力、财务资料怎么处理。

词元云集内部版的租户管理员和领域负责人是谁、灯塔那边由华夏谁来批，见第 6 节。

## 6. 要你定的

1. **飞书读正文这周就做吗？** 要有人在飞书开发者后台加权限、发版、批准。内部版是我们自己的租户，谁有管理员？灯塔那边要华夏的管理员批。
2. **GitHub 这个月要不要做？** 这个月有没有人真会交仓库或 PR 链接？没有就放第三批。
3. **领域负责人**：内部版财务、人力、产品、技术各由谁来当？
4. **「要人看」第一批就加，还是等第二批？** 不加的话，专业结论类的标准，参考评审也会照常给达到 / 未达到，只是不算数。
5. **私有链接读到的正文存不存？** 我建议存在天枢、跟着版本走、不进本体（2.5）。不存的话，「我不同意」重评时要再读一次原文，本人那时没权限了就重评不了。
