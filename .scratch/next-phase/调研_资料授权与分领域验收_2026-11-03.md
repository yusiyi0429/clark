## 1. 一页结论

**授权**

1. **业界几乎都是「两层」：管理员上线时开一次，个人第一次用时自己连一次。** ChatGPT Enterprise 的连接器默认关闭，由管理员开、按角色放权，用户再用自己的账号 OAuth 连【官方，摘要】；Claude Team/Enterprise 由 Owner 在组织设置里加连接器，成员各自点 Connect 登录【官方】；Glean 的 GitHub 连接器由组织管理员装 GitHub App、选仓库，每个用户再授权一次，授权前看不到私有仓库【官方】。
2. **读的时候用「本人身份」，是防越权最省事的办法。** 用户令牌天然只能读到本人有权看的东西：飞书 user_access_token「可读写的数据范围由用户可读写的数据范围决定」【官方】；GitHub App 代用户操作时「只能访问用户有权访问的资源」【官方】；Notion 公开连接按授权人身份走、每人各授权一次【官方】。
3. **用「公司服务身份」读，就必须自己做权限过滤（permission trimming）。** Microsoft 365 Copilot 连接器、Glean 都是用服务账号爬全量，再把源系统的 ACL 随每条数据存下来，在查询时按当前用户过滤【官方】。这套东西重，天枢这个月不该做。Google 的 domain-wide delegation 能冒充域内任何人，Google 自己建议「能不用就不用」【官方】。
4. **新的方向是「身份提供方托管授权」**：Claude 在 Team/Enterprise 上有托管授权，管理员通过 IdP（上线时只支持 Okta）集中配好，成员首次登录自动获得，IdP 里停用账号即同时撤销【官方】。这是「上线时就配好」的终态，但前提是客户有统一 IdP。
5. **审计和撤销靠两头：源系统自己的审计日志，加我们自己记的每次读取。** GitHub 审计日志会把代用户的调用标成「GitHub App user-to-server token」【官方】；Claude 的 M365 连接器每次 Graph 调用都进 M365 审计日志【官方】。撤销：GitHub 卸载 App 或用户撤销授权；飞书 refresh_token 只能用一次、每 365 天必须重新授权【官方】。

**分领域评审**

6. **有细则比没细则准，而且是「针对这一题的细则」最准。** 代码评分里，难题集上无细则 r=0.42，通用细则 0.56，题目专属细则 0.83【论文】；把指令拆成是/否检查清单，和人一致的比例从 46.4% 升到 52.2%【论文】；HealthBench 用 262 位医生写的逐题细则，模型评分和医生的一致度接近医生之间的一致度【论文】。天枢的「每条验收标准」本来就是题目专属细则，方向是对的。
7. **但专业领域里模型和专家的一致度明显低于专家之间。** 营养和心理两个领域，专家同意 LLM 评审 68% / 64%，专家之间是 75% / 72%【论文】。把细则改得更清楚，能让几个评审模型彼此更一致，但和人的一致度没有变好【论文，2026-10】。所以「评审是否准」只能拿人的判断去量，不能拿模型之间是否一致去量。
8. **成熟产品都把 AI 限定为「找问题、给依据」，结论由人下。** Copilot code review 默认不计入必需审批、明说会漏、要人复核【官方】；Harvey 要求人工核验、答案链回原文【官方】；MindBridge 对每笔分录打风险分、说「增强而非替代审计师判断」【官方，厂商自述】；Workday 说重大人事决定「始终留给人」【官方，厂商自述】；Lattice 反馈不够时干脆不出摘要【官方】。
9. **弃权不能靠模型自己报的信心。** 模型口头给的信心多在 80–100%，系统性偏高；多次采样看是否一致更靠谱【论文】。「信任或上交」的做法是先估「人会不会同意」，不够就交给更强的模型或人，可以把和人的一致度保证在设定水平以上【论文，ICLR 2025】。
10. **人力、财务资料有法律边界。** 个保法：对个人权益有重大影响的自动化决策，个人有权拒绝「仅通过自动化决策」作出的决定（第 24 条）；处理敏感个人信息、做自动化决策前要做影响评估（第 55 条）【官方】。欧盟 AI 法把「评估员工表现」列为高风险【二手，律所解读】。天枢「本人确认」这道门在法律上也是必要的，不能省。

**一句话建议**：这个月，飞书文档改用本人授权读正文（加一个只读 scope），GitHub 用组织装的只读 GitHub App 加本人授权读；验收结果加第四档「要人看」，按领域规则触发，不靠模型自报信心；「我不同意」攒成每家客户自己的案例库。服务身份爬全量、权限镜像、IdP 托管授权都放以后。

## 2. 授权：对照表和要点

### 2.1 企业 AI 产品怎么开连接器

| 产品 | 谁开、在哪开 | 个人要不要再授权 | 读的时候用谁的身份 | 怎么不越权 | 审计 / 撤销 | 来源 |
|---|---|---|---|---|---|---|
| ChatGPT Enterprise / Edu | 默认关闭；Owner 在工作区设置开连接器、按角色（RBAC）放权 | 要。用户在 Settings > Apps & Connectors 用自己账号 OAuth 连；GitHub 还要选可读仓库，私有仓库要组织管理员批准 App | 本人 | 「只看得到每个用户本来有权看的」；10/16 起管理员统一同步的连接器已下线，改为实时读 | 角色可收回 | 【官方，摘要】[RBAC](https://help.openai.com/en/articles/11750701-managing-feature-access-with-role-based-access-control-in-chatgpt)、[Enterprise 发布说明](https://help.openai.com/en/articles/10128477-chatgpt-enterprise-and-edu-release-notes)、[连接 GitHub](https://help.openai.com/en/articles/11145903-connecting-github-to-chatgpt) |
| Claude Team / Enterprise | Owner 在 Organization settings > Connectors 加，选哪些角色能用、能请求哪些权限 | 两种二选一：①个人各自登录；②托管授权，经 IdP（上线时只有 Okta）集中配，首次登录自动获得；两者都开时先试托管，失败再退回个人 | 本人（托管时也是本人在 IdP 里的身份） | 「访问范围由 IdP 策略和被连服务的权限决定」 | IdP 里停用账号即撤销；审计日志 180 天导出、Compliance API；M365 连接器的调用进 M365 审计日志 | 【官方】[托管授权](https://support.claude.com/en/articles/15537633-authorize-mcp-connectors-for-your-entire-organization)、[审计日志](https://support.claude.com/en/articles/9970975-access-audit-logs)、[M365 连接器安全](https://support.claude.com/en/articles/12684923-microsoft-365-connector-security-guide) |
| Microsoft 365 Copilot 连接器（原 Graph connectors） | AI 管理员在 M365 管理中心 Copilot > Connectors 建；源系统常要一个服务账号 | 不用 | 服务账号爬，按用户过滤 | 每条导入的数据带 ACL（Entra 用户/组或外部组），按邮箱映射身份；Copilot 只呈现「每个人用同样的访问控制能看到的数据」 | 管理中心可查每个连接器的权限；源系统的权限是「主参考」，变了要同步 | 【官方】[部署](https://learn.microsoft.com/en-us/microsoft-365/copilot/connectors/deployment-overview)、[数据安全](https://learn.microsoft.com/en-us/microsoft-365-copilot/extensibility/data-privacy-security)、[ACL 培训](https://learn.microsoft.com/en-us/training/modules/copilot-graph-connectors-typescript/7-ensure-secure-access) |
| Glean | 管理员装连接器；GitHub 是组织管理员装 Glean 的 GitHub App（只读、范围固定），选全部或部分仓库 | GitHub 要：用户授权后 GitHub 才返回其邮箱，之前看不到私有仓库 | 服务身份爬 + 按用户过滤 | 抓取时把源系统的权限表一起镜像，查询时按镜像过滤；也有「实时访问」直接调源系统 | 权限随源系统变化同步 | 【官方】[连接器总览](https://docs.glean.com/connectors/about)、[GitHub Cloud 设置](https://docs.glean.com/connectors/native/github/setup)、[权限 SDK](https://developers.glean.com/libraries/indexing-sdk/permissions) |

**要点**
- 两条路线：**「实时读 + 本人身份」**（ChatGPT、Claude）和 **「预先爬 + 服务身份 + 权限镜像」**（M365 Copilot、Glean）。前者轻，越权风险低；后者能做全公司搜索，但要维护 ACL 和身份映射。ChatGPT 下线了管理员统一同步的连接器、改成实时应用，说明连 OpenAI 都在往前一种收【官方，摘要】。
- Glean 的 GitHub 是两层叠加：公司层面 App 装好、选好仓库（上线时），个人层面授权一次（第一次用时）。这和用户「部署时就配好」的直觉一致，但个人那一下省不掉，因为要靠它确认「这个人是谁、能看什么」。
- 有第三方报告称 claude.ai 组织级连接器曾经全组织共用一个 OAuth 令牌【二手，[GitHub issue](https://github.com/anthropics/claude-code/issues/46207)】，与官方的「个人各自登录」说法冲突。说明「共用一个令牌」是真实存在的坑：一旦共用，就没法按人过滤。

### 2.2 平台自身的授权机制

| 平台 | 公司身份 | 本人身份 | 读一篇私有资料要什么 | 令牌寿命 / 撤销 | 来源 |
|---|---|---|---|---|---|
| **GitHub** | GitHub App 装到组织：组织 Owner（或仓库管理员）装，**选仓库**，权限细到「Contents 只读」；安装令牌 1 小时过期 | 同一个 App 的用户令牌：「只能访问用户有权访问的资源」，8 小时过期，refresh 6 个月 | App 装在该仓库 + （用本人令牌时）本人对仓库有读权限 | 卸载 App 即失效；审计日志标「GitHub App user-to-server token」 | 【官方】[App vs OAuth App](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps)、[代用户认证](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user)、[刷新令牌](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)、[审计](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/identifying-audit-log-events-performed-by-an-access-token) |
| GitHub 对比项 | OAuth App：只有 `repo` 这种大 scope，读代码就得同时拿到改代码和改设置的权限，且能访问用户所有仓库，令牌默认长期有效 | 个人 token（PAT）：组织可要求细粒度 PAT 先审批、可禁用经典 PAT | — | OAuth App 删令牌后 webhook 不会自动停 | 【官方】同上、[PAT 策略](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization) |
| **飞书 / Lark** | tenant_access_token（应用身份）：数据范围由「应用的数据权限范围」决定。读某篇文档，要先把应用加进文档：文档「…更多 → 添加文档应用」、把含机器人的群加为协作者、链接设成「组织内获得链接的人可阅读」，或把所有权转给应用 | user_access_token（本人身份）：「可读写的数据范围由用户可读写的数据范围决定」，约 2 小时；要 refresh 需申请 `offline_access`；refresh_token 只能用一次；授权满 365 天必须重新授权 | 本人身份：本人能看即可，**不用分享给应用**；应用身份：必须逐篇或按群分享给应用。scope：新版文档 `docx:document:readonly`、知识库 `wiki:wiki`（只读档另查）、表格 `sheets:spreadsheet` 等；纯文本接口 `GET /open-apis/docx/v1/documents/:id/raw_content`，无权限时返回 403/400 | 用户可撤销授权；应用权限变更要发版 | 【官方】[访问凭证](https://open.feishu.cn/document/server-docs/api-call-guide/calling-process/get-access-token)、[云文档 FAQ](https://open.feishu.cn/document/server-docs/docs/faq)、[刷新 user_access_token](https://open.feishu.cn/document/authentication-management/access-token/refresh-user-access-token)、[纯文本接口](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/raw_content?lang=zh-CN) |
| **Google Workspace** | 服务账号 + domain-wide delegation：超级管理员在 Security > API controls 授权；可冒充域内**任何**用户（含超级管理员）；scope 只限数据类型、不限冒充谁；服务账号不受域内共享策略约束；操作记在被冒充的人名下 | 普通 OAuth 同意 | DWD：冒充上传人去读；OAuth：本人读 | Google 建议「能用 OAuth 同意就别用 DWD」，用了就压最小 scope、别用密钥文件 | 【官方】[DWD 最佳实践](https://support.google.com/a/answer/14437356?hl=en)、[服务账号](https://developers.google.com/identity/protocols/oauth2/service-account#delegatingauthority) |
| **Notion** | 内部连接（静态 token）：新建时没有任何页面权限，要成员在页面「Add connections」里逐页分享，子页面跟着父页面；访问属于连接本身，分享人离职也不丢 | 公开连接（OAuth）：按授权人身份，授权时在页面选择器里选页面；每人各授权一次 | 页面必须分享给连接，或本人 OAuth 时选中 | 页面里移除连接即撤销 | 【官方】[内部连接](https://developers.notion.com/guides/get-started/internal-connections)、[公开连接](https://developers.notion.com/guides/get-started/public-connections) |

**要点**
- **GitHub App 是唯一同时满足「上线时配好」和「按人限权」的**：组织装一次、只选要评审的仓库、只给 Contents / Pull requests / Metadata 只读；评审时用这个 App 的本人令牌读，能读到的 = App 装了的仓库 ∩ 本人能看的仓库。OAuth App 和 PAT 都不该用：前者权限大且不能选仓库，后者绑在个人身上、离职就断。
- **飞书用本人身份最合适**：天枢已经有本人飞书 OAuth，只差正文 scope；不需要客户把文档分享给应用。如果改用应用身份，就得让每篇文档都「添加文档应用」或共享给群，等于把公司文档都暴露给应用，还要自己判断上传人能不能看。
- 「把资料分享给应用」（飞书应用身份、Notion 内部连接）适合固定的几个知识库，不适合评审时临时贴的任意链接。
- 自建应用新增 scope 要发新版本、由租户管理员审核【二手，[第三方 SDK 说明](https://github.com/ag9920/bitable-sdk)】。也就是说，「加一个读正文的 scope」要客户管理员点一次批准，适合放进客户上线清单。

### 2.3 四个关键问题的答案

| 问题 | 业界做法 | 对天枢的含义 |
|---|---|---|
| 用公司服务身份读，还是用本人身份读？ | 实时读的产品（ChatGPT、Claude）用本人；全量索引的（Copilot、Glean）用服务身份再按人过滤。Google 明确不推荐冒充式的服务身份 | 评审是「替上传人看他交上来的东西」，**用本人身份**。服务身份只在本人身份读不了、且客户同意时兜底 |
| 怎么保证只看得到上传人本来有权看的？ | 本人令牌天然限权；服务身份靠 ACL 镜像 + 查询时过滤（permission trimming） | 用本人令牌读就不用做过滤。**另一个风险在评审报告**：报告会被 DRI、Co-Agent、本体看到，引用的原文可能被没权限的人读到【推断】，见 4.1 |
| 上线时配，还是每人第一次用时配？ | 两层都要：管理员上线时开连接器、装 App、选范围、批 scope；个人第一次用时 OAuth 一次。Claude 的 IdP 托管能把个人那一步也省掉 | 上线清单里放「装 GitHub App、批飞书 scope」；本人在引导或第一次贴链接时连一次 |
| 审计和撤销怎么做？ | 源系统审计日志（GitHub、M365 都能区分是 App 代用户做的）+ 平台自己的日志；撤销靠卸载 App、IdP 停用、用户撤销授权、令牌短期过期 | 我们自己记一张「读取记录」：谁、哪个链接、用谁的身份、何时、成功与否；本人可在设置里断开；离职靠飞书/GitHub 侧停用自然失效 |

## 3. 分领域评审：做法对照和要点

### 3.1 按评分细则评审的方法和效果

| 方法 | 做法 | 结果（和人的一致度） | 来源 |
|---|---|---|---|
| G-Eval | 给任务说明和评价标准，让模型先自己写评审步骤（思维链），再按表格打分，用各分数概率加权 | 摘要任务上 Spearman 0.514，超过以往方法；作者提醒 LLM 评审偏爱 LLM 写的文本 | 【论文】[arXiv 2303.16634](https://arxiv.org/abs/2303.16634) |
| Prometheus（1、2） | 专门训练的开源评审模型，评审时必须给它用户自定义的评分细则 | 1 代在人写细则上与人 Pearson 0.897，与 GPT-4（0.882）相当；2 代同时支持打分和两两比较 | 【论文】[arXiv 2310.08491](https://arxiv.org/abs/2310.08491)、[arXiv 2405.01535](https://arxiv.org/abs/2405.01535) |
| 题目专属细则（代码评分） | 对比无细则、通用细则、每题专属细则 | 难题集（DSA）：无细则 r=0.423，通用 0.562，专属 **0.825**；简单题集（OOP）：无细则 0.717，通用和专属都约 0.90 | 【论文】[arXiv 2503.23989](https://arxiv.org/html/2503.23989v1) |
| TICK 自动生成检查清单 | 让模型把指令拆成一串是/否问题，逐条判 | 和人完全一致的比例 46.4% → 52.2%；给人看清单，人之间一致度也提高（0.194 → 0.256） | 【论文】[arXiv 2410.03608](https://arxiv.org/abs/2410.03608) |
| HealthBench（逐题专家细则） | 262 位医生为 5000 段对话写专属细则，模型按细则逐条判 | 模型与医生的一致度和医生之间相当 | 【论文】[arXiv 2505.08775](https://arxiv.org/abs/2505.08775) |
| RubricRAG（领域知识检索生成细则） | 现成模型自己写的细则和人写的对不上；从相近题目的人写细则里检索来生成 | 生成的细则更像人写的，下游评审更好（摘要未给数字） | 【论文】[arXiv 2603.20882](https://arxiv.org/abs/2603.20882) |
| 反例：只改清楚细则 | 挑模型之间分歧最大的条款改写 | 模型之间一致度升了，和人的一致度**没有变化** | 【论文】[arXiv 2610.13303](https://arxiv.org/abs/2610.13303) |
| 专业领域的天花板 | 营养、心理两个领域，LLM 评审 vs 专家 | 专家同意 LLM 68% / 64%，专家之间 75% / 72%；作者结论是专家必须留在评审环节 | 【论文】[arXiv 2410.20266](https://arxiv.org/abs/2410.20266) |
| 通用评审偏差 | MT-Bench 研究 | 强模型和人的一致度可达 80% 以上（与人之间相当），但有位置偏差、啰嗦偏差、偏爱自己 | 【论文】[arXiv 2306.05685](https://arxiv.org/abs/2306.05685) |

厂商指南也一样：Anthropic 的评测文档要求「细则要详细清楚」「输出要具体（对/错或 1–5 分）」「打分前先推理」，评审模型最好和生成模型不是同一个【官方】([Claude 文档](https://platform.claude.com/docs/en/docs/test-and-evaluate/develop-tests))。

**「带细则和不带细则差多少」**：没有跨领域的统一数字【未找到】。能找到的是：代码评分难题上相关性从 0.42 到 0.83；通用指令上完全一致率加约 6 个百分点。可以得出的结论是：**细则越具体到这道题，提升越大；题目越难、越需要判断，提升越大**。

### 3.2 领域知识怎么给到评审

| 方式 | 业界例子 | 适合天枢的程度 |
|---|---|---|
| 领域检查清单 / 评审指南 | Google 工程实践的代码评审指南：设计、功能、复杂度、测试……设计最重要【官方】([Google eng-practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html))；Copilot code review 读仓库里的 `.github/copilot-instructions.md`、按路径的指令文件，还会读 CLAUDE.md、REVIEW.md【官方】([GitHub 文档](https://docs.github.com/en/copilot/tutorials/customize-code-review))；CodeRabbit 用 `path_instructions` 按文件路径挂指令，用 `code_guidelines` 引用团队规范【官方】([CodeRabbit](https://docs.coderabbit.ai/configuration/path-instructions)) | 高。天枢可以按「领域」挂一段短清单，客户可以替换成自己的 |
| 题目专属细则 | HealthBench（医生逐题写）、代码评分专属细则 | 已有：Task 的验收标准就是专属细则，质量取决于 M2 拆得多细 |
| 示例库（好的 / 差的交付） | CodeRabbit 的 learnings：评审时用户用自然语言说的偏好会被记住，下次同仓库评审时用上，可设管理员审核窗口 0–30 天【官方】([配置参考](https://docs.coderabbit.ai/reference/configuration))；RubricRAG 从相近题目检索人写细则【论文】 | 中。先攒「我不同意」和最终人判，再用。示例库对 LLM 评审准确度提升多少，没找到可靠数字【未找到】 |
| 领域内部资料作依据 | Harvey 建议附上文件或选知识源，让答案基于审过的资料，每个答案链回原文【官方】([Harvey 帮助中心](https://help.harvey.ai/articles/getting-started-with-harvey)) | 以后。客户的制度、月结清单、职级标准可以作为评审依据上传 |

财务月结清单、人力合规要点这类**领域清单拿来给 LLM 评审用、效果有多少**，没找到研究【未找到】。清单本身是会计、人力行业的常规工具，可以借，但效果要自己量。

|---|---|---|---|---|

**要点**
- **共同点：AI 给「问题清单 + 依据」，人给结论。** 越是人力、财务、法律，越明确「不替人下结论」。
- **限定范围的办法**：①只评有依据的部分（MindBridge 的控制点、Harvey 的知识源）；②明确排除评不了的东西（Copilot 不评依赖文件）；③证据不够就不出（Lattice）。
- **代码领域最成熟**：规范放在仓库里、按路径挂指令、从反馈里学。别的领域可以照这个结构做，「仓库」换成「客户的领域清单」。

### 3.4 风险和弃权

| 风险 | 证据 | 业界应对 |
|---|---|---|
| 一本正经地错 | 专业领域里 LLM 与专家一致度比专家之间低 7–8 个百分点【论文，[2410.20266](https://arxiv.org/abs/2410.20266)】；法律引用幻觉检测最好的模型 F1 只有 68.8%，「内容曲解」最难查【论文，[2606.21155](https://arxiv.org/pdf/2606.21155)】 | 每个结论必须引证据位置；领域专家定细则；定期拿人的判断量一致度 |
| 该说「判断不了」时不说 | 口头信心集中在 80–100%，系统性过度自信；多次采样看一致性比让它自报更好【论文，[2306.13063](https://arxiv.org/abs/2306.13063)】 | 选择性评估：先估「人会不会同意」，低于阈值就上交更强模型或人，可保证一致度不低于设定值（如 80%，覆盖约 80% 样本）【论文，[Trust or Escalate](https://proceedings.iclr.cc/paper_files/paper/2025/hash/08dabd5345b37fffcbe335bd578b15a0-Abstract-Conference.html)】；弃权的综述把它分成「问题本身答不了 / 模型不知道 / 价值上不该答」三类【论文，[2407.18418](https://arxiv.org/abs/2407.18418)】；阈值按问题类别分别设【二手】 |
| 只看模型之间是否一致 | 改清楚细则让模型更一致，但和人不更一致【论文，[2610.13303](https://arxiv.org/abs/2610.13303)】 | 校准要用人的标注，不用模型投票代替 |
| 人力、财务资料的隐私 | 个保法第 28 条：金融账户、医疗健康、特定身份等属敏感个人信息，须有特定目的、充分必要、严格保护；第 24 条第 3 款：对个人权益有重大影响的自动化决策，个人有权拒绝「仅通过自动化决策」作出的决定；第 55 条：处理敏感信息、做自动化决策前要做影响评估【官方，[网信办全文](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)】；欧盟 AI 法把评估员工表现列入高风险，相关义务推迟到 2027 年【二手，[律所解读](https://www.faegredrinker.com/en/insights/publications/2026/6/draft-commission-guidelines-on-high-risk-ai-implications-for-the-workplace)】 | 人做最终决定；只读必要内容；报告少引原文；客户做影响评估 |

## 4. 给天枢的建议

### 4.1 授权

**原则**（由第 2 节推出）：
- **读的时候用上传人本人的身份。** 评审 = 替上传人看他交的东西，本人令牌天然不越权，不用自己做权限过滤。
- **公司层只做两件事：开通道、圈范围。** 装 App、批 scope、选仓库，不给天枢一把能读全公司的钥匙。
- **报告不能比原文更公开**【推断】。原文的权限由源系统管，评审报告却会被 DRI、Co-Agent、本体看到。报告里只写结论、理由和证据位置（第几节、哪个文件哪一行），引用原文不超过一两句；从私有链接读到的全文不进本体，也不长期存。

**这个月能做的最小版本**

| 资产 | 客户上线时配什么（管理员一次） | 每人配什么（第一次用时） | 用谁的身份读 | 怎么不越权 |
|---|---|---|---|---|
| 飞书文档 / 知识库 / 表格 | 在天枢的飞书自建应用里加用户身份只读 scope：`docx:document:readonly`，知识库和表格的只读 scope 按开发者后台实际名称加；发新版本，请客户租户管理员批准。写进上线配置清单 | 本人已连过飞书的，重新授权一次补上新 scope；没连过的，在第一次贴飞书链接时弹「连接飞书」 | 本人 user_access_token | 飞书接口按本人权限返回，读不到就 403；报告写「你在飞书里没有这篇的读权限」，不退回应用身份去读 |
| GitHub 仓库 / PR | 天枢建一个 GitHub App，权限只要 Contents、Pull requests、Metadata 只读；客户组织 Owner 装到组织，**只选要评审的仓库** | 第一次贴 GitHub 链接时，本人授权这个 App 一次（拿用户令牌） | 本人的 GitHub App 用户令牌 | 能读的 = App 装了的仓库 ∩ 本人能看的；不用 OAuth App、不收 PAT |
| 公开网页 | 无 | 无 | 服务端匿名取 | spec 5.4 已定：只放 http/https、不连内网地址、限大小和超时 |
| 内部网站、其他系统 | 无 | 无 | 不读 | 照 spec：标「打不开 · 请导出后上传」；页面可以截图上传（spec 已放开图片） |

再加两样：
- **读取记录**：每次读外部链接记一行（谁、哪个链接、哪种身份、时间、成功或失败原因）。本人能在交付物版本上看到「这一版读过哪些链接」。这就是审计。
- **撤销**：设置里能断开飞书、GitHub；断开后删本地令牌。离职由客户在飞书 / GitHub 停用账号，令牌自然失效（GitHub 用户令牌 8 小时、飞书约 2 小时过期）。

工作量判断【推断】：飞书这条最小，api 已有本人 OAuth 和刷新，加 scope 和一个读正文的函数即可。GitHub 是新集成（App 注册、安装回调、用户授权、存令牌），大约一个独立小单。建议这个月先做飞书，GitHub 看客户是否真的大量交 PR 再定。

**以后**
- **IdP 托管授权**：客户有统一身份（飞书本身就是很多客户的 IdP）时，参照 Claude 的托管授权，让首次登录天枢即自动带上读文档的授权，省掉个人那一步。
- **客户内网资产**：内网网站、私有 GitLab、自建 Wiki。可在客户网络里放一个只读取件程序，或用浏览器插件以本人登录态把页面抓下来交给天枢。这两种都没找到业界标准做法【未找到】，要按客户情况单独设计。
- **服务身份兜底**：本人读不了、但公司认为这份资料该让评审看到时（比如上传人已离职、资料归团队），由管理员显式授权用应用身份读一次，并记审计。默认关。
- **全公司索引和权限镜像**（Glean / Copilot 那套）：只有当天枢要做「在全公司资料里找证据」时才需要，评审本人交的东西用不上。
- 不建议走 Google domain-wide delegation 这类「冒充任何人」的路线。

### 4.2 分领域验收

**原则**（由第 3 节推出）：
- **懂领域主要靠细则，不靠模型自带知识。** 验收标准越具体到这个 Task，评得越准。领域清单是第二层，补的是验收标准没写、但这个领域人人都会查的东西。
- **结论分清「没证据」和「判断不了」。** 现在 spec 是没证据判 ✗，这条保留；新加的是「证据在、但要专业判断才能下结论」，这时 Agent 不下结论。
- **弃权靠规则和一致性检查，不靠模型自报信心。**
- **准不准拿人的判断量**，不拿模型之间是否一致量。

**这个月能做的最小版本**

1. **Task 带一个领域标签**：财务、人力、产品、技术、其他。M2 拆的时候给；没给就由评审 Agent 第一次评时判一个，本人可改。
2. **每个领域一段短清单（5–8 条），写进评审提示词**。只写「这个领域交付时人人都会查的」，例如：
   - 技术：有没有测试或运行证据、改动范围是否和描述一致、有没有安全或数据风险（参照 Google 代码评审指南）；
   - 财务：数字口径和期间是否写清、能否和来源对上、有没有审批或复核痕迹；
   - 人力：涉及具体员工的结论有没有依据、有没有敏感个人信息外露；
   - 产品：有没有真实用户或试用证据、验收场景是否走通。
   清单只用来**补问**和**提醒**，不额外扣分：Task 的验收标准才是判达标的依据。清单内容由我们先写草稿，请对应领域的人（客户或内部）改一遍【推断】。
3. **每条验收结果加第四档「要人看」**（与 ✓ / ◐ / ✗ 并列），写一句「为什么我判断不了、该谁看」。触发规则（写死在代码里，不让模型自己决定要不要弃权）：
   - 这条标准要的是专业结论，不是事实是否存在，比如「税务处理合规」「薪酬方案公平」「架构选型合理」；
   - 人力领域里，任何对**某个具体员工**的评价；
   - 财务领域里，数字是否正确、但交付物里没有可核对的来源；
   - 同一条评两次（不同温度或换顺序）结论不一样。这条最便宜，直接借「一致性比自报信心可靠」的结论。
   「要人看」的条目和「本人有异议」一样**不能直接提交**。这个月由本人在确认时自己判；有指定的领域负责人以后再转给他。
4. **「我不同意」和最终人判全部留档**，带领域标签、标准原文、Agent 原判和人判。这就是以后的示例库和考核集。人豪做「给 AI 做考核的人」时，直接拿这份算一致率。
5. **隐私最小化**：人力、财务领域的交付物，报告只写结论和证据位置，不摘录含个人信息的原文；不把交付物全文写进本体。

**以后**
- **按领域、按客户量一致率**：每个领域攒到几十条人判以后，算 Agent 和人的一致率；某领域某类标准一致率低，就把这类标准默认划进「要人看」。这就是按类别设弃权阈值，参照 Trust or Escalate。
- **示例库**：评新交付时，检索同领域、相近标准的过往人判（好的、差的各一两条）放进提示词，参照 RubricRAG 和 CodeRabbit learnings；新学到的规则要客户管理员或领域负责人审过才生效（CodeRabbit 有 0–30 天审核窗口）。
- **客户自己的领域指南**：上线时让客户上传自己的月结清单、职级标准、技术规范，作为评审依据（Harvey 知识源 / Copilot 指令文件的思路），每家客户一套。
- **「要人看」转给指定的人**：每个领域在客户上线时指定一位负责人，「要人看」的条目推给他确认，结果回到报告。
- **合规**：在客户上线文档里写明「评审结论不是最终决定，最终由本人确认」，以满足个保法第 24 条；涉及人力、财务敏感信息的客户，提醒他们按第 55 条做影响评估。
- **评审模型和生成模型分开**（Anthropic 建议）：本人如果用 AI 写交付物，评审别用同一个模型。
