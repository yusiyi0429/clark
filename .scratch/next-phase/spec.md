## 1. 为什么改

- 自动生成执行事项没有意义，而且让人反感。采集「具体做了什么」像微观管理，几乎没人愿意被这样记，本体也不该留这些琐碎内容。
- 价值在两样东西上：产出物，以及向最终目标推进了多少。
- 孙铭泽 10/29 17:54 在群里回溪南时，把重心又说了一遍：
  - 现版本的 DRI 页面按 Mission → Task → Activity 逐级展示。Activity 靠会议和外部 AI 对话收集，用来帮人维护进展，同时存进本体；
  - 后续版本去掉这一块，天枢不再把 Activity 的进展自动载入、显示在主页；
  - 设计以「Task 的状态」和「影响状态的交付物」为重心；
  - Activity 弱化成辅助推进 Task 和它的衍生物的工具（原话打成了「辅助推荐」，你确认是「推进」）。
- 分工会把这件事说得更彻底：系统里只关心交付物版本的变化（V1 到 V2），所有东西都围绕它（分工会 1:07:18）。要记的是变化和「为什么」，事实只是节点（分工会 27:28）。
- 所以天枢从「替你记事」转成「帮你把交付物做到达标」。事情由人自己建，Agent 的精力花在按验收标准评判交付物、陪人迭代，以及在每个版本节点上说清「这一版为什么变了」。
- 之前刻意弱化了 Agent 的人感，现在反过来：它要像一个常驻在旁边、说话简短、会鼓励人的同事。
- 会上的原话（录音里没区分出这几段是谁说的）：
  - 每 30 分钟抓一次「逐渐就变成 1984 了」，收东西要「按目的去收」，「微观管理没有意义」（录音 55:00、66:52、67:47）；
  - 收的目的是转起数据飞轮，让 Agent 知道大家到底在干什么，这样才帮得上忙（录音 55:00、70:22）；
  - Agent 要当成人来看，平台界面只是它的「场子」，不是它本身（录音 91:34、92:32）；
  - 「为什么越多，这个系统会越聪明」（分工会 27:28）；
  - 「我们永远要避免自己变成钉钉」（分工会 46:25）。

## 2. 目标、非目标、反目标

**目标**
1. 天枢不再定时采集。
   - 每天的进展靠斯一的 skill 写本体，天枢只读；会议靠 Nexus 会后写入。
   - 天枢里发起的收集只有四种：说说现状、交付物证据、确认后的跟进、补齐本体缺口。按请求在本机收，原文不出本机，本人在天枢确认才存。
   - 天枢每天给本人一张自动复盘卡，看不看随意。
2. 执行事项只由人建；天枢里任何地方都不再自动生成执行事项。
3. 选中 Mission、再选中 Task 后，页面以这个 Task 的状态和影响状态的交付物为中心：上传，或者用对话说现状。
4. 围绕版本节点转：
   - 天枢 Agent 按验收标准看交付物达没达标，陪人迭代，达标才能提交；
   - 提交时，Agent 写「这一版为什么变了」，用鼓励的口吻给本人看，不点叉就算认可；
   - Co-Agent 收到新版本，按目标和评估标准评一次，写进展和风险。
5. Agent 以一个胶囊形象常驻在对话窗上方，说短句。
6. 会议：会前预约归天枢；会中、会后归 Nexus；Nexus 提取出的改动、冲突和执行事项，经天枢 Agent 推到本人工作台，由本人处理。
7. 天枢和 Nexus 分清场子：个人对话归天枢；多人聊天和会议归 Nexus；战场、分析结果、洞察进展的数据源是 Nexus，天枢负责呈现。两边界面统一。

**非目标**
- Task 下的 Activity 怎么建不再设计，随各人习惯。
- 交付物格式不预先规定，文档、链接、图片、一段说明都行。
- Task 的增删改不在天枢做。Task 在敲定 Mission Card 时就定了，归 M2。
- 不做多皮肤商店、语音、实时视频形象（Meta Muse 那种）。
- 天枢不做会中、会后整理和会议写入（归 Nexus）。
- 天枢不自己编战场分析（数据源是 Nexus，分工会 07:13）。
- AI 和 AI 之间产生的信息先不考虑（分工会 09:00–09:46）。

**反目标**（即使功能跑通，出现这些也算失败）
- 天枢又在记「你今天做了什么」的流水账，或者把个人的日进展细节摊给别人看。
- 把每天的进展发到群里，变成半日报（分工会 31:27–33:03）。
- 开完会让人点一大堆确认（分工会 14:04）。
- 记下来的全是「是什么」，没有「为什么」（分工会 27:28）。
- Agent 当考官刁难人：只给分不说缺什么，或者凭空判「未达到」。
- Agent 的报告只是把进展汇编一遍，没有判断。会上对 Nexus 会议总结的评价就是「汇编的无脑 PMO，只看进展」（录音 90:19）。
- Agent 反应慢。会上有人问一句「进展怎么样」，它「判断意图」判断了 300 秒，最后回了一句「你到底想干啥」（录音 85:33）。
- Agent 说套话、说大话、动不动长篇。
- 胶囊形象抢注意力、显得幼稚。外界对 Meta Muse 的吉祥物 Jolly 就有「把用户当小孩」的批评。
- 界面上出现解释句。

## 3. 约束

- 模块边界照旧：`apps/web` 只做展示和 API 客户端；评审、状态、存储都在 `apps/api`；契约先改 `packages/contracts` 再生成客户端。
- 各方归属：
  - 本体写入规则归斯一，他也负责卡住越权和乱写（分工会 13:29）；
  - Chat 服务和人设归人豪；
  - M2、Co-Agent 和 Nexus 归溪南，Nexus 主责会议和多人场景（分工会 01:26、04:00）。
  凡是要动他们那一侧的，先对齐再做。
- 不推送、不开 PR、不部署，除非孙铭泽说。流程照旧：测试计划，我在浏览器自测，他测，然后才推送或通知别人。
- 界面不写说明句；新界面复用 ts-design 的组件和主题变量、现有卡片样式，不加新颜色。
- 异步的事（评审、写版本说明）要显示实时阶段和已用时间，不让人干等。
- 新迁移从现有最大号往后编（现在到 217，MVP 段从 200 起）。

## 5. 设计

### 5.0 整条链路

**一个 Task 的一个月**
1. **月初**：M2 拆出 Mission 和 Task，带目标、验收标准和版本节点。Co-Agent 把每个 Task 的进展记成 0。
2. **平时**：
   - 本人和天枢 Agent 一起推进 Task，做交付物。Activity 随本人习惯，天枢不收。
   - 外部工具里的工作由斯一的 skill 每天收，写进本体，天枢读来给 DRI agent（5.1）。
   - 本人在天枢里点「说说现状」「从我电脑里找」这类，由本机按请求收（5.1）。
   - 会议由 Nexus 开完会直接写进本体（5.6）。
   - 天枢每天给本人一张自动复盘卡（5.1）。
3. **版本节点**：
   - 本人上传新版本，或者用对话说现状。天枢 Agent 按验收标准看达没达标，没达标就陪着改（5.4）。
   - 达标后本人点一次提交。Agent 写「这一版为什么变了」，用鼓励的口吻推给本人，不点叉就写进本体（5.4）。
4. **Co-Agent**：收到新版本，按目标和评估标准评一次，写进展（0 或 1）和风险。
5. **回到天枢**：显示 Co-Agent 的结论，Task 状态、战场进展都用这份数据（5.3）。超过计划时间还没有新版本，Agent 来问卡在哪（5.5）。

**一场会**（孙铭泽 10/29 晚上定）
1. 会前预约：归个人 DRI Agent（天枢）。
2. 会中：Nexus 接管。
3. 会后：Nexus 整理会议，写进存储和本体对应的位置。
4. 推送：Nexus 提取出两类内容，交给本人的 DRI Agent，由它推到本人的工作台：
   - 某个事项或事件有改动或冲突，推给对应的负责人；
   - 判定为执行事项的，推给对应的负责人。

### 5.2 Task 的状态由交付物推动；执行事项人建

**核心选择**：交付物挂在 **Task** 上，不挂在执行事项上；Task 的状态跟着交付物走。10/29 17:54 你在群里定的重心也是这两样：「Task 的状态」和「影响状态的交付物」。分工会也说先以 Task 为单位（分工会 1:14:42）。

理由：
- 你说 Task 的边界就是「有没有一个从发布到验收、状态会变的迭代版本」，这个迭代版本就是交付物。
- Activity 交给个人习惯以后，粒度各人不同，挂在上面评判不稳定。分工会上也说 Activity 可能只是一份文档，太碎（分工会 1:14:29）。
- 页面也是选中 Task 再看交付物。

**版本节点**：
- 每个 Task 有计划好的版本节点（比如 v1 初稿、v2 评审版），每个节点有能被评估的完成标准（分工会 1:13:25–1:13:45）。节点和标准由 M2 拆解时给出（第 7 节第 2 条）。
- 进展只有 0 和 1：到了下一个节点就是 1，没到就是 0（分工会 55:32）。进展由 Co-Agent 写。
- 在 M2 给出版本节点之前（我定的）：一个 Task 只当作一个节点，用它的验收标准评。

**交付物的样子**：
- 一个 Task 一个交付物，交付物有多个版本：v1、v2、v3……本人上传的每一份都算一个版本；提交了的版本才算到了节点。
- 一个版本是下面两种之一：
  - 一组材料：文件、链接、图片，可附一句话；
  - 一段现状说明：通过对话形成的文字。
- 每个版本自动评审一次，评审结果跟着这个版本存。
- Task 的状态（我定的），由交付物推动：

| 状态 | 什么时候进入 | 下一步 |
|-|-|-|
| 未开始 | 还没有版本 | 上传或说现状 |
| 迭代中 | 有版本，最新版没达标，或者达标了还没提交 | 改了再传、提交 |
| 已提交 | 提交了某个达标版本 | Co-Agent 评；评之前本人可以撤回 |
| 已到节点 | Co-Agent 评过，进展记 1 | 往下一个节点做；最后一个节点到了，等人在本体里确认完成 |
| 没到节点 | Co-Agent 评过，进展还是 0，带风险和一句理由 | 回到迭代中，理由并进下一次评审 |

- 本体里 Task 也有自己的状态。第一批这套状态只存在天枢里；以后「已提交」「已到节点」怎么对应到本体里 Task 的交付和确认完成，和 5.4 的写本体一起由斯一定。
- 谁能上传、提交（我定的）：这个 Task 的负责人。同一 Mission 下的其他人只读。
- 存储（我定的）：新表存版本、评审报告、提交、版本说明和 Co-Agent 的评判；文件沿用材料上传，`object_type` 加一种指向交付物版本。交付物和评审是天枢自己的业务数据。「提交」「版本说明」「评判」是公司事实，按 ADR-0027 最终要进本体，见 5.4。

**执行事项**：
- 只剩一个来源：人自己建，在页面上建，或者明确叫 AI 工具建。会议里出来的执行事项，本人接手也算人建（5.6）。
- 页面上退到次要位置，见 5.3。现有的本人逐条验收保持不动，因为本来就是人在确认。
- 定位：Activity（执行事项）是本人用来推进 Task、做出交付物的辅助工具，不是天枢要收集、要展示给别人的东西（17:54）。
- 不再自动建：
  - 采集器本来就不建；
  - MCP 的说明改成「只在用户明确要你建时才建」，同时去掉「主动记进展」（采集只留斯一一套，见第 6 节第 4 条）；
  - 会后分派改成 Nexus 推来的执行事项卡、本人接手，见 5.6。
- 「一件 = 一个带 ◆ 关口的 Activity、1–2 周」这条粒度要求不再强制，MCP 说明里一并删掉。

**各状态的样子**：
- 未开始：上面一排验收标准（让人知道按什么评），下面一大块上传区（拖进来、点选、贴链接），旁边是「说说现状」。没有任何说明文字。
- 评审中：版本卡上显示当前阶段（读材料、对照第 2 条……）和「已用时间 / 预计时间」。
- 有报告：达标度圆环加「几条达到」，每条一行：✓ 达到、◐ 部分、✗ 未达到，后面一句理由。展开后看证据（引用交付物里的哪一处）和建议怎么补。
- 已提交：版本锁定，下面是「这一版为什么变了」那张卡（5.4），显示交给 Co-Agent 多久了，可以撤回。
- 已到节点或没到节点：显示 Co-Agent 的结论和一句话；没到节点以后回到「有报告」那一态。
- 版本条：v1 62 · v2 78 · v3 100 ✓，点哪个看哪个的报告。
- 我的事项：默认折叠，只列挂在这个 Task 上的人建事项，沿用现有卡片样式，可以在这里新建。

**上传交付物**：
- 面板里拖进来或点选，生成新版本，马上开始评审。

- 第二批在对话里也能传：文件拖进对话，Agent 只问一句「算『上手流程』的 v3？」，你说是就存。

**用对话说现状**：
- 点「说说现状」，对话窗带上这个 Task 开口，一句话起头。有昨天的日进展就拿它起头：「日进展说你把录屏做完了，还差测试记录？」

- 评审出来以后，对话里只说一句结论（「3/4 条，差第 4 条：缺一次真人试用」），细节看面板。

- 怎么给、给什么，要和溪南定（第 7 节）。第一批两页照旧，不改。

### 5.4 Agent 评判：达标、提交、版本说明、Co-Agent 评

**按什么评**：
- 首选这个 Task 在本体里的验收标准（acceptance_criterion），没有就用 Task 的完成定义加 Mission 的成功证据。报告里标明按哪套标准评的（我定的）。
- 两样都没有时不评，面板显示「没有可对照的标准」这一态，只放一个找负责人补标准的入口。
- 你要的是「体验」层面的详细验收标准，这要在敲定 Mission Card 时由 M2 产出，见第 7 节第 2 条。

**怎么评**（我定的）：
- 只按版本里有的证据判。没证据就判 ✗，并写清缺什么证据（比如「缺一段新人 3 分钟内走完上手的录屏」），不替人猜。
- 每条三档：达到、部分、未达到。每档都有一句理由、引用的证据位置、具体怎么补。
- 达标度 = 各条平均（达到 100、部分 50、未达到 0）。它只说明离提交还差多少，不叫「进展」：进展是 Co-Agent 写的 0/1。
- 达标 = 每一条都「达到」，这时才能提交。这就是分工会上说的质量基线：基线都没达到，就不够提交（分工会 43:56）。
- 评新版本时，带上上一版的报告和 Co-Agent 的理由，报告里说清这一版比上一版多达到了哪几条。
- 文件能读的就读：文档、PDF、图片；链接能读就读，读不了就在报告里说「这个链接我打不开」，请人导出上传（我定的）。
- 用重模型，异步跑，显示阶段和用时。复用现有的作业队列和对照完成标准起草验收的写法。

**判错了怎么办**（我定的）：
- 每条 ◐ 或 ✗ 旁边有「我不同意」，写一句为什么。Agent 带着这句话重评这一条。重评还是不过，这一条保留「本人有异议」的标记。
- 有异议的条目要不要也能提交，待定。按你说的「达标后才能提交」，默认不能。

**提交和「这一版为什么变了」**（分工会 1:07:18–1:10:38）：
- 达标后本人点一次「提交」。
- 天枢 Agent 接着写这一版的说明，按时间顺序取：
  - 上一版到这一版之间本人和天枢的对话；
  - 这段时间的日进展；
  - 本体里挂在这个 Task/Mission 下的会议事件（Nexus 写的）；
  - 两版交付物本身的差别。
- 说明写三样，几句话就够：这一版比上一版多做到了什么；为什么变了（判断怎么变的、用了什么新方法、外部信息有什么变化）；有什么经验或教训。只写「为什么」和变化，不复述做了哪些事。
- 口吻是鼓励：先说达成了一个新节点，再说总结出的几条（分工会 48:25）。
- 出现在已提交版本下面，胶囊在对话里说一句。本人可以改、可以点叉不要。不点叉，就算本人认可的判断（分工会 1:10:38）。
- 两道门叠在一起时（我定的）：本人只点一次「提交」；说明卡默认认可，不再要第二次确认。这样做到了「达标才能提交」，又不让人点一大堆。
- 版本说明写进本体时，是这个 Task 的「判断」和「版本」两个字段，只能由天枢 Agent 写（分工会 1:12:04）。字段和洞察对象的结构要斯一定（第 7 节第 6 条）。

**Co-Agent 评**：
- 下一方定了，是 Co-Agent（分工会 55:32–1:01:51）。它站在公司立场，只在收到新版本时评一次：按 Task 的目标和评估标准看这一版到没到节点，写进展（0 或 1）和风险。它不管过程，过程是本人和他的 Agent 的事。
- 交接（我定的，要溪南、斯一同意）：经本体。天枢把提交写进本体（版本链接、达标报告摘要、版本说明），Co-Agent 读了评，结论写回本体，天枢读回来显示。
- 本体的规矩是「确认完成和各道门只由人记」（tkos-world 的服务说明）。所以 Co-Agent 的结论只算一条评判；最后一个节点到了以后，Task 在本体里的确认完成还要人记。谁来记，第 7 节第 1 条。
- 版本可能倒退（分工会 1:09:45）：新版本比上一版差时，Co-Agent 可以把进展记回 0，天枢照实显示，版本说明里写清退在哪。具体判法待和溪南定。
- 第一批「提交」「版本说明」只记在天枢里；写进本体用一个开关挡着，默认关，等斯一定好写入方式再开。Co-Agent 那一步第二批再接。

### 5.5 Agent 更像人：胶囊形象和短句

**参考**（10/29 查的）：
- Meta Muse：9 月上线的个人 Agent，形象是奶白色圆胖的 Jolly，名字和穿着可以自己改。
- OpenAI Dots：9 月 29 日发布，每个 Agent 是一个「冒泡的小团子」角色，可以选形象、宠物，起名字，定位是「一起干活的伙伴」。
- Claude Duet：10 月 21 日预览，主动型 Agent，早上给简报，敏感动作先问。

我从这三个里取：
- 有一个可辨认、可以起名的角色；
- 常驻、主动，但每次只说一点；
- 要做重要的事先问。

不取：实时视频形象、让人产生依赖的陪伴感。

会上的说法（录音 91:34–103:41）：
- 平台只是它的场子；
- 要想它还能以什么方式出现；
- 你们在给它「造脸、造手、造嘴」；
- 最好大家工作方式不变，它也能嵌进来。

分工会上又说，它对本人是个「好朋友」，帮着做、给鼓励；Co-Agent 才是给结果打分的那个（分工会 1:01:27）。

所以胶囊不是首页的一个装饰，而是「你的 Agent」这个人在天枢里露的脸。以后它在飞书里也应该是你自己的那个 bot，而不是一个叫「天枢」的独立身份（录音 76:03，第二批以后）。

**胶囊**：
- 位置：对话窗顶部，替掉现在那行「我的对话」。
- 样子：一个横向小胶囊，左边是角色头像（第一批只做一个熊猫），右边是名字。高度和现在的标题行差不多，用 ts-design 的主题色，不加新颜色。
- 状态靠动作表达，不配文字：

| 状态 | 动作 |
|-|-|
| 空闲 | 偶尔眨眼 |
| 你在输入 | 看向输入框 |
| 在想 | 轻轻点头，评审等长任务旁边带阶段和用时 |
| 在说 | 嘴动 |
| 有事找你 | 胶囊轻跳一下，带一个小点 |

- 点胶囊展开一张小卡：名字、形象。第一批只能改名字，其余后面再做（我定的）。
- 同一个胶囊出现在所有和「我的天枢」对话的地方：首页、二级页面的对话栏、手机版的对话页。
- 以后还会出现在溪南那边：Co-Agent 页里嵌的个人对话，M2 复盘页里「我的 Agent」的头像。会上说过那个头像是临时的，应该由你来设计（录音 40:53）。和 Nexus 界面的视觉统一，见第 7 节。
- 形象我先画一版简单的扁平 SVG 熊猫给你看，定稿再换（我定的）。画风参照你定过的「无边框、自然」。

**说话方式**（写进人设，第一批改本地运行时，正式环境的人设由人豪改）：
- 默认一到两句，一般不超过 40 字。一次只问一件事。
- 不说套话（「好的！我来为您……」），不说大话（「非常出色的进展！」），不主动列清单。
- 鼓励要具体：说达成了哪个节点、哪一点做得好，不说空的夸奖（我定的）。这样和上一条「不说大话」不冲突。
- 要长内容时（报告、文档），正文放到面板或文档里，对话里只说一句指过去。
- 可以把一段回复拆成两三个短气泡，像人连着发几条（我定的）。
- 像同事一样接着昨天说话，凭的是日进展和交付物的版本记录。不知道就说不知道。
- 先快速回一句再去想。像「进展怎么样」这种问题，不能让人等几分钟（录音 85:33 那次等了 300 秒）。要想久的事，胶囊进入「在想」，对话里先说一句「我看一下」（我定的）。
- 主动开口只在这几个时候：
  - 当天第一次打开（一句现状加一个问题）；
  - 评审出了结果，或者版本说明写好了；
  - 每天的自动复盘卡出来了（5.1）；
  - 过了计划时间还没有新版本，问一句卡在哪（分工会 39:12；时间怎么算待定）；
  - 没有日进展来源的人，每天晚上问一句今天推进到哪了（5.1 的 C）。
- 不推送，不刷存在感。

**游戏化**（分工会 49:26–50:56，做到哪待定）：
- 会上提了：任务明确且短、达成有快速的小反馈、大目标有大反馈，以后配能量、钻石这类激励。
- 我的建议：第一批只做鼓励的口吻和版本条上的节点进度；能量、钻石这类等激励规则定了再做。

### 5.6 会议：会前归天枢，会中会后归 Nexus

**流程**（孙铭泽 10/29 晚上定）：
1. 会前预约：归个人 DRI Agent（天枢）。
2. 会中：Nexus 接管。
3. 会后：Nexus 整理会议，写进存储和本体对应的位置。
4. 推送：Nexus 提取出两类内容，交给本人的 DRI Agent，由它推到本人的工作台：
   - 某个事项或事件有改动或冲突，推给对应的负责人；
   - 判定为执行事项的，推给对应的负责人。

**依据**（分工会 10:37–14:23）：
- Nexus 固定做会后总结和写入，不让人逐条确认：「写入不要判断了，太复杂了」。
- 会议事件直接写；对象状态在对象层面更新，留版本历史；和以前的版本冲突时，AI 判断并升级出来。
- 斯一负责卡住越权和乱写；Nexus 怎么写准，由溪南和斯一对。
- 下午你补充的「会后产出分两类」（决策改动、执行事项）也落在这四步里：Nexus 写和判定，天枢接收和呈现。

**天枢要做的三件事**：
1. **会前预约**：现有的约会议照旧。会上说过最好会前给 Agent 看材料（录音 103:41），先不做。
2. **接收两类卡，放进本人工作台**：
   - **改动或冲突卡**，给对象的负责人：写清改了什么、和以前哪条冲突、出自哪场会哪句话。三种处理：同意、不同意（附一句理由）、改说法。回应交回 Nexus，由 Nexus 写本体（我的猜测，要和溪南定）。
   - **执行事项卡**，给对应的人：一张卡装一个或多个，逐条翻看。每条带标题、出处、建议挂的 Mission/Task、建议截止。每条三个选择：
     - 接手：可以先改标题、Mission/Task、截止，再点接手。接手后它就成了本人的执行事项，来源记成「会议，本人接手」。这一步就是「人建」；
     - 转给别人：选一个人，附一句话，卡就转到那个人那里；
     - 不接：写一句为什么。
     全部处理完，卡消失。处理结果交回 Nexus。
   - 两类卡都出现在通知栏；胶囊在对话里说一句（第二批）；以后飞书里走本人自己的 bot 推（录音 76:03）。
3. **接手以后**：执行事项归本人，在天枢里推进。要拉人协作时，发起在天枢，多人的场子是 Nexus 的（分工会 06:06），现在天枢的事项群怎么办，待和溪南定。

**没人处理怎么办**（我定的，给溪南参考）：
- 不自动生效，不自动建，也不自动删。
- 3 个工作日没处理：胶囊提醒本人一次，主持人那边看得到还有几条没人处理。
- 7 天没处理：从本人通知栏收起，交回主持人处理。

**天枢原来的方案交给溪南、斯一参考**：
v0.4 里天枢自己做会后两类时定过一些细则，现在归 Nexus，留作参考：
- 要找人确认的四种：
  - 冲突：和本体里同一对象已记的事实不兼容；
  - 牵连：影响到别人负责的对象；
  - 推翻：让以前确认过的决策变了；
  - 进展改动：完成、延期、改截止、重开、取消。
- 下游要能分清四个状态：直接写入、待负责人确认、已确认、负责人不同意。
- 改错了，由人提更正，追加更正事件，原记录不删。
