## 1. 为什么改

- 自动生成执行事项没有意义，而且让人反感。采集「具体做了什么」像微观管理，几乎没人愿意被这样记，本体也不该留这些琐碎内容。
- 价值在两样东西上：产出物，以及向最终目标推进了多少。
- 所以天枢从「替你记事」转成「帮你把交付物做到达标」。事情由人自己建，进度一天收一次，Agent 的精力花在按验收标准评判交付物、陪人迭代上。
- 之前刻意弱化了 Agent 的人感，现在反过来：它要像一个常驻在旁边、说话简短的同事。
- 会上的原话（录音里没区分出这几段是谁说的）：
  - 每 30 分钟抓一次「逐渐就变成 1984 了」，收东西要「按目的去收」，「微观管理没有意义」（录音 55:00、66:52、67:47）；
  - 收的目的是转起数据飞轮，让 Agent 知道大家到底在干什么，这样才帮得上忙（录音 55:00、70:22）；
  - Agent 要当成人来看，平台界面只是它的「场子」，不是它本身（录音 91:34、92:32）。

## 2. 目标、非目标、反目标

**目标**
1. 进度一天收一次，只来自斯一的日进展；天枢不再自己采集。
2. 执行事项只由人建；天枢里任何地方都不再自动生成执行事项。
3. 选中 Mission、再选中 Task 后，页面以这个 Task 的交付物为中心：上传，或者用对话说现状。
4. Agent 按验收标准给交付物打分、出报告；人按报告迭代，达标才能提交；提交后交给下一方做进度评判。
5. Agent 以一个胶囊形象常驻在对话窗上方，说短句。
6. 会后产出分两类处理：
   - 决策上的修改直接改写本体，只有冲突、牵连别的事、推翻以前的决策、改动进展时才找负责人确认；
   - 执行事项由天枢起草成卡片推给对应的人，本人接手才算数。
   这一块要先和斯一谈妥，第一批不做。

**非目标**
- Task 下的 Activity 怎么建不再设计，随各人习惯。
- 交付物格式不预先规定，文档、链接、图片、一段说明都行。
- Task 的增删改不在天枢做。Task 在敲定 Mission Card 时就定了，归 M2。
- 不做多皮肤商店、语音、实时视频形象（Meta Muse 那种）。

**反目标**（即使功能跑通，出现这些也算失败）
- 天枢又在记「你今天做了什么」的流水账，或者把个人的日进展细节摊给别人看。
- Agent 当考官刁难人：只给分不说缺什么，或者凭空判「未达到」。
- Agent 的报告只是把进展汇编一遍，没有判断。会上对 Nexus 会议总结的评价就是「汇编的无脑 PMO，只看进展」（录音 90:19）。
- Agent 反应慢。会上有人问一句「进展怎么样」，它「判断意图」判断了 300 秒，最后回了一句「你到底想干啥」（录音 85:33）。
- Agent 说套话、说大话、动不动长篇。
- 胶囊形象抢注意力、显得幼稚。外界对 Meta Muse 的吉祥物 Jolly 就有「把用户当小孩」的批评。
- 界面上出现解释句。

- 模块边界照旧：`apps/web` 只做展示和 API 客户端；评审、状态、存储都在 `apps/api`；契约先改 `packages/contracts` 再生成客户端。
- 本体写入规则归斯一，Chat 服务和人设归人豪，M2 和 Co-Agent 归溪南。凡是要动他们那一侧的，先对齐再做。
- 不推送、不开 PR、不部署，除非孙铭泽说。流程照旧：测试计划，我在浏览器自测，他测，然后才推送或通知别人。
- 界面不写说明句；新界面复用 ts-design 的组件和主题变量、现有卡片样式，不加新颜色。
- 异步的事（评审）要显示实时阶段和已用时间，不让人干等。

## 5. 设计

### 5.1 进度：只收斯一的日进展，一天一次，先给 DRI agent 用

**收什么**：斯一的日进展 skill 每天 20:30 在本人电脑上跑，按本人负责的 Mission/Task 各写一条外部事件进本体，首行是「【日进展】姓名 日期」，正文四段：今日摘要、关键进展与结果、关键问题与不确定性、关键协同与待决事项。天枢只读这些事件，自己不再读任何人电脑上的会话。
- 会上说的是「只收进展和洞察，关心关键事、卡点、要不要升级」（录音 67:47）。所以 DRI agent 最看重四段里的进展、问题和待决，不是流水账（我定的）。洞察怎么进四段，要和斯一对齐。

**多久收一次**（我定的）：每天一次。
- 按下面「待定」里推荐的第三种：skill 每天跑完，就把四段交给天枢。
- 如果最后选第一种：天枢每天北京时间 21:30 从本体读一次当天的。
- 不管哪种，本人第二天第一次打开天枢时都再补一次，接住晚跑或补跑的。

**放在哪、给谁用**：
- 存进本人的 Agent 记忆，按「人 × 日期 × Task/Mission」存四段原文和本体事件 id。只本人的 DRI agent 读，别人看不到。在本体里谁能看到，照本体自己的权限，天枢不再多给一份。
- DRI agent 用它做三件事：
  1. 知道你昨天推进到哪，开口能接上，比如「昨天交了 v2，今天补录屏？」；
  2. 你点「说说现状」时，先拿昨天的日进展起个头，你改一句就能记成现状；
  3. 你问「我这周怎么样」时有依据可说。
- **不**拿来更新执行事项，不改事项状态，不写进展。

**天枢自己的采集器下线**（我定的）：

  - 待核、候选条目不进日进展；
  - 周复盘和会议结论只引用、不复述。

- 所以我改推第三种，两头都照顾到（我定的，要斯一同意）：
  1. skill 照旧在本人电脑上跑，按上午会上的口径只总结关键里程碑、卡点和洞察；
  2. 同一次运行里，完整四段用本人令牌交给天枢，进 DRI agent 的记忆，只本人可见；

  这样做到了：
  - 先进 DRI agent；
  - 大部分只有自己能看到（录音 59:50）；
  - 本人写（斯一）；
  - 天枢不用变成代写方。
  会议结论、周复盘在四段里只引用对应事件，不复述。
  第一批不做日进展，所以不管选哪种，第一批都不受影响。
- skill 丢答复的缺陷已经在 tkos-ontology-runtime #309 修好；天枢以后要接 skill 的输出时，以那个版本为准。
- 没装 skill 的人就没有日进展，DRI agent 对他只能靠对话和交付物。录音里田田正是这种情况（工作在云端 Chat 和飞书会议里），会上的说法是接不进来就自己手动补（录音 52:36–57:30）。能接受吗？

### 5.2 执行事项人建；交付物挂在 Task 上

**核心选择**（我定的）：交付物挂在 **Task** 上，不挂在执行事项上。

理由：
- 你说 Task 的边界就是「有没有一个从发布到验收、状态会变的迭代版本」，这个迭代版本就是交付物。
- Activity 交给个人习惯以后，粒度各人不同，挂在上面评判不稳定。
- 页面也是选中 Task 再看交付物。

**交付物的样子**：
- 一个 Task 一个交付物，交付物有多个版本：v1、v2、v3……
- 一个版本是下面两种之一：
  - 一组材料：文件、链接、图片，可附一句话；
  - 一段现状说明：通过对话形成的文字。
- 每个版本自动评审一次，评审结果跟着这个版本存。
- 交付物的状态（我定的）：

| 状态 | 什么时候进入 | 下一步 |
|-|-|-|
| 未开始 | 还没有版本 | 上传或说现状 |
| 迭代中 | 有版本，最新版没达标，或者达标了还没提交 | 改了再传、提交 |
| 已提交 | 提交了某个达标版本 | 下一方评判；评判前本人可以撤回 |
| 已通过 | 下一方评判通过 | — |
| 退回 | 下一方退回，带一句意见 | 回到迭代中，退回意见并进下一次评审 |

- 谁能上传、提交（我定的）：这个 Task 的负责人。同一 Mission 下的其他人只读。
- 存储（我定的）：新表存版本、评审报告、提交和评判记录；文件沿用材料上传，`object_type` 加一种指向交付物版本。交付物和评审是天枢自己的业务数据。「提交」和「通过」是公司事实，按 ADR-0027 最终要进本体，见 5.4。

**执行事项**：
- 只剩一个来源：人自己建，在页面上建，或者明确叫 AI 工具建。
- 页面上退到次要位置，见 5.3。现有的本人逐条验收保持不动，因为本来就是人在确认。
- 不再自动建：
  - 采集器本来就不建；
  - MCP 的说明改成「只在用户明确要你建时才建」，同时去掉「主动记进展」（采集只留斯一一套，见第 6 节第 4 条）；
  - 会后分派改成执行事项卡、本人接手，放到 5.6 一起改。
- 「一件 = 一个带 ◆ 关口的 Activity、1–2 周」这条粒度要求不再强制，MCP 说明里一并删掉。

### 5.3 选中 Mission、再选 Task 后的页面

顶行照旧：日历、Mission 选择，以及雷达、战场、发出去的消息、预约会议四个按钮。
选中 Mission 后左边还是 Task 列表，每个 Task 多一个小标记：未交、迭代中带分数、已提交、已通过、退回。
右边原来的执行事项两栏，换成选中 Task 的交付物面板。选中 Mission 时，默认选中第一个还没通过的 Task（我定的）。

```
┌ Task 列表 ───────┐┌ 交付物面板 ────────────────────────────────────┐
│ ● 上手流程  78    ││ 上手流程跑通                                    │
│ ○ 会议写回  未交  ││ [标准1 ✓] [标准2 ◐] [标准3 ✓] [标准4 ✗]         │
│ ✓ 页面上下文      ││                                                │
│                  ││  v1 62 · v2 78 · v3 评审中 00:41 / 约 1 分钟    │
│                  ││ ┌ v2 ──────────────────────────────────────┐   │
│                  ││ │ 📎 上手录屏.mp4  🔗 测试记录                │   │
│                  ││ │ (78) 2/4 条达到                           │   │
│                  ││ │ ✓ 标准1  一句理由                ▸         │   │
│                  ││ │ ◐ 标准2  缺什么、怎么补   [我不同意] ▸      │   │
│                  ││ │ ✗ 标准4  缺什么、怎么补   [我不同意] ▸      │   │
│                  ││ └──────────────────────────────────────────┘   │
│                  ││ [上传新版本]  [说说现状]            [提交]（灰）  │
│                  ││ ▸ 我的事项 3                                    │
└──────────────────┘└────────────────────────────────────────────────┘
```

**各状态的样子**：
- 未开始：上面一排验收标准（让人知道按什么评），下面一大块上传区（拖进来、点选、贴链接），旁边是「说说现状」。没有任何说明文字。
- 评审中：版本卡上显示当前阶段（读材料、对照第 2 条……）和「已用时间 / 预计时间」。
- 有报告：分数环加「几条达到」，每条一行：✓ 达到、◐ 部分、✗ 未达到，后面一句理由。展开后看证据（引用交付物里的哪一处）和建议怎么补。
- 已提交：版本锁定，显示交给了谁、提交了多久，可以撤回。
- 已通过或退回：显示结论和对方的一句话；退回以后回到「有报告」那一态。
- 版本条：v1 62 · v2 78 · v3 100 ✓，点哪个看哪个的报告。
- 我的事项：默认折叠，只列挂在这个 Task 上的人建事项，沿用现有卡片样式，可以在这里新建。

**上传交付物**：
- 面板里拖进来或点选，生成新版本，马上开始评审。
- 第二批在对话里也能传：文件拖进对话，Agent 只问一句「算『上手流程』的 v3？」，你说是就存。

**用对话说现状**：
- 点「说说现状」，对话窗带上这个 Task 开口，一句话起头。有昨天的日进展就拿它起头：「日进展说你把录屏做完了，还差测试记录？」
- Agent 最多追问一两句，然后用三行以内复述：「记成 v3：……？」你说好就存成一个「现状说明」版本，并开始评审。
- 评审出来以后，对话里只说一句结论（「3/4 条，差第 4 条：缺一次真人试用」），细节看面板。
- 实现上，天枢这边做一个「把现状存成交付物版本」的接口和工具。本地对话运行时第一批就接上；正式环境走人豪的 Chat 服务，要他接这个工具，并且页面上下文要带上选中的 Mission/Task（见第 7 节）。

### 5.4 Agent 评判：打分、报告、迭代、提交、流转

**按什么评**：
- 首选这个 Task 在本体里的验收标准（acceptance_criterion），没有就用 Task 的完成定义加 Mission 的成功证据。报告里标明按哪套标准评的（我定的）。
- 两样都没有时不评，面板显示「没有可对照的标准」这一态，只放一个找负责人补标准的入口。
- 你要的是「体验」层面的详细验收标准，这要在敲定 Mission Card 时由 M2 产出，见第 7 节溪南那一条。

**怎么评**（我定的）：
- 只按版本里有的证据判。没证据就判 ✗，并写清缺什么证据（比如「缺一段新人 3 分钟内走完上手的录屏」），不替人猜。
- 每条三档：达到、部分、未达到。每档都有一句理由、引用的证据位置、具体怎么补。
- 分数 = 各条平均（达到 100、部分 50、未达到 0）。分数就是达标进度，不另起一个看不懂的总分。
- 达标 = 每一条都「达到」，这时才能提交。
- 评新版本时，带上上一版的报告和退回意见，报告里说清这一版比上一版多达到了哪几条。
- 文件能读的就读：文档、PDF、图片；链接能读就读，读不了就在报告里说「这个链接我打不开」，请人导出上传（我定的）。
- 用重模型，异步跑，显示阶段和用时。复用现有的作业队列和对照完成标准起草验收的写法。

**判错了怎么办**（我定的）：
- 每条 ◐ 或 ✗ 旁边有「我不同意」，写一句为什么。Agent 带着这句话重评这一条。重评还是不过，这一条保留「本人有异议」的标记。
- 有异议的条目要不要也能提交，待定。按你说的「达标后才能提交」，默认不能。

**提交以后**：
- 提交的是「这个版本 + Agent 报告 + 本人异议（如果有）」。
- 下一方是谁，待定。我的猜测：语音里的「口」是 Co，指溪南的 Co-Agent。
  - 也就是：天枢把提交记进本体，Co-Agent 从本体读到后做进度评判，结论再经本体回来，天枢显示「已通过」或「退回 + 意见」。
  - 这样天枢和 Co-Agent 只通过本体交接，不用直连。
  - 录音里溪南讲 M2 时说过同一个思路：本人和自己的 Agent 聊完不能直接改，要由 Co-Agent 站在公司立场、中立客观地评判（录音 23:42）。
  - 分工就成了：你的 Agent 帮你把交付物做到达标，Co-Agent 判这件事推进了多少。
- 如果下一方是人，比如 Mission 负责人或你，就在他的通知栏出一张卡，点进去用二级页面的同一个壳：左边是交付物，右边是报告，逐条打勾后通过，或者写一句退回。Agent 报告预填逐条勾选，复用 `taskAcceptanceDraft` 的做法。
- 第一批「提交」只记在天枢里；写进本体用一个开关挡着，默认关，等斯一定好写入方式再开。

### 5.5 Agent 更像人：胶囊形象和短句

**参考**（10/29 查的）：
- Meta Muse：9 月上线的个人 Agent，形象是奶白色圆胖的 Jolly，名字和穿着可以自己改。
- OpenAI Dots：9 月 29 日发布，每个 Agent 是一个「冒泡的小团子」角色，可以选形象、宠物，起名字，定位是「一起干活的伙伴」。
- Claude Duet：10 月 21 日预览，主动型 Agent，早上给简报，敏感动作先问。

我从这三个里取：
- 有一个可辨认、可以起名的角色；
- 常驻、主动，但每次只说一点；
- 要做重要的事先问。

不取：实时视频形象、让人产生依赖的陪伴感。

会上的说法（录音 91:34–103:41）：
- 平台只是它的场子；
- 要想它还能以什么方式出现；
- 你们在给它「造脸、造手、造嘴」；
- 最好大家工作方式不变，它也能嵌进来。

所以胶囊不是首页的一个装饰，而是「你的 Agent」这个人在天枢里露的脸。以后它在飞书里也应该是你自己的那个 bot，而不是一个叫「天枢」的独立身份（录音 76:03，第二批以后）。

**胶囊**：
- 位置：对话窗顶部，替掉现在那行「我的对话」。
- 样子：一个横向小胶囊，左边是角色头像（第一批只做一个熊猫），右边是名字。高度和现在的标题行差不多，用 ts-design 的主题色，不加新颜色。
- 状态靠动作表达，不配文字：

| 状态 | 动作 |
|-|-|
| 空闲 | 偶尔眨眼 |
| 你在输入 | 看向输入框 |
| 在想 | 轻轻点头，评审等长任务旁边带阶段和用时 |
| 在说 | 嘴动 |
| 有事找你 | 胶囊轻跳一下，带一个小点 |

- 点胶囊展开一张小卡：名字、形象。第一批只能改名字，其余后面再做（我定的）。
- 同一个胶囊出现在所有和「我的天枢」对话的地方：首页、二级页面的对话栏、手机版的对话页。
- 以后还会出现在溪南那边：Co-Agent 页里嵌的个人对话，M2 复盘页里「我的 Agent」的头像。会上说过那个头像是临时的，应该由你来设计（录音 40:53）。
- 形象我先画一版简单的扁平 SVG 熊猫给你看，定稿再换（我定的）。画风参照你定过的「无边框、自然」。

**说话方式**（写进人设，第一批改本地运行时，正式环境的人设由人豪改）：
- 默认一到两句，一般不超过 40 字。一次只问一件事。
- 不说套话（「好的！我来为您……」），不说大话（「非常出色的进展！」），不主动列清单。
- 要长内容时（报告、文档），正文放到面板或文档里，对话里只说一句指过去。
- 可以把一段回复拆成两三个短气泡，像人连着发几条（我定的）。
- 像同事一样接着昨天说话，凭的是日进展和交付物的版本记录。不知道就说不知道。
- 先快速回一句再去想。像「进展怎么样」这种问题，不能让人等几分钟（录音 85:33 那次等了 300 秒）。要想久的事，胶囊进入「在想」，对话里先说一句「我看一下」（我定的）。
- 主动开口只在两个时候：
  - 当天第一次打开（一句现状加一个问题）；
  - 评审出了结果。
- 不推送，不刷存在感。

### 5.6 会后产出分两类（第一批不做，先和斯一谈）

**从哪改到哪**：原来是会后整理出决策和待办，推给相关的人，确认后才写本体。现在改成两类分开处理（口述，10/29 下午）：
1. 决策上的修改：直接改写本体里的内容。改的过程中有冲突、牵连到别的东西、让某个决策和以前不一样了，才找人确认。
2. 执行事项：单独做卡，一张卡装一个或多个，逐条翻看，推给对应的人，本人接手才算数。

你的原意：开完会每个人本来就要自己梳理该做什么；天枢把这前半段梳理好，本人只看总结、接手执行事项；接手后要协作，再在天枢里接着做。
录音里你演示时也是这个意思：会后妙记自动进天枢，提取执行事项推给对应参会人（录音 73:28）。

#### 第一类：决策上的修改

**什么直接写**（我定的，要斯一同意）：
- 新增的决策（不改已有内容）：写进这场会的主事件。一场会一个主事件，和斯一 10/28 第 6 条一致。
- 改已有内容，并且下面四条都满足的，直接修订那个对象：
  - 改的是参会人自己负责的对象；
  - 和本体里已记的事实不冲突；
  - 不牵连别人负责的对象；
  - 不推翻以前确认过的决策。
  修订引用这场会的主事件，标「会议直接修订、未经逐字确认」。

**什么要找人确认**（四种，任一种都算）：
- 冲突：和本体里同一对象当前已记的事实相反或不兼容，比如负责人、截止日期、范围或验收标准、优先级；或者和最近 30 天别的会上对同一对象的结论相反。
- 牵连：改动会影响别人负责的对象。比如改了一个 Task 的截止，另一个人负责的下游 Task 也得跟着动。
- 推翻：让以前确认过的某个决策变了。
- 进展改动：会改变某个对象的进度，比如完成、交付、延期、改截止、重开、取消。这条出自下午第一次补充；第二次补充没再提，我保留了。

**怎么判定**：写入前，按这条结论挂到的对象，读它的当前状态、下游关联和最近的决策事件，由模型逐条判这四种。拿不准的按「要确认」处理。

**要确认的怎么走**：
- 主事件里照记，标「待负责人确认」，对象本身先不改。
- 给那个对象的负责人发确认卡，三种处理：
  - 同意：追加确认事件，再按决策修订对象；
  - 不同意：追加更正事件，标「负责人不同意」，附一句理由；
  - 改说法：更正事件里带新内容，再按新内容修订。
- 没人回（我定的）：不自动生效。3 个工作日后提醒一次，同时让主持人看到。之后一直标「待确认」。
- 「确认决策」不等于「批准 Task 修改」（斯一 10/28 说的）：要改别人负责的对象，由那个人确认。

**下游怎么知道没确认**：
- 每条结论、每次会议修订都带四个状态之一：直接写入（未逐字确认）、待负责人确认、已确认、负责人不同意。同时带来源会议和版本。
- Chat、M2、Inception 引用时，要把这个状态显示出来。三方都能区分之前，按斯一 10/28 第 1 条，只留原记录链接。

**改错了怎么撤**：
- 直接写入的修订，参会人或这个对象的负责人都可以提更正。
- 提了以后，追加一条更正事件，再把对象修订回去或改成新内容。原记录不删。
- 斯一 10/28 说过「已执行的修改不自动撤销」。这里是人提更正后再改，不是自动撤，和他那条不冲突。

#### 第二类：执行事项卡

**起草**：
- 天枢从会议里提取「谁要做什么」，按人分组，每人一张卡，卡里一条或多条。
- 每条带：标题、出处（会上原话的位置）、建议挂的 Mission/Task、建议截止。
- 没有明确负责人的，交给主持人补，和斯一 10/28 第 3 条一致。

**推送**：
- 卡出现在本人通知栏。
- 第二批起，胶囊在对话里也说一句。
- 以后飞书里走本人自己的 bot 推（录音 76:03）。

**接手**（单独的一步）：在卡里逐条翻看，每条三个选择：
- 接手：可以先改标题、Mission/Task、截止，再点接手。接手后它就成了本人的执行事项，来源记成「会议，本人接手」。这一步就是「人建」。
- 转给别人：选一个人，附一句话，卡就转到那个人那里。主持人看得到。
- 不接：写一句为什么，这条回到主持人那里。
全部处理完，卡消失。

**没人接手怎么办**（我定的）：
- 不自动建，也不自动删。
- 3 个工作日没处理：胶囊提醒本人一次，主持人那边显示「还有 N 条没人接」。
- 7 天没处理：从本人通知栏收起，放进主持人的「没人接的事」，由主持人改派、自己接或者关掉。
- 本体里这场会的主事件记着每条的状态：待接手、已接手（谁）、转给了谁、不接（理由）、主持人已关。

**接手以后**：要协作就拉人进事项群，沿用现有的事项群（录音 46:52 你演示的那套）。

**和现在的做法比**：
- 现在 `dispatchMeetingTodo` 在行动项确认后直接建事项，挂不上的进「待归位」。
- 没有负责人的行动项默认记给主持人，所以主持人名下会多出主语是别人的事项（第 4 节）。
- 改成上面这样以后，会议不再直接建事项，「待归位」也不再有新来源。
- 第一批要不要先把会后分派关掉，见第 10 节第 7 问。

**和斯一 10/28 规则的冲突**：见第 6 节第 1 条。谈妥之前，照斯一 10/29 16:27 同意的现行规则走：只写本人逐条确认过的决策和行动项，不改对象，不代确认。人工过渡和每天的只读核查都已经停了。
