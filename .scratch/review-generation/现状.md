# 月末复盘链路：现状与缺口（2026-10-17）

分支 `feat/review-generation`，基于本地 `feat/collector`（要用它的 `collector_items`，迁移 075）。行号以这个分支为准。

## 结论

1. 天枢的月末链路从个人复盘到起草任务卡，每一段都已经有了，而且都由 Co-Agent 自动起草，人只做修改和确认。
2. 和你定的五步比，缺三样：
   - **个人复盘不读采集记录**，「每周复盘」只是混在执行事项进展里，没有按周整理；没有出处约束；重新起草要先上传材料，并且会覆盖本人改过的内容。这一块这次做了，见第 4 节。
   - **10 月 Mission 卡还不在天枢里**。这是个人复盘的前提：复盘开启时只给「这个月有 Mission 的人」建个人复盘。接口见第 5 节，等下周拿到格式再做。
   - **公司复盘要等战场复盘逐项提交、CEO 逐项确认之后才生成**，中间多了一层人工关口；它也不判断 PO 要不要变。设计见第 6 节，这次不做。

## 2. 重点看的三件事

### 个人复盘草稿现在怎么生成

- 开启复盘时，每个有当月 Mission 的人建一份，状态直接是「起草中」，Co-Agent 马上起草（monthlyReviewService.ts:386-400）。
- 输入只有三类：Mission 全文、本人负责的执行事项进展、复盘对话里的材料。**不读采集记录。**
- 输出四栏，每栏一个 `sources` 列表。提示词只要求「sources 引用输入中真实的 Mission、进展日期、附件或消息」，服务端不核对，正文里也没有出处标记。
- 重新起草的按钮只在上传过材料后出现，而且整份覆盖，本人改过的段落也会被覆盖。
- 另一条路是本人的 AI 工具经 MCP 读 `get_my_review`、写 `save_review_draft`。

### 「每周复盘」从哪来

- 天枢里没有单独的「周复盘」。每周的东西是**执行事项进展**（`task_progress`）：本人或本人的 AI 工具每周「同步本周进展」写进来，周五 18 点起没同步会提醒（weeklySyncReminder.ts）。周进展页按 ISO 周汇总它（weeklyProgress.ts:43）。
- 个人复盘起草时读的就是这张表，但只取「本人负责的执行事项」，不按周分，最多 60 条，本人在别人事项上写的进展读不到。
- 飞书里每个人写的周复盘文档，只在 9 月导入时给两个人当过起草材料（`personal_reviews.imported_materials`），没有常规的载入通道。

### 公司复盘有没有自动生成

有。战场复盘全部确认后自动进入「汇总中」，Agent 生成四部分和 LTCO 修订建议，CEO 改、确认，再做 LTCO 决定。但它不是「所有人确认个人复盘后」就生成：中间要经过战场复盘的起草、负责人提交、偏差评估、CEO 逐项确认。

## 4. 这次实现：个人复盘生成

- **输入**：在原来的 Mission 全文、复盘对话材料之外，加两项：
  - **每周复盘**：按 ISO 周整理本人当月的执行事项进展（本人写的，或写在本人负责事项上的），只列已经开始的周；某周没有记录也列出来，标成缺少记录。
  - **采集记录**：本人在当月（北京时间）开始的 `collector_items`，按时间排列，最多取最近 150 条，每条摘要截到 500 字。
- **出处**：每条输入记录带 `cite` 和 `label`，Agent 照抄成 `[label](cite:…)` 写在句末，用的是对话里已有的出处语法。服务端逐行核对：每一行都要有出处，或者是「缺少记录」，或者是「无」；出处只能是这次输入里真有的记录。不合格就重试，三次都不合格算起草失败。`sources` 由服务端按正文里的出处生成。
- **缺少记录**：Mission 卡、每周复盘、采集记录哪一类是空的，就在输入里列出来，草稿里必须如实写「缺少记录」。
- **步骤**：读 Mission 卡 → 读每周复盘 → 读采集记录 → 起草，每步 `{id,label,status,result?}`，存在 `personal_reviews.generation_steps`，随个人复盘一起返回；`startPersonalDraft` 另外接受一个 `onStep` 回调，给以后「一句话生成」的对话工具用。
- **本人的修改不被覆盖**：本人（或本人的 AI 工具）保存过的段落记在 `personal_reviews.edited_fields`；重新生成只替换没改过的段落，改过但清空的段落会重新生成。
- **入口**：沿用 `personal-review.draft_with_co_agent` 动作，不再要求先上传材料，按钮在页头，没有草稿时叫「生成」，有了叫「重新生成」（手机上只留图标）。生成中显示步骤，生成后可以展开「生成过程」看每步结果；段落里的出处显示成句末小标记，悬停看名称；每段单独点「修改」，出处在编辑框里显示成〔名称〕，保存时还原成原来的出处，删掉〔名称〕就是去掉这条出处；改过的段落标「你改过」。原来「上传材料，让 Co-Agent 重新起草」「直接改」两张说明卡去掉了，只留「让你的 AI 工具补充改写」。
- 顺带修了对话出处标记的一个问题：几个出处紧挨着写（中间没有顿号）时，只有最后一个变成小标记，前面的显示成名称（citationMarks.ts）。
- 迁移：`077_personal_review_generation.sql`。078 没有用。
- 这次不做：对话里的「一句话生成」工具（等 W3 合并）；MCP `get_my_review` 仍是原来的输入。

## 5. Mission 卡预载：接口设计（不实现）

**为什么要在 10/28 前做完**：复盘开启时，只给 `missions` 表里有 `period=2026-10` 的负责人建个人复盘（personalReviews.ts:34）。10 月的卡不进 `missions`，这些人就没有个人复盘，后面战场复盘、公司复盘也拿不到他们的 Mission。

**入口**：CEO 接口，和现有 `POST /api/config/missions` 同一套校验与写入；另配一个 CLI，方便在服务器上先试跑。

```
POST /api/config/missions/import-feishu         （只有 CEO）
pnpm --filter @warmap/api missions:import-feishu <链接或 token> --period 2026-10 [--dry-run]
```

**输入**

```ts
{
  source: { url: string } | { token: string };  // 知识库页面链接 https://tokenking.feishu.cn/wiki/<node_token>，或 node_token / docx 的 obj_token
  period: "2026-10";
  dryRun?: boolean;                              // 只解析、校验，不写库
}
```

服务端用天枢的飞书应用身份（W1 接入后）解析：wiki 节点 → 文档 obj_token 和版本号 → 正文块。一份文档里有多张卡还是一人一份子页面，等拿到格式再定；解析结果先变成和 `missions:import` 相同的行：`ownerId`（按 company-people 的姓名匹配）、`code`、`title`、`capabilityCode`、`battlefieldCodes`、`outcome`、`why`、`successEvidence`、`milestones`、`boundaries` 等 Mission 卡字段。

**输出**

- 落到 **`missions` 表**：`period=2026-10`，`source_ref`=页面链接，`source_document_id`=obj_token，`source_revision`=文档版本，`source_title`=页面标题。复用 `registerMission`，能力域、战场按编号匹配，一批一个事务，有一条不合法整批不写。
- 同一文档同一版本重复导入跳过；文档改了版本再导入，同一张卡（同 owner + 同编号）按新版本更新，已经有个人复盘起草后不再改。
- 返回：

```ts
{
  created: number; updated: number; skipped: number;
  unmatched: { name: string; reason: "人员不在名单" | "能力域编号不存在" | "战场编号不存在" | "缺少必填字段" }[];
  missions: { id: string; ownerId: string; code: string; title: string }[];
}
```

**依赖**：飞书应用的知识库读权限（W1）；拿到 10 月卡的实际格式。迁移不需要，`missions` 现有字段够用。

## 6. 公司复盘自动生成：设计（不实现）

现有的汇总生成器保留，改三处：

1. **触发**：在「个人复盘全部提交或跳过」这一步之后直接往下走。做法是给 `monthly_reviews` 加一种来源 `auto`（和 9 月导入用的 `origin='import'` 同一条路径）：战场复盘由 Co-Agent 起草后直接确认，不走负责人提交和 CEO 逐项确认，紧接着生成公司复盘。10 月这一轮开启时设成 `auto`；以后要恢复逐项确认，不设就行。
2. **输入**：在已确认的战场复盘之外，加上每个人已提交的个人复盘四栏（带出处），和 10 月的月度计划（公司结果、各战场 PO）。
3. **输出**：在现有的总体结果、关键判断、下周期重点、`ltcoSuggestion`（方向和战场 LTO 要不要变）之外，加一个 `poSuggestion`：每个战场 10 月的 PO 在 11 月是延续、调整还是结束，带理由和出处。CEO 确认公司复盘、做完 LTCO 决定后，`poSuggestion` 进入下月计划草案的输入，CEO 签发时看得到。

界面不新增页面：仍在 /reviews/[period] 看、改、确认；LTCO 页多一栏 PO 建议。

## 7. 需要你定的问题

1. **「每周复盘」指什么**：这次按天枢里的执行事项周进展来做（每周「同步本周进展」写进来的那份）。如果你说的是每个人在飞书里写的周复盘文档，需要像 Mission 卡一样做一个载入通道，落到一张新表（可以用预留的 078），生成时在「读每周复盘」这一步一起读。
2. **10 月的个人复盘要不要跳过战场复盘这一层**（第 6 节第 1 点）：跳过就能在个人复盘交齐后直接出公司复盘，但战场负责人不再逐项提交，CEO 不再逐项确认。
3. **复盘开启时要不要自动起草**：现在开启当天就为每个人自动生成一版。按 10/29「每个人说一句生成我的复盘」的设想，也可以改成开启后等本人点「生成」，这样生成时采集记录更全。这次没改，仍然自动起草。
